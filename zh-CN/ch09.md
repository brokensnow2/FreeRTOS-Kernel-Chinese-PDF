# 9 事件组

<a id="91-chapter-introduction-and-scope"></a>
## 9.1 本章简介与范围

前文已经指出，实时嵌入式系统必须响应事件并采取相应动作。前几章介绍了 FreeRTOS 中用于把事件传递给任务的功能，例如信号量和队列。它们都具有以下特性：

- 允许任务进入阻塞状态，等待单个事件发生。

- 事件发生时，只解除一个任务的阻塞。被解除阻塞的是等待该事件的任务中优先级最高的任务。

事件组是 FreeRTOS 提供的另一种任务事件通知机制。与队列和信号量不同：

- 事件组允许任务进入阻塞状态，等待一个或多个事件的组合发生。

- 当某个事件或事件组合发生时，事件组会解除所有等待同一事件或事件组合的任务的阻塞。

事件组的这些独特属性使其适合用于同步多个任务、向多个任务广播事件、让任务在阻塞状态下等待一组事件中的任意一个发生，以及等待多个操作全部完成。

事件组还有助于减少应用程序的 RAM 占用，因为很多情况下可以用一个事件组替代多个二值信号量。

事件组功能是可选的。要在项目中使用事件组，请把 FreeRTOS 源文件 `event_groups.c` 加入构建。

<a id="911-scope"></a>
### 9.1.1 范围

本章旨在帮助读者充分理解：

- 事件组的实际用途。
- 与 FreeRTOS 其他功能相比，事件组的优点和缺点。
- 如何设置事件组中的位。
- 如何进入阻塞状态，等待事件组中的位被置位。
- 如何使用事件组同步一组任务。

## 9.2 事件组的特性

<a id="921-event-groups-event-flags-and-event-bits"></a>
### 9.2.1 事件组、事件标志和事件位

事件“标志”是一个布尔值（1 或 0），用于表示某个事件是否已经发生。事件“组”则是一组事件标志。

事件标志只能是 1 或 0，因此单个事件标志的状态可以存储在一个位中，而事件组中全部事件标志的状态可以存储在一个变量中。事件组内每个事件标志的状态，由 `EventBits_t` 类型变量中的一个位表示。因此，事件标志也称为事件“位”。如果 `EventBits_t` 变量中的某一位被置为 1，则该位代表的事件已经发生；如果某一位为 0，则该位代表的事件尚未发生。

- 定义事件组中的位 1 表示“已有消息准备发送到网络”。

- 定义事件组中的位 2 表示“中止当前网络连接”。

<a id="922-more-about-the-eventbitst-data-type"></a>
### 9.2.2 深入了解 EventBits_t 数据类型

事件组中可用事件位的数量取决于 FreeRTOSConfig.h 中的编译期配置常量 `configTICK_TYPE_WIDTH_IN_BITS`[^24]：

[^24]: `configTICK_TYPE_WIDTH_IN_BITS` 用于配置保存 RTOS Tick 计数的数据类型，看起来似乎与事件组功能无关。它之所以会影响 `EventBits_t` 类型，是 FreeRTOS 内部实现方式造成的。尽管把 `configTICK_TYPE_WIDTH_IN_BITS` 设为 `TICK_TYPE_WIDTH_16_BITS` 可能有其优势，但只有当 FreeRTOS 运行所在的体系结构处理 16 位类型比处理 32 位类型更高效时，才应这样配置。

- 如果 `configTICK_TYPE_WIDTH_IN_BITS` 为 `TICK_TYPE_WIDTH_16_BITS`，则每个事件组包含 8 个可用事件位。

- 如果 `configTICK_TYPE_WIDTH_IN_BITS` 为 `TICK_TYPE_WIDTH_32_BITS`，则每个事件组包含 24 个可用事件位。

- 如果 `configTICK_TYPE_WIDTH_IN_BITS` 为 `TICK_TYPE_WIDTH_64_BITS`，则每个事件组包含 56 个可用事件位。

<a id="923-access-by-multiple-tasks"></a>
### 9.2.3 多任务访问

事件组本身就是一种对象，任何知道其存在的任务或 ISR 都可以访问它。任意数量的任务都可以在同一个事件组中置位，也可以读取同一个事件组中的位。

<a id="924-a-practical-example-of-using-an-event-group"></a>
### 9.2.4 使用事件组的实际示例

FreeRTOS+TCP 协议栈的实现提供了一个实际示例，说明事件组如何同时简化设计并尽量减少资源占用。

TCP 套接字必须响应许多不同事件，例如接受事件、绑定事件、读取事件和关闭事件。套接字在某一时刻可能遇到哪些事件，取决于套接字当前的状态。例如，如果套接字已经创建但尚未绑定地址，那么它可能接收到绑定事件，却不会接收到读取事件，因为没有地址的套接字无法读取数据。

FreeRTOS+TCP 套接字的状态保存在名为 `FreeRTOS_Socket_t` 的结构体中。该结构体包含一个事件组，其中为套接字必须处理的每种事件分别定义了一个事件位。需要阻塞等待某个事件或一组事件的 FreeRTOS+TCP API 调用，只需阻塞在这个事件组上。

该事件组还包含一个“中止”位，因此无论套接字当时正在等待哪种事件，都可以中止 TCP 连接。

<a id="93-event-management-using-event-groups"></a>
## 9.3 使用事件组管理事件

<a id="931-the-xeventgroupcreate-api-function"></a>
### 9.3.1 xEventGroupCreate() API 函数

事件组必须先显式创建才能使用。FreeRTOS 还提供 `xEventGroupCreateStatic()` 函数，它使用调用者提供的 `StaticEventGroup_t` 缓冲区创建事件组，而不从 FreeRTOS 堆中动态分配内存。

事件组通过 `EventGroupHandle_t` 类型的变量引用。`xEventGroupCreate()` API 函数用于创建事件组，并返回一个用于引用所创建事件组的 `EventGroupHandle_t`。

<a name="list9.1" title="代码清单 9.1 xEventGroupCreate() API 函数原型"></a>

```c
EventGroupHandle_t xEventGroupCreate( void );
```
***代码清单 9.1*** *`xEventGroupCreate()` API 函数原型*

**xEventGroupCreate() 返回值**

- 返回值

  如果返回 `NULL`，则事件组创建失败，因为 FreeRTOS 没有足够的堆内存用于分配事件组数据结构。第 3 章提供了更多堆内存管理信息。

  非 `NULL` 返回值表示事件组创建成功。该返回值应保存为所创建事件组的句柄。

<a id="932-the-xeventgroupsetbits-api-function"></a>
### 9.3.2 xEventGroupSetBits() API 函数

`xEventGroupSetBits()` API 函数用于设置事件组中的一个或多个位，通常用来通知任务：被置位的一个或多个位所代表的事件已经发生。

> *注意：切勿从中断服务程序调用 `xEventGroupSetBits()`，应改用其中断安全版本 `xEventGroupSetBitsFromISR()`。*

<a name="list9.2" title="代码清单 9.2 xEventGroupSetBits() API 函数原型"></a>

```c
EventBits_t xEventGroupSetBits( EventGroupHandle_t xEventGroup,

const EventBits_t uxBitsToSet );
```
***代码清单 9.2*** *`xEventGroupSetBits()` API 函数原型*

**xEventGroupSetBits() 参数和返回值**

- `xEventGroup`

  要在其中设置位的事件组句柄。该句柄由创建事件组时调用的 `xEventGroupCreate()` 返回。

- `uxBitsToSet`

  一个位掩码，用于指定要在事件组中置为 1 的一个或多个事件位。事件组的原值与 `uxBitsToSet` 按位或后，得到更新后的事件组值。

  例如，把 `uxBitsToSet` 设为 0x04（二进制 0100），会使事件组中的事件位 2 被置位（如果尚未置位），而其他事件位保持不变。

- 返回值

  `xEventGroupSetBits()` 返回时事件组的值。请注意，返回值中不一定仍然包含 `uxBitsToSet` 指定的置位状态，因为这些位可能已经被另一个任务再次清零。

<a id="933-the-xeventgroupsetbitsfromisr-api-function"></a>
### 9.3.3 xEventGroupSetBitsFromISR() API 函数

`xEventGroupSetBitsFromISR()` 是 `xEventGroupSetBits()` 的中断安全版本。

“给出”信号量是一项确定性操作，因为事先可以确定：给出一个信号量最多只会使一个任务离开阻塞状态。设置事件组中的位时，事先无法确定会有多少任务离开阻塞状态，因此在事件组中置位不是确定性操作。

FreeRTOS 的设计与实现规范不允许在中断服务程序内或中断被禁用时执行非确定性操作。因此，`xEventGroupSetBitsFromISR()` 不会直接在中断服务程序中设置事件位，而是把这项操作延迟到 RTOS 守护任务中执行。

<a name="list9.3" title="代码清单 9.3 xEventGroupSetBitsFromISR() API 函数原型"></a>

```c
BaseType_t xEventGroupSetBitsFromISR( EventGroupHandle_t xEventGroup,
                                      const EventBits_t uxBitsToSet,
                                      BaseType_t *pxHigherPriorityTaskWoken );
```
***代码清单 9.3*** *`xEventGroupSetBitsFromISR()` API 函数原型*

**xEventGroupSetBitsFromISR() 参数和返回值**

- `xEventGroup`

  要在其中设置位的事件组句柄。该句柄由创建事件组时调用的 `xEventGroupCreate()` 返回。

- `uxBitsToSet`

  一个位掩码，用于指定要在事件组中置为 1 的一个或多个事件位。事件组的原值与 `uxBitsToSet` 按位或后，得到更新后的事件组值。

  例如，把 `uxBitsToSet` 设为 0x05（二进制 0101），会使事件组中的事件位 2 和事件位 0 被置位（如果尚未置位），而其他事件位保持不变。

- `pxHigherPriorityTaskWoken`

  `xEventGroupSetBitsFromISR()` 不会直接在中断服务程序中设置事件位，而是通过向定时器命令队列发送命令，把这项操作延迟到 RTOS 守护任务中执行。如果守护任务原本处于阻塞状态，等待定时器命令队列中出现数据，那么写入定时器命令队列会使守护任务离开阻塞状态。如果守护任务的优先级高于当前正在执行的任务（即被中断的任务），`xEventGroupSetBitsFromISR()` 会在内部把 `*pxHigherPriorityTaskWoken` 设为 `pdTRUE`。

  如果 `xEventGroupSetBitsFromISR()` 把该值设为 `pdTRUE`，则应在退出中断前执行上下文切换。这样可确保中断直接返回到守护任务，因为守护任务将是处于就绪状态的最高优先级任务。

- 返回值

  可能有两种返回值：

  - 只有在数据成功发送到定时器命令队列时才返回 `pdPASS`。

  - 如果定时器命令队列已满，导致“设置位”命令无法写入队列，则返回 `pdFALSE`。

<a id="934-the-xeventgroupwaitbits-api-function"></a>
### 9.3.4 xEventGroupWaitBits() API 函数

`xEventGroupWaitBits()` API 函数允许任务读取事件组的值；如果指定的事件位尚未置位，还可以选择让任务进入阻塞状态，等待事件组中的一个或多个事件位被置位。

<a name="list9.4" title="代码清单 9.4 xEventGroupWaitBits() API 函数原型"></a>

```c
EventBits_t xEventGroupWaitBits( EventGroupHandle_t xEventGroup,
                                 const EventBits_t uxBitsToWaitFor,
                                 const BaseType_t xClearOnExit,
                                 const BaseType_t xWaitForAllBits,
                                 TickType_t xTicksToWait );
```
***代码清单 9.4*** *`xEventGroupWaitBits()` API 函数原型*

调度器用来判断任务是否进入阻塞状态以及何时离开阻塞状态的条件，称为“解除阻塞条件”。该条件由 `uxBitsToWaitFor` 和 `xWaitForAllBits` 两个参数的取值共同指定：

- `uxBitsToWaitFor` 指定要检查事件组中的哪些事件位。

- `xWaitForAllBits` 指定使用按位或测试，还是按位与测试。

如果调用 `xEventGroupWaitBits()` 时任务的解除阻塞条件已经满足，任务不会进入阻塞状态。

表 6 给出了会使任务进入或离开阻塞状态的条件示例。表中只显示事件组值和 `uxBitsToWaitFor` 值最低的 4 个二进制位，假定这两个值的其他位均为 0。

<a name="tbl6" title="表 6 uxBitsToWaitFor 和 xWaitForAllBits 参数的作用"></a>

* * *
| 事件组现有值 | `uxBitsToWaitFor` 值 | `xWaitForAllBits` 值 | 结果行为 |
| ------------ | --------------------- | --------------------- | -------- |
| 0000 | 0101 | `pdFALSE` | 事件组中的位 0 和位 2 均未置位，因此调用任务进入阻塞状态；位 0 或位 2 中任意一个被置位时，任务离开阻塞状态。 |
| 0100 | 0101 | `pdTRUE` | 事件组中的位 0 和位 2 尚未同时置位，因此调用任务进入阻塞状态；位 0 和位 2 都被置位时，任务离开阻塞状态。 |
| 0100 | 0110 | `pdFALSE` | `xWaitForAllBits` 为 `pdFALSE`，而 `uxBitsToWaitFor` 指定的两个位中已有一个置位，因此调用任务不会进入阻塞状态。 |
| 0100 | 0110 | `pdTRUE` | `xWaitForAllBits` 为 `pdTRUE`，而 `uxBitsToWaitFor` 指定的两个位中只有一个置位，因此调用任务进入阻塞状态；位 1 和位 2 都被置位时，任务离开阻塞状态。 |

***表 6*** *`uxBitsToWaitFor` 和 `xWaitForAllBits` 参数的作用*
* * *

调用任务通过 `uxBitsToWaitFor` 参数指定要检查的位，而且通常需要在解除阻塞条件满足后把这些位清零。可以使用 `xEventGroupClearBits()` API 函数清除事件位，但在以下情况下，手动调用该函数清除事件位会在应用程序代码中造成竞态条件：

- 多个任务使用同一个事件组。
- 事件组中的位由另一个任务或中断服务程序设置。

`xClearOnExit` 参数用于避免这些潜在的竞态条件。如果把 `xClearOnExit` 设为 `pdTRUE`，那么从调用任务的角度看，检查并清除事件位是一项原子操作，不会被其他任务或中断打断。

**xEventGroupWaitBits() 参数和返回值**

- `xEventGroup`

  包含待读取事件位的事件组句柄。该句柄由创建事件组时调用的 `xEventGroupCreate()` 返回。

- `uxBitsToWaitFor`

  一个位掩码，用于指定要在事件组中检查的一个或多个事件位。

  例如，如果调用任务希望等待事件组中的事件位 0 和/或事件位 2 被置位，则把 `uxBitsToWaitFor` 设为 0x05（二进制 0101）。更多示例请参见表 6。

- `xClearOnExit`

  如果调用任务的解除阻塞条件已经满足，并且 `xClearOnExit` 为 `pdTRUE`，那么调用任务退出 `xEventGroupWaitBits()` API 函数之前，事件组中由 `uxBitsToWaitFor` 指定的事件位会被清零。

  如果 `xClearOnExit` 为 `pdFALSE`，则 `xEventGroupWaitBits()` API 函数不会修改事件组中各事件位的状态。

- `xWaitForAllBits`

  `uxBitsToWaitFor` 参数指定要在事件组中检查的事件位。`xWaitForAllBits` 则指定：当 `uxBitsToWaitFor` 所指定的一个或多个事件位被置位时，就把调用任务移出阻塞状态；还是只有在指定的所有事件位均被置位时，才把任务移出阻塞状态。

  如果 `xWaitForAllBits` 为 `pdFALSE`，那么因等待解除阻塞条件满足而进入阻塞状态的任务，会在 `uxBitsToWaitFor` 指定的任意事件位被置位时离开阻塞状态，或者在 `xTicksToWait` 指定的超时时间到期时离开阻塞状态。

  如果 `xWaitForAllBits` 为 `pdTRUE`，那么因等待解除阻塞条件满足而进入阻塞状态的任务，只有在 `uxBitsToWaitFor` 指定的全部事件位都被置位时才会离开阻塞状态，或者在 `xTicksToWait` 指定的超时时间到期时离开阻塞状态。

  相关示例请参见表 6。

- `xTicksToWait`

  任务为了等待解除阻塞条件满足而保持阻塞状态的最长时间。

  如果 `xTicksToWait` 为 0，或者调用 `xEventGroupWaitBits()` 时解除阻塞条件已经满足，`xEventGroupWaitBits()` 会立即返回。

  阻塞时间以 Tick 周期为单位，因此它所代表的绝对时间取决于 Tick 频率。宏 `pdMS_TO_TICKS()` 可把以毫秒表示的时间转换为以 Tick 表示的时间。

  如果 FreeRTOSConfig.h 中的 `INCLUDE_vTaskSuspend` 设为 1，把 `xTicksToWait` 设为 `portMAX_DELAY` 会使任务无限期等待，不会超时。

- 返回值

  如果 `xEventGroupWaitBits()` 因调用任务的解除阻塞条件得到满足而返回，则返回值是条件满足时的事件组值，也就是在 `xClearOnExit` 为 `pdTRUE` 时自动清除任何位之前的值。此时，返回值也满足解除阻塞条件。

  如果 `xEventGroupWaitBits()` 因 `xTicksToWait` 参数指定的阻塞时间到期而返回，则返回值是阻塞时间到期时的事件组值。此时，返回值不满足解除阻塞条件。

***示例 9.1*** *试验事件组*

本示例演示如何：

- 创建事件组。
- 从中断服务程序设置事件组中的位。
- 从任务设置事件组中的位。
- 阻塞在事件组上。

本示例先把 `xEventGroupWaitBits()` 的 `xWaitForAllBits` 参数设为 `pdFALSE` 执行一次，再把它设为 `pdTRUE` 执行一次，以展示该参数的作用。

事件位 0 和事件位 1 由任务设置，事件位 2 由中断服务程序设置。代码清单 9.6 使用 `#define` 语句为这三个位定义了便于理解的名称。

<a name="list9.6" title="代码清单 9.6 示例 9.1 使用的事件位定义"></a>

```c
/* 事件组中各事件位的定义。 */
#define mainFIRST_TASK_BIT ( 1UL << 0UL )  /* 事件位 0，由任务设置 */
#define mainSECOND_TASK_BIT ( 1UL << 1UL ) /* 事件位 1，由任务设置 */
#define mainISR_BIT ( 1UL << 2UL )         /* 事件位 2，由 ISR 设置 */
```

## 9.4 使用事件组同步任务

应用程序的设计有时要求两个或多个任务彼此同步。例如，设想任务 A 接收到一个事件后，把该事件所需的部分处理工作交给任务 B、任务 C 和任务 D。如果任务 B、C、D 全部完成对上一个事件的处理之前，任务 A 不能接收下一个事件，那么这四个任务就必须彼此同步。每个任务完成自己的处理工作后到达同步点，在其他任务也完成处理之前不能继续执行。只有当四个任务全部到达各自的同步点后，任务 A 才能接收下一个事件。

FreeRTOS+TCP 的一个演示项目给出了更具体的任务同步示例。该演示让两个任务共享一个 TCP 套接字：一个任务向套接字发送数据，另一个任务从同一套接字接收数据[^25]。在确认另一个任务不会再次访问套接字之前，任何一个任务关闭套接字都不安全。如果其中一个任务希望关闭套接字，它必须先把这一意图通知另一个任务，然后等待另一个任务停止使用套接字。代码清单 9.11 的伪代码展示了发送任务希望关闭套接字时的情形。

[^25]: 在编写本书时，这是让多个任务共享同一个 FreeRTOS+TCP 套接字的唯一方式。

代码清单 9.11 所示情形很简单，因为只有两个任务需要彼此同步。但可以看出，如果还有其他任务执行依赖套接字保持打开的处理工作，这种情形会迅速变得复杂，并要求更多任务参与同步。

<a name="list9.11" title="代码清单 9.11 两个任务相互同步的伪代码，用于确保关闭共享 TCP 套接字之前两个任务都不再使用它"></a>

```c
void SocketTxTask( void *pvParameters )
{
    xSocket_t xSocket;
    uint32_t ulTxCount = 0UL;

    for( ;; )
    {
        /* 创建新套接字。本任务向该套接字发送数据，另一个任务从中接收数据。 */
        xSocket = FreeRTOS_socket( ... );

        /* 连接套接字。 */
        FreeRTOS_connect( xSocket, ... );

        /* 使用队列把套接字发送给接收数据的任务。 */
        xQueueSend( xSocketPassingQueue, &xSocket, portMAX_DELAY );

        /* 向套接字发送 1000 条消息，然后关闭套接字。 */
        for( ulTxCount = 0; ulTxCount < 1000; ulTxCount++ )
        {
            if( FreeRTOS_send( xSocket, ... ) < 0 )
            {
                /* 发生意外错误，退出循环，随后关闭套接字。 */
                break;
            }
        }

        /* 通知 Rx 任务：Tx 任务希望关闭套接字。 */
        TxTaskWantsToCloseSocket();

        /* 这是 Tx 任务的同步点。Tx 任务在此等待 Rx 任务到达它的同步点。
           只有当 Rx 任务不再使用套接字时，它才会到达同步点，此时可以
           安全关闭套接字。 */
        xEventGroupSync( ... );

        /* 两个任务都不再使用套接字。关闭连接，然后关闭套接字。 */
        FreeRTOS_shutdown( xSocket, ... );
        WaitForSocketToDisconnect();
        FreeRTOS_closesocket( xSocket );
    }
}
/*-----------------------------------------------------------*/

void SocketRxTask( void *pvParameters )
{
    xSocket_t xSocket;

    for( ;; )
    {
        /* 等待接收由 Tx 任务创建并连接的套接字。 */
        xQueueReceive( xSocketPassingQueue, &xSocket, portMAX_DELAY );

        /* 持续从套接字接收数据，直到 Tx 任务希望关闭套接字。 */
        while( TxTaskWantsToCloseSocket() == pdFALSE )
        {
           /* 接收并处理数据。 */
           FreeRTOS_recv( xSocket, ... );
           ProcessReceivedData();
        }

        /* 这是 Rx 任务的同步点。只有不再使用套接字时，Rx 任务才会到达
           这里，因此此时 Tx 任务可以安全关闭套接字。 */
        xEventGroupSync( ... );
    }
}
```

***代码清单 9.11*** *两个任务相互同步的伪代码，用于确保关闭共享 TCP 套接字之前两个任务都不再使用它*

可以使用事件组创建同步点：

- 为必须参与同步的每个任务，在事件组中分别分配一个唯一的事件位。

- 每个任务到达同步点时，设置代表自己的事件位。

- 设置自己的事件位后，每个任务都阻塞在事件组上，等待代表其他所有同步任务的事件位也被置位。

但是，不能在这种场景中组合使用 `xEventGroupSetBits()` 和 `xEventGroupWaitBits()` API 函数。否则，设置事件位（表示任务已到达同步点）与检查事件位（判断其他同步任务是否已到达同步点）会成为两个独立操作。要理解这为何会导致问题，可以考虑任务 A、任务 B 和任务 C 尝试使用一个事件组进行同步的场景：

1. 任务 A 和任务 B 已经到达同步点，因此它们的事件位已在事件组中置位。两个任务都处于阻塞状态，等待任务 C 的事件位也被置位。

2. 任务 C 到达同步点，并调用 `xEventGroupSetBits()` 在事件组中设置自己的位。任务 C 的位一经设置，任务 A 和任务 B 就会离开阻塞状态，并清除全部三个事件位。

3. 随后任务 C 调用 `xEventGroupWaitBits()`，等待全部三个事件位被置位。但此时三个事件位都已经被清除，任务 A 和任务 B 也已经离开各自的同步点，因此同步失败。

要成功使用事件组创建同步点，设置事件位和随后检查事件位必须作为一项不可中断的操作执行。FreeRTOS 为此提供了 `xEventGroupSync()` API 函数。

<a id="941-the-xeventgroupsync-api-function"></a>
### 9.4.1 xEventGroupSync() API 函数

`xEventGroupSync()` 使两个或多个任务能够借助事件组彼此同步。该函数让任务在事件组中设置一个或多个事件位，然后等待同一事件组中的一组事件位被置位，并把这两个步骤作为一项不可中断的操作执行。

`xEventGroupSync()` 的 `uxBitsToWaitFor` 参数指定调用任务的解除阻塞条件。如果函数因该条件得到满足而返回，那么在 `xEventGroupSync()` 返回前，`uxBitsToWaitFor` 指定的事件位会被清零。

<a name="list9.12" title="代码清单 9.12 xEventGroupSync() API 函数原型"></a>

```c
EventBits_t xEventGroupSync( EventGroupHandle_t xEventGroup,
                             const EventBits_t uxBitsToSet,
                             const EventBits_t uxBitsToWaitFor,
                             TickType_t xTicksToWait );
```
***代码清单 9.12*** *`xEventGroupSync()` API 函数原型*

**xEventGroupSync() 参数和返回值**

- `xEventGroup`

  要在其中设置并随后检查事件位的事件组句柄。该句柄由创建事件组时调用的 `xEventGroupCreate()` 返回。

- `uxBitsToSet`

  一个位掩码，用于指定要在事件组中置为 1 的一个或多个事件位。事件组的原值与 `uxBitsToSet` 按位或后，得到更新后的事件组值。

  例如，把 `uxBitsToSet` 设为 0x04（二进制 0100），会使事件位 2 被置位（如果尚未置位），而其他事件位保持不变。

- `uxBitsToWaitFor`

  一个位掩码，用于指定要在事件组中检查的一个或多个事件位。

  例如，如果调用任务希望等待事件组中的事件位 0、1 和 2 都被置位，则把 `uxBitsToWaitFor` 设为 0x07（二进制 111）。

- `xTicksToWait`

  任务为了等待解除阻塞条件满足而保持阻塞状态的最长时间。

  如果 `xTicksToWait` 为 0，或者调用 `xEventGroupSync()` 时解除阻塞条件已经满足，`xEventGroupSync()` 会立即返回。

  阻塞时间以 Tick 周期为单位，因此它所代表的绝对时间取决于 Tick 频率。宏 `pdMS_TO_TICKS()` 可把以毫秒表示的时间转换为以 Tick 表示的时间。

  如果 FreeRTOSConfig.h 中的 `INCLUDE_vTaskSuspend` 设为 1，把 `xTicksToWait` 设为 `portMAX_DELAY` 会使任务无限期等待，不会超时。

- 返回值

  如果 `xEventGroupSync()` 因调用任务的解除阻塞条件得到满足而返回，则返回值是条件满足时的事件组值，也就是所有事件位自动清零之前的值。此时，返回值也满足调用任务的解除阻塞条件。

  如果 `xEventGroupSync()` 因 `xTicksToWait` 参数指定的阻塞时间到期而返回，则返回值是阻塞时间到期时的事件组值。此时，返回值不满足调用任务的解除阻塞条件。

```c
static void vSyncingTask( void *pvParameters )
{
    const TickType_t xMaxDelay = pdMS_TO_TICKS( 4000UL );
    const TickType_t xMinDelay = pdMS_TO_TICKS( 200UL );
    TickType_t xDelayTime;
    EventBits_t uxThisTasksSyncBit;
    const EventBits_t uxAllSyncBits = ( mainFIRST_TASK_BIT  |
                                        mainSECOND_TASK_BIT |
                                        mainTHIRD_TASK_BIT );

    /* 创建本任务的三个实例，每个任务在同步时使用不同的事件位。通过任务
       参数向每个任务实例传入要使用的事件位，并把它保存到
       uxThisTasksSyncBit 变量中。 */
    uxThisTasksSyncBit = ( EventBits_t ) pvParameters;

    for( ;; )
    {
        /* 延迟一段伪随机时间，以模拟本任务执行某项操作所花的时间。这样可
           防止三个任务实例同时到达同步点，从而更容易观察示例的行为。 */
        xDelayTime = ( rand() % xMaxDelay ) + xMinDelay;
        vTaskDelay( xDelayTime );

        /* 输出消息，说明本任务已经到达同步点。pcTaskGetTaskName() 是一个
           API 函数，返回创建任务时为其指定的名称。 */
        vPrintTwoStrings( pcTaskGetTaskName( NULL ), "reached sync point" );

        /* 等待所有任务到达各自的同步点。 */
        xEventGroupSync( /* 用于同步的事件组。 */
                         xEventGroup,

                         /* 本任务设置该位，表示自己已经到达同步点。 */
                         uxThisTasksSyncBit,

                         /* 要等待的位，每个参与同步的任务对应一个位。 */
                         uxAllSyncBits,

                         /* 无限期等待三个任务全部到达同步点。 */
                         portMAX_DELAY );

        /* 输出消息，说明本任务已经越过同步点。这里使用无限期延迟，因此只有
           在所有任务都到达各自的同步点后，才会执行下一行。 */
        vPrintTwoStrings( pcTaskGetTaskName( NULL ), "exited sync point" );
    }
```

```c
       直观看出正在执行的是哪个任务。通过任务参数传入任务到达同步点时要使用
       的事件位。 */
    xTaskCreate( vSyncingTask, "Task 1", 1000, mainFIRST_TASK_BIT, 1, NULL );
    xTaskCreate( vSyncingTask, "Task 2", 1000, mainSECOND_TASK_BIT, 1, NULL );
    xTaskCreate( vSyncingTask, "Task 3", 1000, mainTHIRD_TASK_BIT, 1, NULL );

    /* 启动调度器，使创建的任务开始执行。 */
    vTaskStartScheduler();

    /* 与以往一样，程序永远不应执行到下一行。 */
    for( ;; );
    return 0;
}
```
