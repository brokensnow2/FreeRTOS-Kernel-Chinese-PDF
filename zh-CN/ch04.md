## 4.2 任务函数

任务由 C 函数实现，并且必须符合代码清单 4.1 所示的函数原型：接收一个 `void` 指针参数，不返回任何值。

<a name="list4.1" title="代码清单 4.1 任务函数原型"></a>

```c
void vATaskFunction( void * pvParameters );
```

***代码清单 4.1*** *任务函数原型*


每个任务本身就是一个小程序。它有一个入口点，通常会永远在无限循环中运行，并且不会退出。代码清单 4.2 显示了一个典型任务的结构。

实现 FreeRTOS 任务的函数绝不能以任何方式返回：既不能包含 `return` 语句，也不能执行到函数末尾。如果不再需要某个任务，应如代码清单 4.2 所示显式删除它。

一个任务函数可以用来创建任意数量的任务；创建出的每个任务都是独立的执行实例。每个实例都有自己的栈，因此也有一份任务函数内所定义的自动变量（栈变量）副本。


<a name="list4.2" title="代码清单 4.2 典型任务函数的结构"></a>


```c
void vATaskFunction( void * pvParameters )
{
    /*
     * 栈分配的变量可以在函数内部正常声明。
     * 使用此示例函数创建的每个任务实例都将在其栈上拥有自己的
     * lStackVariable 的独立实例。
     */
    long lStackVariable = 0;

    /*
     * 与栈分配的变量相反，使用 `static` 关键字声明的变量由链接器
     * 分配到内存中的特定位置。这意味着所有调用 vATaskFunction 的任务
     * 将共享 lStaticVariable 的同一个实例。
     */
    static long lStaticVariable = 0;

    for( ;; )
    {
        /* 实现任务功能的代码将写在这里。 */
    }

    /*
     * 如果任务实现曾经退出上述循环，则任务必须在到达其实现函数
     * 末尾之前被删除。当 NULL 作为参数传递给 vTaskDelete() API 函数时，
     * 表示要删除的任务是调用（当前）任务。
     */
    vTaskDelete( NULL );
}
```

<a id="43-top-level-task-states"></a>
## 4.3 顶层任务状态

一个应用程序可能包含许多任务。如果运行应用程序的处理器包含单个核，则在任何给定时间只能执行一个任务。这意味着任务可以存在于两种状态之一：*运行中* 和 *未运行*。首先考虑这种简化的模型。本章后面将描述 *未运行* 状态的几个子状态。

当处理器正在执行该任务的代码时，任务处于 *运行中* 状态。当任务处于 *未运行* 状态时，任务暂停，其状态已保存，以便下次调度器决定它应进入 *运行中* 状态时可以恢复执行。当任务恢复执行时，它从离开 *运行中* 状态之前即将执行的指令处开始执行。

任务从 *未运行* 状态转换到 *运行中* 状态称为“切入”或“换入”；反之，从 *运行中* 状态转换到 *未运行* 状态称为“切出”或“换出”。只有 FreeRTOS 调度器能够将任务切入或切出 *运行中* 状态。

<a id="44-task-creation"></a>
## 4.4 任务创建

有六个 API 函数可用于创建任务：
`xTaskCreate()`、
`xTaskCreateStatic()`、
`xTaskCreateRestricted()`、
`xTaskCreateRestrictedStatic()`、
`xTaskCreateAffinitySet()` 和
`xTaskCreateStaticAffinitySet()`

每个任务需要两个 RAM 块：一个用于保存其任务控制块（TCB），另一个用于存储其栈。名称中包含"Static"的 FreeRTOS API 函数使用预先分配的 RAM 块作为参数传入函数。相反，名称中不包含"Static"的 API 函数在运行时从系统堆动态分配所需的 RAM。

某些 FreeRTOS 移植版本支持任务以“受限”或“非特权”模式运行。名称中包含 `Restricted` 的 FreeRTOS API 函数所创建的任务只能访问有限的系统内存；名称中不包含 `Restricted` 的 API 函数所创建的任务则在“特权模式”下运行，可以访问完整的系统内存映射。

支持对称多处理（SMP）的 FreeRTOS 移植版本允许不同任务在同一 CPU 的多个核上同时运行。对于这些移植版本，可以使用名称中包含 `Affinity` 的函数指定任务在哪个核上运行。

FreeRTOS 任务创建 API 函数相当复杂。本文档中的大多数示例使用 `xTaskCreate()`，因为它是这些函数中最简单的。

<a name="list4.3" title="代码清单 4.3 xTaskCreate() API 函数原型"></a>


```c
BaseType_t xTaskCreate( TaskFunction_t pvTaskCode,
                        const char * const pcName,
                        configSTACK_DEPTH_TYPE usStackDepth,
                        void * pvParameters,
                        UBaseType_t uxPriority,
                        TaskHandle_t * pxCreatedTask );
```

***代码清单 4.3*** *xTaskCreate() API 函数原型*

**xTaskCreate() 参数和返回值：**

- `pvTaskCode`

  任务就是永远不会退出的 C 函数，因此通常实现为无限循环。`pvTaskCode` 参数只是一个指向实现任务的函数的指针（实际上就是函数名）。

- `pcName`

  任务的描述性名称。FreeRTOS 不以任何方式使用它，它纯粹作为调试辅助工具包含在内。通过人类可读的名称来识别任务比通过其句柄要简单得多。

  应用程序定义的常量 `configMAX_TASK_NAME_LEN` 定义了任务名称的最大长度，包括 NULL 终止符。提供更长的字符串会导致字符串被截断。

- `usStackDepth`

  指定为任务分配栈的大小。使用 `xTaskCreateStatic()` 而不是 `xTaskCreate()` 来使用预先分配的内存而不是动态分配的内存。

  注意该值指定栈可以容纳的字数，而不是字节数。例如，如果栈是 32 位宽且 `usStackDepth` 为 128，则 `xTaskCreate()` 分配 512 字节的栈空间（128 * 4 字节）。

  `configSTACK_DEPTH_TYPE` 是一个宏，允许应用程序编写者指定用于保存栈大小的数据类型。如果未定义，`configSTACK_DEPTH_TYPE` 默认为 `uint16_t`，因此如果栈深度乘以栈宽度大于 65535（最大可能的 16 位数字），则在 `FreeRTOSConfig.h` 中将 `configSTACK_DEPTH_TYPE` 定义为 `unsigned long` 或 `size_t`。

  [第 13.3 节 栈溢出](ch13.md#133-stack-overflow)，描述了一种选择最佳栈大小的实用方法。

- `pvParameters`

  实现任务的函数接受一个 void 指针（`void *`）参数。`pvParameters` 是通过该参数传递给任务的值。

- `uxPriority`

  定义任务的优先级。0 是最低优先级，`(configMAX_PRIORITIES - 1)` 是最高优先级。[第 4.5 节](#45-task-priorities)介绍了由用户定义的 `configMAX_PRIORITIES` 常量。

  如果指定的 `uxPriority` 大于 `(configMAX_PRIORITIES - 1)`，它将被限制为 `(configMAX_PRIORITIES - 1)`。

- `pxCreatedTask`

  指向存储所创建任务句柄位置的指针。该句柄可在将来的 API 调用中使用，例如更改任务的优先级或删除任务。

  `pxCreatedTask` 是一个可选参数，如果不需要任务句柄，可以设置为 NULL。

- 返回值

  有两个可能的返回值：

  - `pdPASS`

    表示任务创建成功。

  - `pdFAIL`

    表示没有足够的堆内存来创建任务。[第 3 章](ch03.md#3-heap-memory-management)提供了更多关于堆内存管理的信息。

     * 空闲任务或定时器任务（本书后面描述）。第 3 章提供了更多关于

     */
    for( ;; )

    }

<a id="45-task-priorities"></a>
## 4.5 任务优先级

FreeRTOS 调度器始终选择当前能够运行的最高优先级任务进入 *运行中* 状态。优先级相同的任务则轮流进入和退出 *运行中* 状态。

用于创建任务的 API 函数的 `uxPriority` 参数为任务提供初始优先级。`vTaskPrioritySet()` API 函数在任务创建后更改其优先级。

应用程序定义的编译时配置常量 `configMAX_PRIORITIES` 设置可用优先级的数量。数值越小，任务优先级越低，其中优先级 0 为最低优先级；因此，有效优先级范围是 0 到 `(configMAX_PRIORITIES - 1)`。任意数量的任务都可以共享同一优先级。

FreeRTOS 调度器有两种用于选择 *运行中* 状态任务的算法实现，`configMAX_PRIORITIES` 的最大允许值取决于所使用的实现：

<a id="451-generic-scheduler"></a>
### 4.5.1 通用调度器

通用调度器使用 C 语言编写，可用于所有 FreeRTOS 架构移植版本。它不限制 `configMAX_PRIORITIES` 的上限。通常应尽量减小 `configMAX_PRIORITIES`，因为更多的优先级会占用更多 RAM，并延长最坏情况下的执行时间。

<a id="452-architecture-optimized-scheduler"></a>
### 4.5.2 架构优化调度器

架构优化的实现用特定于架构的汇编代码编写，比通用 C 实现性能更高，并且对于所有 `configMAX_PRIORITIES` 值，最坏情况执行时间相同。

架构优化的实现在 32 位架构上将 `configMAX_PRIORITIES` 的最大值限制为 32，在 64 位架构上限制为 64。与通用方法一样，建议将 `configMAX_PRIORITIES` 保持在尽可能低的值，因为更高的值需要更多的 RAM。

在 `FreeRTOSConfig.h` 中将 `configUSE_PORT_optimized_TASK_SELECTION` 设置为 1 可使用架构优化实现，设置为 0 则使用通用实现。并非所有 FreeRTOS 移植版本都提供架构优化实现。对于提供该实现的移植版本，如果未定义此宏，其默认值为 1；否则默认值为 0。

<a id="46-time-measurement-and-the-tick-interrupt"></a>
## 4.6 时间测量和 Tick 中断

[第 4.12 节“调度算法”](#412-scheduling-algorithms)介绍了一项称为“时间片”的可选功能。前面的示例都使用了时间片，输出中也体现了这种行为。示例中的两个任务具有相同优先级，并且始终能够运行。因此，每个任务各执行一个“时间片”：在时间片开始时进入 *运行中* 状态，在时间片结束时退出该状态。图 4.3 中，t1 到 t2 之间的时长就是一个时间片。

调度器在每个时间片结束时运行，以选择下一个要执行的任务[^5]。为此，系统使用一个称为“Tick 中断”的周期性中断。编译时配置常量 `configTICK_RATE_HZ` 设置 Tick 中断频率，也就决定了每个时间片的长度。例如，将 `configTICK_RATE_HZ` 设置为 100 Hz 时，每个时间片持续 10 毫秒。两次 Tick 中断之间的时间称为“Tick 周期”，因此一个时间片等于一个 Tick 周期。

[^5]: 需要注意的是，时间片的结束不是调度器可以选择新运行任务的唯一时机。正如我们将在本书中演示的，调度器还会在当前执行任务进入 *阻塞* 状态后立即选择新任务运行，或者当中断将更高优先级的任务移到 *就绪* 状态时。

`configTICK_RATE_HZ` 的最佳值取决于应用程序，尽管值 100 是典型的。

<a id="47-expanding-the-not-running-state"></a>
## 4.7 扩展 *未运行* 状态

到目前为止创建的任务总有工作要做，无需等待任何事件，因此始终能够进入 *运行中* 状态。这类“连续处理”任务的实用性有限，因为它们只能按最低优先级创建；如果使用其他优先级，它们就会阻止优先级更低的任务运行。

为了使这些任务有用，必须将它们重写为事件驱动。事件驱动任务只有在事件触发后才有工作（处理）要执行，并且在该时间之前不能进入 *运行中* 状态。调度器始终选择可以运行的优先级最高的任务。如果无法选择高优先级任务，因为它正在等待事件，则调度器必须改为选择可以运行的较低优先级任务。因此，编写事件驱动任务意味着可以以不同的优先级创建任务，而最高优先级的任务不会饿死所有较低优先级任务的处理时间。

<a id="471-the-blocked-state"></a>
### 4.7.1 *阻塞* 状态

等待事件的任务被称为处于"阻塞"状态，这是 *未运行* 状态的一个子状态。

任务可以进入 *阻塞* 状态以等待两种不同类型的事件：

1. 时间相关事件：在延迟时间到期或到达某个绝对时刻时发生。例如，任务可以进入 *阻塞* 状态，等待 10 毫秒过去。

1. 同步事件：由另一个任务或中断触发。例如，任务可以进入 *阻塞* 状态，等待数据到达队列。同步事件涵盖多种不同的事件类型。

FreeRTOS 队列、二进制信号量、计数信号量、互斥量、递归互斥量、事件组、流缓冲区、消息缓冲区和直接任务通知都可以创建同步事件。后面的章节涵盖了大多数这些功能。

任务可以在具有超时的情况下阻塞在同步事件上，从而有效地同时阻塞在两种类型的事件上。例如，任务可以选择最多等待 10 毫秒让数据到达队列。如果数据在 10 毫秒内到达，或者 10 毫秒过去而没有数据到达，任务将离开 *阻塞* 状态。

<a id="472-the-suspended-state"></a>
### 4.7.2 *挂起* 状态

*挂起* 也是 *未运行* 的一个子状态。处于挂起状态的任务对调度器不可用。进入挂起状态的唯一方法是通过调用 `vTaskSuspend()` API 函数，退出挂起状态的唯一方法是通过调用 `vTaskResume()` 或 `xTaskResumeFromISR()` API 函数。大多数应用程序不使用挂起状态。

<a id="473-the-ready-state"></a>
### 4.7.3 就绪状态

处于 *未运行* 状态且未 *阻塞* 或 *挂起* 的任务被称为处于 *就绪* 状态。它们可以运行，因此"准备"运行，但当前不在 *运行中* 状态。

### 4.7.5 vTaskDelayUntil() API 函数

`vTaskDelayUntil()` 与 `vTaskDelay()` 类似。前面已经说明，`vTaskDelay()` 的参数指定从任务调用该函数到再次离开 *阻塞* 状态之间经过的 Tick 数。因此，任务保持阻塞的时长由参数决定，而离开 *阻塞* 状态的时刻则相对于调用 `vTaskDelay()` 的时刻计算。

相比之下，`vTaskDelayUntil()` 的参数指定调用任务从 *阻塞* 状态转入 *就绪* 状态时的准确 Tick 计数。当任务需要以固定频率周期执行时，应使用 `vTaskDelayUntil()`，因为任务解除阻塞的时刻是绝对时刻，而不是像 `vTaskDelay()` 那样相对于函数调用时刻计算。

                      TickType_t xTimeIncrement );

**vTaskDelayUntil() 参数**

- `pxPreviousWakeTime`

  该参数名源于这样一种用法：使用 `vTaskDelayUntil()` 实现按固定频率周期执行的任务。此时，`pxPreviousWakeTime` 保存任务上次离开 *阻塞* 状态（被“唤醒”）的时刻，并以此为基准计算任务下次应离开 *阻塞* 状态的时刻。

  `vTaskDelayUntil()` 会自动更新 `pxPreviousWakeTime` 指向的变量。应用程序通常不应修改该变量，但必须在首次使用前将其初始化为当前 Tick 计数。代码清单 4.15 演示了初始化方法。

- `xTimeIncrement`

  该参数名同样源于上述用法，任务的执行频率由 `xTimeIncrement` 的值决定。

  `xTimeIncrement` 以 Tick 为单位。宏 `pdMS_TO_TICKS()` 可将毫秒转换为 Tick 数。

## 4.8 空闲任务和空闲任务钩子

示例 4.4 中创建的任务大部分时间处于阻塞状态。在这种状态下，它们无法运行，因此不能被调度器选中。

必须始终至少有一个任务可以进入 *运行中* 状态[^6]。为了确保这一点，调度器在调用 `vTaskStartScheduler()` 时自动创建一个空闲任务。空闲任务几乎什么都不做，只是在一个循环中运行，因此与第一个示例中的任务一样，它始终能够运行。

[^6]: 即使在使用 FreeRTOS 的特殊低功耗功能时也是如此，在这种情况下，如果应用程序创建的任何任务都无法执行，则运行 FreeRTOS 的微控制器将进入低功耗模式。

空闲任务具有最低优先级（优先级 0），因此不会阻止更高优先级的应用程序任务进入 *运行中* 状态。应用程序也可以创建同为优先级 0、与空闲任务共享该优先级的任务。`FreeRTOSConfig.h` 中的编译时配置常量 `configIDLE_SHOULD_YIELD` 可防止空闲任务占用本可分配给这些应用程序任务的处理器时间。第 4.12 节“调度算法”将进一步介绍 `configIDLE_SHOULD_YIELD`。

空闲任务以最低优先级运行，因此一旦更高优先级的任务进入 *就绪* 状态，它就会立即退出 *运行中* 状态。图 4.9 的 **tn** 时刻展示了这一点：任务 2 一离开 *阻塞* 状态，空闲任务就立即被换出，让任务 2 开始执行。此时称任务 2 抢占（preempt）了空闲任务。抢占自动发生，被抢占的任务对此并不知情。

> *注意：如果任务使用 `vTaskDelete()` API 函数删除自身，则确保空闲任务不被饿死处理时间至关重要。这是因为空闲任务负责清理已删除自身任务所使用的内核资源。*

<a id="481-idle-task-hook-functions"></a>
### 4.8.1 空闲任务钩子函数

可以通过使用空闲钩子（或空闲回调）函数将应用程序特定的功能直接添加到空闲任务中，该函数由空闲任务在空闲任务循环的每次迭代中自动调用。

空闲任务钩子的常见用途包括：

- 执行低优先级、后台或连续处理功能，而无需为此创建应用程序任务而增加 RAM 开销。

- 测量空闲处理能力。（空闲任务只有在所有更高优先级的应用程序任务没有工作要执行时才会运行；因此，测量分配给空闲任务的处理时间量可以清楚地指示空闲处理时间。）

- 将处理器置于低功耗模式，以便在没有应用程序工作要处理时简单、自动地降低功耗（不过，其节能效果不如无 Tick 空闲模式）。

<a id="482-limitations-on-the-implementation-of-idle-task-hook-functions"></a>
### 4.8.2 空闲任务钩子函数实现的限制

空闲任务钩子函数必须遵守以下规则。

- 空闲任务钩子函数绝不能尝试阻塞或挂起自身。

  *注意：以任何方式阻塞空闲任务都可能导致没有任务可进入 *运行中* 状态的情况。*

- 如果应用程序任务使用 `vTaskDelete()` API 函数删除自身，则空闲任务钩子必须在合理的时间内始终返回其调用者。这是因为空闲任务负责清理删除自身任务分配的内核资源。如果空闲任务永久停留在空闲钩子函数中，则此清理无法发生。

***示例 4.8*** *更改任务优先级*

---

调度器始终选择优先级最高的 *就绪* 状态任务进入 *运行中* 状态。示例 4.8 使用 `vTaskPrioritySet()` API 函数改变两个任务的相对优先级，以演示这一行为。

示例 4.8 以两个不同的优先级创建两个任务。两个任务都不调用任何可能导致它们进入阻塞状态的 API 函数，因此两者始终处于 *就绪* 状态或 *运行中* 状态。因此，具有较高相对优先级的任务将始终是被调度器选为 *运行中* 状态的任务。

示例 4.8 的行为如下：

1. 任务 1（代码清单 4.23）以最高优先级创建，因此它保证首先运行。任务 1 打印出几个字符串，然后将任务 2（代码清单 4.24）的优先级提高到高于自身。

1. 任务 2 一旦具有最高相对优先级就开始运行（进入 *运行中* 状态）。一次只能有一个任务处于 *运行中* 状态，因此当任务 2 处于 *运行中* 状态时，任务 1 处于 *就绪* 状态。

1. 任务 2 打印出一条消息，然后将自己的优先级降低到任务 1 以下。

1. 当任务 2 降低其优先级时，任务 1 再次成为最高优先级任务，因此任务 1 重新进入 *运行中* 状态，迫使任务 2 回到 *就绪* 状态。


<a name="list4.23" title="代码清单 4.23 示例 4.8 中任务 1 的实现"></a>

```c
void vTask1( void * pvParameters )
{
    UBaseType_t uxPriority;

    /* 
     * 此任务将始终在任务 2 之前运行，因为它以更高的优先级创建。
     * 任务 1 和任务 2 都不阻塞，因此两者始终处于运行中或就绪状态。
     */

    /*
     * 查询此任务运行的优先级 - 传递 NULL 意味着"返回调用任务的优先级"。
     */
    uxPriority = uxTaskPriorityGet( NULL );

    for( ;; )
    {
        /* 打印此任务的名称。 */
        vPrintLine( "Task 1 is running" );

        /*
         * 将任务 2 的优先级设置到任务 1 的优先级以上将导致任务 2
         * 立即开始运行（因为此时任务 2 将具有两个创建任务中较高的优先级）。
         * 注意在调用 vTaskPrioritySet() 时使用了任务 2 的句柄（xTask2Handle）。
         * 代码清单 4.25 显示了如何获取句柄。
         */
        vPrintLine( "About to raise the Task 2 priority" );
        vTaskPrioritySet( xTask2Handle, ( uxPriority + 1 ) );

        /*
         * 任务 1 仅在其优先级高于任务 2 时才会运行。
         * 因此，对于此任务到达此点，任务 2 必须已经执行并将自己的优先级
         * 降低到此任务的优先级以下。
         */
    }
}
```

     * 任务 1 将始终在此任务之前运行，因为任务 1 以更高的优先级创建。
     * 任务 1 和任务 2 都不阻塞，因此始终处于运行中或就绪状态。
     *
     * 查询此任务运行的优先级 - 传递 NULL 意味着"返回调用任务的优先级"。

## 4.10 删除任务

<a id="4101-the-vtaskdelete-api-function"></a>
### 4.10.1 vTaskDelete() API 函数

`vTaskDelete()` API 函数删除一个任务。`vTaskDelete()` API 函数仅在 FreeRTOSConfig.h 中将 `INCLUDE_vTaskDelete` 设置为 1 时可用。

不建议在运行时持续创建和删除任务，因此如果您发现自己需要此函数，请考虑其他设计选项，例如重用任务。

已删除的任务不再存在，不能再进入 *运行中* 状态。

> *注意：只有内核本身分配给任务的内存在任务删除时自动释放。在任务实现期间分配的任何内存或其他资源，如果不再需要，必须显式释放。*

## 4.11 线程局部存储和可重入性

线程局部存储允许应用程序开发者在每个任务的任务控制块中保存任意数据。它最常用于保存那些原本会由非可重入函数存放在全局变量中的数据。

可重入函数可以由多个线程安全调用，而不会在线程之间产生副作用。在多线程环境中使用非可重入函数而又没有线程局部存储时，必须格外小心，并在临界区内检查这些函数通过带外通道返回的结果。过度使用临界区会降低 RTOS 性能，因此通常更适合使用线程局部存储。

线程局部存储最常见的用途，是为 C 标准库和 POSIX 系统所使用的 ISO C 全局变量 `errno` 提供每线程实例。`errno` 用于保存 `strtof()`、`strtol()` 等常见标准库函数的扩展结果或错误码。

<a id="4111-c-runtime-thread-local-storage-implementations"></a>
### 4.11.1 C 运行时线程局部存储实现

大多数嵌入式 libc 实现提供 API 以确保非可重入函数可以在多线程环境中正常工作。FreeRTOS 包含对两个常用开源库的重入 API 的支持：
[newlib](https://sourceware.org/newlib/) 和
[picolibc](https://github.com/picolibc/picolibc)。
在项目的 `FreeRTOSConfig.h` 文件中定义下列对应宏，即可启用这些预构建的 C 运行时线程局部存储实现。

- 对于 [newlib](https://sourceware.org/newlib/)，定义 `configUSE_NEWLIB_REENTRANT`
- 对于 [picolibc](https://github.com/picolibc/picolibc)，定义 `configUSE_PICOLIBC_TLS`

<a id="4112-custom-c-runtime-thread-local-storage"></a>
### 4.11.2 自定义 C 运行时线程局部存储

应用程序开发者可以在 `FreeRTOSConfig.h` 文件中定义以下宏，实现线程局部存储：

- 将 `configUSE_C_RUNTIME_TLS_SUPPORT` 定义为 1，以启用 C 运行时线程局部存储支持。

- 将 `configTLS_BLOCK_TYPE` 定义为用于保存 C 运行时线程局部存储数据的 C 类型。

- 将 `configINIT_TLS_BLOCK` 定义为初始化 C 运行时线程局部存储块时应执行的 C 代码。

- 将 `configSET_TLS_BLOCK` 定义为换入新任务时应执行的 C 代码。

- 将 `configDEINIT_TLS_BLOCK` 定义为销毁 C 运行时线程局部存储块时应执行的 C 代码。

<a id="4113-application-thread-local-storage"></a>

## 4.12 调度算法

<a id="4121-a-recap-of-task-states-and-events"></a>
### 4.12.1 任务状态和事件回顾

实际正在执行（占用处理器时间）的任务处于 *运行中* 状态。在单核处理器上，任何时刻都只能有一个任务处于 *运行中* 状态。也可以让多个 FreeRTOS 实例分别运行在多个核上（非对称多处理，AMP），或由 FreeRTOS 在多个核之间调度任务（对称多处理，SMP）。本书此处不讨论这些场景。

实际未运行但也不处于阻塞状态或 *挂起* 状态的任务处于 *就绪* 状态。处于就绪状态的任务可由调度器选择作为进入 *运行中* 状态的任务。调度器将始终选择优先级最高的就绪状态任务进入 *运行中* 状态。

任务可以在 *阻塞* 状态中等待事件，并在事件发生时自动返回 *就绪* 状态。定时事件在指定时刻发生，例如阻塞时间到期时，通常用于实现周期性操作或超时。同步事件则在任务或中断服务程序通过任务通知、队列、事件组、消息缓冲区、流缓冲区或某种信号量发送信息时发生，通常用于通知异步活动，例如外设收到数据。


<a id="4122-selecting-the-scheduling-algorithm"></a>
### 4.12.2 选择调度算法

调度算法是决定将哪个 *就绪* 状态任务转换到 *运行中* 状态的软件例程。

到目前为止，所有示例都使用了相同的调度算法，但可以使用 `configUSE_PREEMPTION` 和 `configUSE_TIME_SLICING` 配置常量更改该算法。这两个常量都在 FreeRTOSConfig.h 中定义。

第三个配置常量 `configUSE_TICKLESS_IDLE` 也会影响调度算法，因为启用它后可能会长时间完全关闭 Tick 中断。`configUSE_TICKLESS_IDLE` 是一个高级选项，专门用于必须尽量降低功耗的应用程序。本节假设 `configUSE_TICKLESS_IDLE` 设置为 0，这也是未定义该常量时的默认值。

在所有可能的单核配置中，FreeRTOS 调度器依次选择共享同一优先级的任务。这种"轮流"策略通常称为"轮转调度"。轮转调度算法不保证处理时间在相同优先级的任务之间平均分配，只保证相同优先级的 *就绪* 状态任务轮流进入 *运行中* 状态。

<a id="4123-prioritized-preemptive-scheduling-with-time-slicing"></a>
### 4.12.3 带时间片的优先级抢占式调度

表 5 中显示的配置将 FreeRTOS 调度器设置为使用称为"带时间片的固定优先级抢占式调度"的调度算法，这是大多数小型 RTOS 应用程序使用的调度算法，也是本书迄今为止所有示例使用的算法。下表提供了算法名称中使用的术语说明。

**用于描述调度策略的术语说明：**

- 固定优先级

  描述为"固定优先级"的调度算法不会更改分配给被调度任务的优先级，但也不会阻止任务自身更改自己的优先级或其他任务的优先级。

- 抢占式

  抢占式调度算法会在优先级更高的任务进入 *就绪* 状态时，立即“抢占”当前处于 *运行中* 状态的任务。被抢占意味着任务在没有主动让出或阻塞的情况下，被移出 *运行中* 状态并转入 *就绪* 状态，以便另一个任务进入 *运行中* 状态。抢占可以在任何时刻发生，并不局限于 RTOS Tick 中断。

- 时间片

  时间片用于在相同优先级的任务之间共享处理器时间，即使这些任务没有显式让出处理器或进入 *阻塞* 状态。采用 *时间片* 的调度算法会在每个时间片结束时检查是否还有与当前任务优先级相同的 *就绪* 状态任务；如果有，就选择另一个任务进入 *运行中* 状态。一个时间片等于两次 RTOS Tick 中断之间的时间。

  空闲任务和任务 2 轮流进入 *运行中* 状态，这可能导致两个任务在同一时间片的部分时间内处于 *运行中* 状态，如 t5 和 t8 之间发生的那样。

- 任务 1

  任务 1 的优先级高于空闲优先级。任务 1 是一个事件驱动任务，大部分时间处于 *阻塞* 状态等待其感兴趣的事件，每次事件发生时从 *阻塞* 状态转换到 *就绪* 状态。

  感兴趣的事件在时间 t6 发生。在 t6，任务 1 成为可以运行的优先级最高的任务，因此任务 1 在一个时间片中间抢占空闲任务。事件的处理在时间 t7 完成，此时任务 1 重新进入阻塞状态。

图 4.19 显示空闲任务与应用程序创建的任务共享处理器时间。如果应用程序创建的空闲优先级任务有工作要做，而空闲任务本身没有，那么为后者分配如此多的处理器时间可能并不合适。可以使用编译时配置常量 `configIDLE_SHOULD_YIELD` 更改空闲任务的调度方式：

- 如果 `configIDLE_SHOULD_YIELD` 设置为 0，则空闲任务在其整个时间片内保持在 *运行中* 状态，除非被更高优先级的任务抢占。

- 如果 `configIDLE_SHOULD_YIELD` 设置为 1，则如果存在其他处于 *就绪* 状态的空闲优先级任务，空闲任务在其循环的每次迭代时让出（自愿放弃其分配时间片的剩余部分）。

图 4.19 所示的执行模式是当 `configIDLE_SHOULD_YIELD` 设置为 0 时观察到的。图 4.20 所示的执行模式是在相同场景下当 `configIDLE_SHOULD_YIELD` 设置为 1 时观察到的。

<a id="4124-prioritized-preemptive-scheduling-without-time-slicing"></a>
### 4.12.4 不带时间片的优先级抢占式调度

不带时间片的优先级抢占式调度保持与上一节描述的相同的任务选择和抢占算法，但不使用时间片在相同优先级的任务之间共享处理时间。

表 5 显示了将 FreeRTOS 调度器配置为使用不带时间片的优先级抢占式调度的 FreeRTOSConfig.h 设置。

如图 4.19 所示，如果使用时间片，并且有多个处于就绪状态的最高优先级任务可以运行，则调度器在每个 RTOS tick 中断（tick 中断标记一个时间片的结束）期间选择一个新任务进入 *运行中* 状态。如果不使用时间片，则调度器仅在以下情况下选择新任务进入 *运行中* 状态：

- 更高优先级的任务进入 *就绪* 状态。

- *运行中* 状态的任务进入 *阻塞* 或 *挂起* 状态。

不使用时间片时的任务上下文切换次数少于使用时间片时。因此，关闭时间片会导致调度器处理开销的减少。但是，关闭时间片也可能导致相同优先级的任务获得截然不同的处理时间量，图 4.21 演示了这种场景。因此，不使用时间片运行调度器被认为是一种高级技术，只应由有经验的用户使用。

参考图 4.21，假设 `configIDLE_SHOULD_YIELD` 设置为 0：

- Tick 中断

  Tick 中断发生在时间 t1、t2、t3、t4、t5、t8、t11、t12 和 t13。

- 任务 1

  任务 1 是一个高优先级事件驱动任务，大部分时间处于 *阻塞* 状态等待其感兴趣的事件。每次事件发生时，任务 1 从 *阻塞* 状态转换到 *就绪* 状态（随后，作为优先级最高的 *就绪* 状态任务，进入 *运行中* 状态）。图 4.21 显示任务 1 在 t6 和 t7 之间处理一个事件，然后在 t9 和 t10 之间再次处理一个事件。

- 空闲任务和任务 2

  空闲任务和任务 2 都是连续处理任务，并且都具有优先级 0（空闲优先级）。连续处理任务不会进入 *阻塞* 状态。

  不使用时间片，因此处于 *运行中* 状态的空闲优先级任务将保持在 *运行中* 状态，直到被更高优先级的任务 1 抢占。

  任务 2 从时间 t7 开始运行，即任务 1 重新进入 *阻塞* 状态等待另一个事件时。任务 2 保持在 *运行中* 状态，直到同样在时间 t9 被任务 1 抢占，这距离其进入 *运行中* 状态不到一个 tick 周期。

  在时间 t10，空闲任务重新进入 *运行中* 状态，尽管它此前获得的处理器时间已经超过任务 2 的四倍。

### 4.12.5 协作式调度

本书侧重于抢占式调度，但 FreeRTOS 也可以使用协作式调度。表 5 显示了将 FreeRTOS 调度器配置为使用协作式调度的 FreeRTOSConfig.h 设置。

使用协作式调度器时（并假定应用程序提供的中断服务程序不会显式请求上下文切换），只有当 *运行中* 状态的任务进入 *阻塞* 状态，或调用 `taskYIELD()` 主动让出处理器（手动请求重新调度）时，才会发生上下文切换。任务不会被抢占，因此也不能使用时间片。

图 4.22 演示了协作式调度器的行为。图 4.22 中的水平虚线显示任务何时处于就绪状态。

***

参考图 4.22：

- 任务 1

  任务 1 具有最高优先级。它开始时处于 *阻塞* 状态，等待一个信号量。

  在时间 t3，一个中断释放了信号量，使任务 1 离开 *阻塞* 状态并进入 *就绪* 状态（第 6 章将介绍如何从中断中释放信号量）。

  在时间 t3，任务 1 是最高优先级的 *就绪* 状态任务，如果使用抢占式调度器，任务 1 将成为 *运行中* 状态任务。但是，由于使用的是协作式调度器，任务 1 保持在 *就绪* 状态，直到时间 t4，即 *运行中* 状态任务调用 `taskYIELD()` 时。

- 任务 2

  任务 2 的优先级介于任务 1 和任务 3 之间。它开始时处于 *阻塞* 状态，等待任务 3 在时间 t2 发送给它的消息。

  在时间 t2，任务 2 是最高优先级的 *就绪* 状态任务，如果使用抢占式调度器，任务 2 将成为 *运行中* 状态任务。但是，由于使用的是协作式调度器，任务 2 保持在 *就绪* 状态，直到 *运行中* 状态的任务进入 *阻塞* 状态或调用 `taskYIELD()`。

  *运行中* 状态的任务在时间 t4 调用 `taskYIELD()`，但此时任务 1 是最高优先级的 *就绪* 状态任务，因此直到任务 1 在时间 t5 重新进入 *阻塞* 状态之前，任务 2 实际上不会成为 *运行中* 状态的任务。

  在时间 t6，任务 2 重新进入 *阻塞* 状态等待下一条消息，此时任务 3 再次成为最高优先级的 *就绪* 状态任务。

在多任务应用程序中，应用程序编写者必须注意一个资源不会被多个任务同时访问，因为同时访问可能破坏资源。例如，考虑以下场景，其中被访问的资源是 UART（串行端口）。两个任务向 UART 写入字符串；任务 1 写入 "abcdefghijklmnop"，任务 2 写入 "123456789"：

1. 任务 1 处于 *运行中* 状态并开始写入其字符串。它向 UART 写入 "abcdefg"，但在写入任何更多字符之前离开 *运行中* 状态。

1. 任务 2 进入 *运行中* 状态并向 UART 写入 "123456789"，然后离开 *运行中* 状态。

1. 任务 1 重新进入 *运行中* 状态并向 UART 写入其字符串的其余字符。

在该场景中，实际写入 UART 的是 "abcdefg123456789hijklmnop"。任务 1 写入的字符串没有按预期以不间断的顺序写入 UART，而是被破坏了，因为任务 2 写入 UART 的字符串出现在其中。

使用协作式调度器通常比使用抢占式调度器更容易避免由同时访问引起的问题[^7]：

[^7]: 在任务之间安全共享资源的方法将在本书后面介绍。FreeRTOS 本身提供的资源，如队列和信号量，在任务之间始终是安全的。

- 当您使用抢占式调度器时，*运行中* 状态的任务可以在任何时候被抢占，包括当它与另一个任务共享的资源处于不一致状态时。正如 UART 示例刚刚演示的，将资源留在不一致状态可能导致数据损坏。

- 当您使用协作式调度器时，您可以控制何时切换到另一个任务。因此，您可以确保在资源处于不一致状态时不会发生切换到另一个任务。

- 在上述 UART 示例中，您可以确保任务 1 在将其整个字符串写入 UART 之前不会离开 *运行中* 状态，从而消除了字符串被另一个任务的活动破坏的可能性。

如图 4.22 所示，使用协作式调度器使系统的响应性低于使用抢占式调度器：

- 使用抢占式调度器时，一旦某个任务成为优先级最高的 *就绪* 状态任务，调度器就会立即开始运行它。实时系统通常必须在规定时间内响应高优先级事件，因此往往需要这种行为。

- 使用协作式调度器时，直到 *运行中* 状态的任务进入 *阻塞* 状态或调用 `taskYIELD()` 后，才会执行切换到已成为最高优先级 *就绪* 状态的任务。
