# 2 FreeRTOS 内核发行版

<a id="21-introduction"></a>

## 2.1 简介

为了帮助读者熟悉 FreeRTOS 内核的文件和目录，本章将：

- 概览 FreeRTOS 的目录结构。
- 说明任一 FreeRTOS 项目所需的源文件。
- 介绍演示应用。
- 说明如何创建新的 FreeRTOS 项目。

这里的说明仅适用于官方 FreeRTOS 发行版。本书配套示例采用的组织方式略有不同。

<a id="22-understanding-the-freertos-distribution"></a>

## 2.2 了解 FreeRTOS 发行版

<a id="221-definition-freertos-port"></a>

### 2.2.1 定义：FreeRTOS 移植版本

FreeRTOS 可以使用大约 20 种不同的编译器构建，并可运行在 40 多种不同的处理器架构上。每一种受支持的编译器与处理器组合，都称为一个 FreeRTOS 移植版本（FreeRTOS port）。

<a id="222-building-freertos"></a>

### 2.2.2 构建 FreeRTOS

FreeRTOS 是一个库，它为原本只能单线程运行的裸机应用提供多任务处理能力。

FreeRTOS 以一组 C 源文件的形式提供。有些源文件对所有移植版本通用，另一些则只适用于特定移植版本。将这些源文件作为项目的一部分进行构建后，应用便可使用 FreeRTOS API。每个官方 FreeRTOS 移植版本都提供一个可供参考的演示应用。演示应用已经预先配置，会构建正确的源文件并包含正确的头文件。

每个演示应用在创建时都可以“开箱即用”地完成构建，不会产生编译器错误或警告。如果后续构建工具发生变化，导致情况不再如此，请通过 FreeRTOS 支持论坛（<https://forums.FreeRTOS.org>）告知我们。第 2.3 节将介绍这些演示应用。

<a id="223-freertosconfigh"></a>

### 2.2.3 FreeRTOSConfig.h

内核由名为 `FreeRTOSConfig.h` 的头文件中定义的常量进行配置。不要在源文件中直接包含 `FreeRTOSConfig.h`！应当包含 `FreeRTOS.h`，后者会在适当的时候包含 `FreeRTOSConfig.h`。

`FreeRTOSConfig.h` 用于针对具体应用裁剪 FreeRTOS 内核。例如，`FreeRTOSConfig.h` 中的 `configUSE_PREEMPTION` 常量用于指定 FreeRTOS 采用协作式调度还是抢占式调度[^1]。

[^1]: 当前版本的调度算法见第 4.12 节；英文原文此处写作第 4.13 节。

由于 `FreeRTOSConfig.h` 用于针对具体应用定制 FreeRTOS，因此它应位于应用自身的目录中，而不应位于包含 FreeRTOS 源代码的目录中。

FreeRTOS 主发行版为每个 FreeRTOS 移植版本都提供一个演示应用，并且每个演示应用都有自己的 `FreeRTOSConfig.h` 文件。建议以所用移植版本对应演示应用中的 `FreeRTOSConfig.h` 为起点，在此基础上进行修改，而不是从头创建该文件。

FreeRTOS 参考手册和 <https://www.freertos.org/a00110.html> 介绍了 `FreeRTOSConfig.h` 中可以使用的常量。无需在 `FreeRTOSConfig.h` 中包含所有常量，许多未写出的常量会采用默认值。

### 2.2.4 官方发行版

包括内核在内的各个 FreeRTOS 库，既可以从各自的 GitHub 仓库获取，也可以通过 zip 归档文件获取。在生产代码中使用 FreeRTOS 时，能够单独获取某个库会很方便。不过，对于刚开始使用 FreeRTOS 的读者，最好下载同时包含各个库和示例项目的 FreeRTOS 主发行版。

主发行版包含所有 FreeRTOS 库的源代码、所有 FreeRTOS 内核移植版本，以及所有 FreeRTOS 演示应用的项目文件。不要被文件数量吓到！实际应用只需要其中很小的一部分。

可以通过 <https://github.com/FreeRTOS/FreeRTOS/releases/latest> 下载包含最新发行版的 zip 文件。也可以使用下面任一 Git 命令从 GitHub 克隆主发行版，并同时克隆从各自 Git 仓库以子模块形式引入的各个库：

### 2.2.5 所有移植版本通用的 FreeRTOS 源文件

`tasks.c` 和 `list.c` 实现 FreeRTOS 内核的核心功能，始终是必需的。它们直接位于 `FreeRTOS/Source` 目录中，如图 2.2 所示。同一目录还包含以下可选源文件：

- **queue.c**

  `queue.c` 提供队列和信号量服务，本书后续章节将对此进行介绍。几乎所有项目都需要 `queue.c`。

- **timers.c**

  `timers.c` 提供软件定时器功能，本书后续章节将对此进行介绍。只有应用使用软件定时器时，才需要构建该文件。

- **event\_groups.c**

  `event_groups.c` 提供事件组功能，本书后续章节将对此进行介绍。只有应用使用事件组时，才需要构建该文件。

- **stream\_buffer.c**

  `stream_buffer.c` 同时提供流缓冲区和消息缓冲区功能，本书后续章节将对此进行介绍。只有应用使用流缓冲区或消息缓冲区时，才需要构建该文件。

- **croutine.c**

  `croutine.c` 实现 FreeRTOS 协程功能。只有应用使用协程时，才需要构建该文件。协程面向非常小的微控制器设计，如今已很少使用。因此，协程不再维护，也不建议在新设计中使用。本书不介绍协程。

### 2.2.6 特定于移植版本的 FreeRTOS 源文件

`FreeRTOS/Source/portable` 目录包含特定于 FreeRTOS 移植版本的源文件。`portable` 目录采用层级结构组织，第一层按编译器划分，第二层按处理器架构划分。图 2.3 展示了这一层级结构。

如果要在架构为“*architecture*”的处理器上使用“*compiler*”编译器运行 FreeRTOS，除了核心 FreeRTOS 源文件外，还必须构建 `FreeRTOS/Source/portable/[compiler]/[architecture]` 目录中的文件。

如第 3 章“堆内存管理”所述，FreeRTOS 也将堆内存分配视为可移植层的一部分。如果 `configSUPPORT_DYNAMIC_ALLOCATION` 设置为 0，则不要在项目中包含堆内存分配方案。

FreeRTOS 在 `FreeRTOS/Source/portable/MemMang` 目录中提供了示例堆分配方案。如果 FreeRTOS 配置为使用动态内存分配，则必须在项目中包含该目录中的一个堆实现源文件，或者提供自己的实现。

> **！不要在同一个项目中包含多个示例堆分配实现。**

<a id="227-include-paths"></a>

### 2.2.7 头文件搜索路径

FreeRTOS 要求将三个目录加入编译器的头文件搜索路径：

1. FreeRTOS 内核核心头文件所在的路径，即 `FreeRTOS/Source/include`。

2. 当前所用 FreeRTOS 移植版本的专用源文件所在路径，即 `FreeRTOS/Source/portable/[compiler]/[architecture]`。

3. 正确的 `FreeRTOSConfig.h` 头文件所在路径。

<a id="228-header-files"></a>

### 2.2.8 头文件

使用 FreeRTOS API 的源文件必须先包含 `FreeRTOS.h`，再包含声明所用 API 函数原型的头文件，即 `task.h`、`queue.h`、`semphr.h`、`timers.h`、`event_groups.h`、`stream_buffer.h`、`message_buffer.h` 或 `croutine.h`。不要显式包含其他 FreeRTOS 头文件；`FreeRTOS.h` 会自动包含 `FreeRTOSConfig.h`。

## 2.3 演示应用

每个 FreeRTOS 移植版本都至少带有一个演示应用。在创建时，这些演示应用都可以“开箱即用”地完成构建，不会产生编译器错误或警告。如果后续构建工具发生变化，导致情况不再如此，请通过 FreeRTOS 支持论坛（<https://forums.FreeRTOS.org>）告知我们。

> **跨平台支持**：FreeRTOS 在 Windows、Linux 和 macOS 系统上进行开发和测试，使用的工具链既有嵌入式工具链，也有传统工具链。不过，版本差异或遗漏的测试偶尔也会导致构建错误。如果遇到此类错误，请通过 FreeRTOS 支持论坛（<https://forums.FreeRTOS.org>）提醒我们。

演示应用有以下几个用途：

- 提供一个能够正常工作且预先配置好的项目示例，其中包含正确的文件，并设置了正确的编译器选项。
- 让用户只需极少的设置和预备知识，即可进行“开箱即用”的实验。
- 演示如何使用 FreeRTOS API。
- 作为创建实际应用的基础。
- 对内核实现进行压力测试。

每个演示项目都位于 `FreeRTOS/Demo` 目录下的独立子目录中。子目录的名称表明该演示项目对应的移植版本。

FreeRTOS.org 网站为每个演示应用都提供了一个页面，其中包含以下信息：

- 如何在 FreeRTOS 目录结构中找到该演示的项目文件。
- 项目配置使用的硬件或仿真器。
- 如何配置硬件以运行演示。
- 如何构建演示。
- 演示的预期行为。

所有演示项目都会创建“公共演示任务”（common demo tasks）的一个子集，这些任务的实现在 `FreeRTOS/Demo/Common/Minimal` 目录中。公共演示任务用于展示 FreeRTOS API 的用法并测试 FreeRTOS 内核移植版本，它们不实现任何特定的实用功能。

许多演示项目还可以配置为创建一个简单的“闪烁灯”（blinky）风格入门项目。这类项目通常会创建两个 RTOS 任务和一个队列。

每个演示项目都包含一个名为 `main.c` 的文件，其中包含 `main()` 函数。该函数在启动 FreeRTOS 内核之前创建演示应用的任务。有关某个具体演示的信息，请参阅相应 `main.c` 文件中的注释。

### 2.4.1 修改随附的演示项目

每个 FreeRTOS 移植版本都至少带有一个预先配置好的演示应用。建议通过修改其中一个现有项目来创建新项目，以确保新项目包含正确的文件、安装了正确的中断处理程序，并设置了正确的编译器选项。

要从现有演示项目创建新的应用，请执行以下步骤：

1. 打开随附的演示项目，确认它能够按预期构建和运行。

2. 删除实现演示任务的源文件，也就是位于 `Demo/Common` 目录中的文件。

3. 删除 `main()` 中除 `prvSetupHardware()` 和 `vTaskStartScheduler()` 之外的所有函数调用，如代码清单 2.1 所示。

4. 确认项目仍能正常构建。

完成这些步骤后，将得到一个包含正确 FreeRTOS 源文件、但尚未定义任何功能的项目。

### 2.4.2 从零创建新项目

如前所述，建议从现有演示项目创建新项目。如果不希望采用这种方式，则可以按照以下步骤从零创建新项目：

1. 使用所选工具链创建一个尚未包含任何 FreeRTOS 源文件的新项目。

1. 确认新项目能够构建、下载到目标硬件并正常运行。

1. 只有在确认已经拥有一个可以正常工作的项目后，才将表 1 所列的 FreeRTOS 源文件添加到项目中。

1. 将所用移植版本对应演示项目中的 `FreeRTOSConfig.h` 头文件复制到新项目目录。

1. 将以下目录加入项目搜索头文件时使用的路径：

   - `FreeRTOS/Source/include`

   - 包含 `FreeRTOSConfig.h` 头文件的目录

1. 从相应的演示项目复制编译器设置。

1. 安装可能需要的 FreeRTOS 中断处理程序。可以参考所用移植版本的说明网页以及该移植版本随附的演示项目。

## 2.5 数据类型和编码风格指南

<a id="251-data-types"></a>

### 2.5.1 数据类型

FreeRTOS 的每个移植版本都有一个独立的 `portmacro.h` 头文件，其中定义了两个特定于移植版本的数据类型：`TickType_t` 和 `BaseType_t`。下面分别介绍这些宏或 typedef 及其实际类型：

- `TickType_t`

  FreeRTOS 会配置一个称为时钟节拍中断（tick interrupt）的周期性中断。

  FreeRTOS 应用启动后累计发生的时钟节拍中断次数称为*时钟节拍计数*（tick count）。时钟节拍计数用于度量时间。

  两次时钟节拍中断之间的时间称为*时钟节拍周期*（tick period）。时间以时钟节拍周期的倍数表示。

  `TickType_t` 是用于保存时钟节拍计数值和指定时间的数据类型。

  根据 `FreeRTOSConfig.h` 中 `configTICK_TYPE_WIDTH_IN_BITS` 的设置，`TickType_t` 可以是无符号 16 位、无符号 32 位或无符号 64 位类型。`configTICK_TYPE_WIDTH_IN_BITS` 的设置取决于处理器架构，FreeRTOS 移植版本也会检查该设置是否有效。

  在 8 位和 16 位架构上使用 16 位类型可以显著提高效率，但会严重限制 FreeRTOS API 调用所能指定的最大阻塞时间。在 32 位或 64 位架构上，没有理由使用 16 位的 `TickType_t`。

  过去使用的 `configUSE_16_BIT_TICKS` 已由 `configTICK_TYPE_WIDTH_IN_BITS` 取代，以支持超过 32 位的时钟节拍计数。新设计应使用 `configTICK_TYPE_WIDTH_IN_BITS`，而不是 `configUSE_16_BIT_TICKS`。

   <a name="tbl2" title="表 2 TickType_t 数据类型与 configTICK_TYPE_WIDTH_IN_BITS 配置"></a>

   * * *
   | configTICK\_TYPE\_WIDTH\_IN\_BITS | 8 位架构 | 16 位架构 | 32 位架构 | 64 位架构 |
   | --- | --- | --- | --- | --- |
   | TICK\_TYPE\_WIDTH\_16_BITS | uint16\_t	| uint16\_t	| uint16\_t	| N/A |
   | TICK\_TYPE\_WIDTH\_32_BITS | uint32\_t	| uint32\_t	| uint32\_t	| N/A |
   | TICK\_TYPE\_WIDTH\_64_BITS | N/A | N/A | uint64\_t | uint64\_t |

   ***表 2*** *`TickType_t` 数据类型与 `configTICK_TYPE_WIDTH_IN_BITS` 配置*
   * * *

- `BaseType_t`

  `BaseType_t` 始终定义为对当前架构而言效率最高的数据类型。通常，它在 64 位架构上是 64 位类型，在 32 位架构上是 32 位类型，在 16 位架构上是 16 位类型，在 8 位架构上是 8 位类型。

  `BaseType_t` 通常用于取值范围非常有限的返回类型，以及 `pdTRUE`/`pdFALSE` 这类布尔值。

### 2.5.2 变量命名

变量名称以其类型作为前缀：`c` 表示 `char`，`s` 表示 `int16_t`（short），`l` 表示 `int32_t`（long），`x` 表示 `BaseType_t` 以及其他非标准类型，例如结构体、任务句柄和队列句柄等。

如果变量为无符号类型，其名称还会带有 `u` 前缀；如果变量是指针，还会带有 `p` 前缀。例如，`uint8_t` 类型变量使用 `uc` 前缀，指向 `char` 的指针变量（`char *`）使用 `pc` 前缀。

<a id="253-function-names"></a>

### 2.5.3 函数命名

函数名称的前缀同时表示返回值类型和函数定义所在的文件。例如：

- v**Task**PrioritySet() 返回 *v*oid，定义在 **tasks**.c 中。
- x**Queue**Receive() 返回 `BaseType_t` 类型的变量，定义在 **queue**.c 中。
- pv**Timer**GetTimerID() 返回指向 *v*oid 的指针，定义在 **timers**.c 中。

文件作用域内的私有函数使用 `prv` 前缀。

<a id="254-formatting"></a>

### 2.5.4 格式

某些演示应用使用制表符，并始终将一个制表符设置为四个空格。内核已不再使用制表符。

### 2.5.6 大量类型转换的原因

FreeRTOS 源代码需要使用许多不同的编译器进行编译，而这些编译器在生成警告的方式和时机上存在差异。尤其是，不同编译器对类型转换的使用方式有不同要求。因此，FreeRTOS 源代码中的类型转换比通常情况下需要的更多。
