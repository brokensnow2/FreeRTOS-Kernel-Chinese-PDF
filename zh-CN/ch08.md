# 8 资源管理

<a id="81-chapter-introduction-and-scope"></a>
## 8.1 本章简介与范围

在多任务系统中，如果一个任务开始访问某项资源，却在访问完成前被切换出运行状态，就可能发生错误。如果资源此时处于不一致状态，其他任务或中断再访问同一资源，便可能导致数据损坏或类似问题。

以下是一些示例：

* 访问外设

  假设两个任务都要向液晶显示器（LCD）写入数据：

  1. 任务 A 开始执行，并向 LCD 写入字符串 `Hello world`。

  2. 任务 A 只输出了开头的 `Hello w`，随后被任务 B 抢占。

  3. 任务 B 把 `Abort, Retry, Fail?` 写入 LCD，然后进入阻塞状态。

  4. 任务 A 从被抢占的位置继续执行，输出剩余的 `orld`。

  LCD 最终显示的是已经混杂的字符串 `Hello wAbort, Retry, Fail?orld`。

* 读-修改-写操作

  代码清单 8.1 给出一行 C 代码，以及编译器通常生成的汇编代码。可以看到，程序先把 `PORTA` 的值从内存读入寄存器，在寄存器中修改，再写回内存。这就是读-修改-写操作。

   <a name="list8.1" title="代码清单 8.1 读-修改-写操作示例"></a>

   ```c
   /* 待编译的 C 代码。 */
   PORTA |= 0x01;

   /* 编译 C 代码后生成的汇编代码。 */
   LOAD  R1,[#PORTA] ; Read a value from PORTA into R1
   MOVE  R2,#0x01    ; Move the absolute constant 1 into R2
   OR    R1,R2       ; Bitwise OR R1 (PORTA) with R2 (constant 1)
   STORE R1,[#PORTA] ; Store the new value back to PORTA
   ```
   ***代码清单 8.1*** *读-修改-写操作示例*

   这是一个“非原子”操作，因为它需要多条指令才能完成，并且可能在中途被打断。假设两个任务都要更新名为 `PORTA` 的内存映射寄存器：

   1. 任务 A 把 `PORTA` 的值载入寄存器，完成操作的“读”阶段。

   2. 任务 A 尚未完成“修改”和“写”阶段，就被任务 B 抢占。

   3. 任务 B 更新 `PORTA` 的值，然后进入阻塞状态。

   4. 任务 A 从被抢占的位置继续执行。它修改寄存器中保存的旧 `PORTA` 副本，再把结果写回 `PORTA`。

   在这种情况下，任务 A 修改并写回的是过时的 `PORTA` 值。任务 B 的修改发生在任务 A 读取 `PORTA` 之后、写回之前，因此任务 A 最后的写入覆盖了任务 B 的修改，实际破坏了 `PORTA` 寄存器值。

   本例使用外设寄存器，但对普通变量执行读-修改-写操作时，原理完全相同。

- 对变量的非原子访问

  更新结构体的多个成员，或者更新大于处理器自然字长的变量，例如在 16 位机器上更新 32 位变量，都是非原子访问。如果访问过程被打断，可能造成数据丢失或损坏。

- 函数可重入性

  如果一个函数可以由多个任务安全调用，或者可以同时由任务和中断安全调用，就称它是“可重入的”。可重入函数也称为“线程安全”函数，因为多个执行线程调用它时，不会破坏数据或逻辑状态。

  每个任务都有自己的栈和一组处理器寄存器值。如果函数只访问当前调用者栈上或寄存器中的数据，它就是可重入且线程安全的。代码清单 8.2 展示可重入函数，代码清单 8.3 展示不可重入函数。

  如果应用程序使用 newlib C 库，必须在 `FreeRTOSConfig.h` 中把 `configUSE_NEWLIB_REENTRANT` 设为 1，确保正确分配 newlib 所需的线程局部存储。

  如果应用程序使用 picolibc C 库，必须在 `FreeRTOSConfig.h` 中把 `configUSE_PICOLIBC_TLS` 设为 1，确保正确分配 picolibc 所需的线程局部存储。

  如果应用程序使用其他 C 库，并且需要线程局部存储（TLS），则必须在 `FreeRTOSConfig.h` 中把 `configUSE_C_RUNTIME_TLS_SUPPORT` 设为 1，并实现以下宏：
  - `configTLS_BLOCK_TYPE`：定义每个任务 TLS 块的类型。
  - `configINIT_TLS_BLOCK`：初始化每个任务的 TLS 块。
  - `configSET_TLS_BLOCK`：更新当前 TLS 块。上下文切换时会调用它，以确保使用正确的 TLS 块。
  - `configDEINIT_TLS_BLOCK`：释放 TLS 块。

  <a name="list8.2" title="代码清单 8.2 可重入函数示例"></a>

  ```c
  /* 参数通过栈或处理器寄存器传入函数。两种方式都是安全的，因为调用该函数的
     每个任务或中断都有自己的栈和寄存器值，所以也都有自己的 lVar1 副本。 */
  long lAddOneHundred( long lVar1 )
  {
      /* 根据编译器和优化级别，这个函数作用域变量同样会分配到栈或寄存器中。
         调用该函数的每个任务或中断都有自己的 lVar2 副本。 */
      long lVar2;

      lVar2 = lVar1 + 100;
      return lVar2;
  }
  ```

<a id="811-mutual-exclusion"></a>
### 8.1.1 互斥

为了始终保持数据一致性，任务之间共享的资源，以及任务与中断共享的资源，都必须采用“互斥”技术管理访问。目标是确保某个任务一旦开始访问不可重入、非线程安全的共享资源，就能独占该资源，直到资源恢复一致状态。

FreeRTOS 提供了多种实现互斥的机制。不过，只要条件允许，最好的方法仍是在设计上避免共享资源，让每项资源只由一个任务访问，尽管这在实际系统中并不总能做到。

## 8.2 临界区与挂起调度器

<a id="821-basic-critical-sections"></a>
### 8.2.1 基本临界区

基本临界区是由宏 `taskENTER_CRITICAL()` 和 `taskEXIT_CRITICAL()` 包围的一段代码。临界区也称为临界段。

`taskENTER_CRITICAL()` 和 `taskEXIT_CRITICAL()` 都不接收参数，也不返回值[^23]。代码清单 8.4 展示了它们的用法。

[^23]: 函数式宏并不会像真正的函数那样“返回值”。本书对宏使用“返回值”一词，只是为了便于把宏按函数来理解。

<a name="list8.4" title="代码清单 8.4 使用临界区保护寄存器访问"></a>

```c
/* 把 PORTA 寄存器访问放在临界区内，确保访问过程不会被打断。进入临界区。 */
taskENTER_CRITICAL();

/* 从调用 taskENTER_CRITICAL() 到调用 taskEXIT_CRITICAL() 之间不会切换到
   其他任务。在允许中断嵌套的 FreeRTOS 移植版本中，中断仍可能执行，但仅限
   逻辑优先级高于 configMAX_SYSCALL_INTERRUPT_PRIORITY 所设值的中断；
   这些中断不得调用 FreeRTOS API 函数。 */
PORTA |= 0x01;

/* PORTA 访问已经完成，现在可以安全退出临界区。 */
taskEXIT_CRITICAL();
```
***代码清单 8.4*** *使用临界区保护寄存器访问*

本书配套示例使用 `vPrintString()` 函数向标准输出写入字符串；使用 FreeRTOS Windows 移植版本时，标准输出就是终端窗口。许多不同任务都会调用 `vPrintString()`，因此理论上可以用临界区保护标准输出访问，如代码清单 8.5 所示。

<a name="list8.5" title="代码清单 8.5 vPrintString() 的一种可能实现"></a>

```c
void vPrintString( const char *pcString )
{
    /* 把字符串写入 stdout，并以临界区作为一种简单粗糙的互斥方法。 */
    taskENTER_CRITICAL();
    {
        printf( "%s", pcString );
        fflush( stdout );
    }
    taskEXIT_CRITICAL();
}
```
***代码清单 8.5*** *`vPrintString()` 的一种可能实现*

以这种方式使用临界区，是一种非常粗糙的互斥方法。它会完全禁用中断；对于支持中断嵌套的 FreeRTOS 移植版本，则屏蔽逻辑优先级不高于 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 的中断。抢占式上下文切换只能由中断触发，因此只要相关中断保持禁用，调用 `taskENTER_CRITICAL()` 的任务就会一直处于运行状态，直到退出临界区。

基本临界区必须非常短，否则会损害中断响应时间。每次调用 `taskENTER_CRITICAL()` 都必须与一次 `taskEXIT_CRITICAL()` 严格配对。因此，不应像代码清单 8.5 那样用临界区保护标准输出（`stdout`，即程序写出数据的流），因为写终端可能耗时较长。本章后续示例将介绍其他方案。

临界区可以安全嵌套，因为内核会记录嵌套深度。只有嵌套深度回到零，也就是每次先前的 `taskENTER_CRITICAL()` 都有一次对应的 `taskEXIT_CRITICAL()` 时，系统才真正退出临界区。

对任务而言，调用 `taskENTER_CRITICAL()` 和 `taskEXIT_CRITICAL()` 是更改 FreeRTOS 所在处理器中断使能状态的唯一合法方式。通过其他方式更改中断使能状态，会破坏这两个宏维护的嵌套计数。

`taskENTER_CRITICAL()` 和 `taskEXIT_CRITICAL()` 的名称不以 `FromISR` 结尾，因此不得从中断服务程序调用。`taskENTER_CRITICAL_FROM_ISR()` 和 `taskEXIT_CRITICAL_FROM_ISR()` 分别是它们的中断安全版本。只有允许中断嵌套的 FreeRTOS 移植版本才提供这些宏，因为在不支持嵌套的移植版本中并不需要它们。

`taskENTER_CRITICAL_FROM_ISR()` 返回一个值，该值必须传给与之配对的 `taskEXIT_CRITICAL_FROM_ISR()` 调用。代码清单 8.6 展示了这种用法。

<a name="list8.6" title="代码清单 8.6 在中断服务程序中使用临界区"></a>

```c
void vAnInterruptServiceRoutine( void )
{
    /* 声明变量，用于保存 taskENTER_CRITICAL_FROM_ISR() 的返回值。 */
    UBaseType_t uxSavedInterruptStatus;

    /* ISR 的这一部分可以被任何更高优先级的中断打断。 */

    /* 使用 taskENTER_CRITICAL_FROM_ISR() 保护 ISR 中的一段代码。保存其
       返回值，以便传给配对的 taskEXIT_CRITICAL_FROM_ISR() 调用。 */
    uxSavedInterruptStatus = taskENTER_CRITICAL_FROM_ISR();

    /* ISR 的这一部分位于 taskENTER_CRITICAL_FROM_ISR() 与
       taskEXIT_CRITICAL_FROM_ISR() 调用之间，因此只能被逻辑优先级高于
       configMAX_SYSCALL_INTERRUPT_PRIORITY 所设值的中断打断。 */

    /* 调用 taskEXIT_CRITICAL_FROM_ISR() 退出临界区，并传入与之配对的
       taskENTER_CRITICAL_FROM_ISR() 所返回的值。 */
    taskEXIT_CRITICAL_FROM_ISR( uxSavedInterruptStatus );

    /* ISR 的这一部分可以被任何更高优先级的中断打断。 */
}
```
***代码清单 8.6*** *在中断服务程序中使用临界区*

如果进入和退出临界区所花的时间，比真正受保护的代码还长，就得不偿失。基本临界区的进入和退出都非常快，而且耗时确定，因此特别适合保护很短的代码段。

<a id="822-suspending-or-locking-the-scheduler"></a>
### 8.2.2 挂起（或锁定）调度器

也可以通过挂起调度器来建立临界区。挂起调度器有时也称为“锁定”调度器。

基本临界区可以防止其他任务和中断访问受保护代码；通过挂起调度器建立的临界区则只防止其他任务访问，因为中断仍保持使能。

如果临界区太长，不适合通过禁用中断来保护，可以改为挂起调度器。不过，调度器挂起期间发生的中断活动，可能使恢复（或“解除挂起”）调度器成为耗时较长的操作。因此，需要根据具体情况选择更合适的方法。

<a id="823-the-vtasksuspendall-api-function"></a>
### 8.2.3 vTaskSuspendAll() API 函数

<a name="list8.7" title="代码清单 8.7 vTaskSuspendAll() API 函数原型"></a>

```c
void vTaskSuspendAll( void );
```
***代码清单 8.7*** *`vTaskSuspendAll()` API 函数原型*

调用 `vTaskSuspendAll()` 可以挂起调度器。调度器挂起后不会发生上下文切换，但中断仍然使能。如果中断在此期间请求上下文切换，该请求会暂存起来，直到调度器恢复时才执行。

调度器挂起期间不得调用 FreeRTOS API 函数。

### 8.2.4 xTaskResumeAll() API 函数

<a name="list8.8" title="代码清单 8.8 xTaskResumeAll() API 函数原型"></a>

```c

```
***代码清单 8.8*** *`xTaskResumeAll()` API 函数原型*

调用 `xTaskResumeAll()` 可以恢复（解除挂起）调度器。

**xTaskResumeAll() 返回值**

- 返回值

  调度器挂起期间请求的上下文切换会暂存起来，只在调度器恢复时执行。如果暂存的上下文切换在 `xTaskResumeAll()` 返回前已经执行，函数返回 `pdTRUE`；否则返回 `pdFALSE`。

`vTaskSuspendAll()` 和 `xTaskResumeAll()` 可以安全嵌套，因为内核会记录嵌套深度。只有嵌套深度回到零，也就是每次先前的 `vTaskSuspendAll()` 都有一次对应的 `xTaskResumeAll()` 时，调度器才会真正恢复。

## 8.3 互斥量（与二值信号量）

互斥量是一种特殊的二值信号量，用于控制两个或多个任务对共享资源的访问。MUTEX 一词源自 “MUTual EXclusion”。必须在 `FreeRTOSConfig.h` 中把 `configUSE_MUTEXES` 设为 1，才能使用互斥量。

在互斥场景中，可以把互斥量看作与共享资源绑定的令牌。任务要合法访问资源，必须先成功“获取”令牌，成为令牌持有者。用完资源后，持有者必须“归还”令牌。只有令牌归还后，其他任务才能获取令牌并安全访问同一资源。没有持有令牌的任务不得访问共享资源。图 8.1 展示了这一机制。

互斥量和二值信号量虽然具有许多共同特性，但图 8.1 的互斥场景与图 7.6 的同步场景完全不同。主要区别在于获取信号量之后如何处理：

- 用于互斥的信号量必须始终归还。
- 用于同步的信号量通常在获取后直接消耗，不再归还。

### 8.3.1 xSemaphoreCreateMutex() API 函数

互斥量属于信号量，因此句柄同样保存在 `SemaphoreHandle_t` 类型的变量中。使用互斥量之前必须先创建它。`xSemaphoreCreateMutex()` 从 FreeRTOS 堆中动态分配所需内存；FreeRTOS 还提供 `xSemaphoreCreateMutexStatic()`，使用调用者预先提供的内存创建互斥量。

***代码清单 8.10*** *`xSemaphoreCreateMutex()` API 函数原型*

**xSemaphoreCreateMutex() 返回值**

本示例创建 `vPrintString()` 的新版本 `prvNewPrintString()`，并由多个任务调用。它的功能与 `vPrintString()` 相同，但使用互斥量而不是锁定调度器来控制标准输出访问。代码清单 8.11 给出了它的实现。

<a name="list8.11" title="代码清单 8.11 prvNewPrintString() 的实现"></a>

```c
static void prvNewPrintString( const char *pcString )
{
    /* 互斥量在调度器启动前创建，因此本任务执行时它已经存在。

       尝试获取互斥量。如果互斥量未立即可用，就无限期阻塞等待。
       xSemaphoreTake() 只有成功获取互斥量后才会返回，因此无需检查返回值。
       如果使用其他等待时间，则必须确认 xSemaphoreTake() 返回 pdTRUE 后，
       才能访问共享资源，本例中的共享资源是标准输出。如本书前文所述，生产
       代码不建议使用无限期超时。 */
    xSemaphoreTake( xMutex, portMAX_DELAY );
    {
        /* 只有成功获取互斥量后，下面的代码才会执行。任一时刻只能有一个任务
           持有互斥量，因此现在可以安全访问标准输出。 */
        printf( "%s", pcString );
        fflush( stdout );

        /* 必须归还互斥量！ */
    }
    xSemaphoreGive( xMutex );
}
```
***代码清单 8.11*** *`prvNewPrintString()` 的实现*

<a name="list8.12" title="代码清单 8.12 示例 8.1 的 prvPrintTask() 实现"></a>

```c
static void prvPrintTask( void *pvParameters )
{
    char *pcStringToPrint;
    const TickType_t xMaxBlockTimeTicks = 0x20;

    /* 本任务会创建两个实例。待输出字符串通过任务参数传入，再转换为所需类型。 */

    {

        prvNewPrintString( pcStringToPrint );

        /* 等待一段伪随机时间。注意，rand() 不一定可重入，但本例并不关心它返回
```

### 8.3.2 优先级反转

图 8.3 展示了使用互斥量实现互斥的一项潜在问题：高优先级任务 2 必须等待低优先级任务 1 释放互斥量。高优先级任务以这种方式被低优先级任务延迟，称为“优先级反转”。如果高优先级任务等待互斥量时又有中等优先级任务开始执行，问题会进一步恶化：高优先级任务等待低优先级任务，而低优先级任务却连运行机会都得不到。这通常称为*无界优先级反转*，因为中等优先级任务可能无限期延迟低优先级和高优先级任务。图 8.4 展示了这种最坏情况。

<a id="833-priority-inheritance"></a>
### 8.3.3 优先级继承

FreeRTOS 互斥量与二值信号量非常相似，区别在于互斥量带有基本的“优先级继承”机制，而二值信号量没有。优先级继承用于尽量减小优先级反转的负面影响。它不能消除优先级反转，只能确保反转持续时间有界。不过，优先级继承会增加系统时序分析的复杂度，因此不应依赖它来保证系统正确运行。

优先级继承会暂时提高互斥量持有者的优先级，使其等于所有等待该互斥量的任务中的最高优先级。换言之，持有互斥量的低优先级任务“继承”了等待者的优先级。图 8.5 展示了这一过程。互斥量归还后，持有者的优先级会自动恢复为原始值。

* * *
![](media/image67.png)   
***图 8.5*** *优先级继承减小优先级反转的影响*
* * *

如上所述，优先级继承会改变使用互斥量的任务优先级，因此不得从中断服务程序中使用互斥量。

FreeRTOS 实现的是一种基础优先级继承机制，设计目标是节省空间和处理器周期。完整实现需要明显更多的数据和运算，才能随时确定继承优先级，尤其是在一个任务同时持有多个互斥量时。

需要记住这种优先级继承机制的具体行为：
- 如果任务尚未释放已持有的互斥量，又获取另一个互斥量，它继承的优先级可能继续提高。
- 任务会保持所继承的最高优先级，直到释放自己持有的全部互斥量，与互斥量的释放顺序无关。
- 如果任务持有多个互斥量，即使等待其中某个互斥量的任务停止等待（例如超时），持有者仍会保持所继承的最高优先级。

<a id="834-deadlock-or-deadly-embrace"></a>
### 8.3.4 死锁（或称致命拥抱）

“死锁”是使用互斥量实现互斥时的另一个潜在问题，有时也被形象地称为“致命拥抱”。

当两个任务都在等待对方持有的资源，因而谁也无法继续时，就发生了死锁。假设任务 A 和任务 B 都必须同时获得互斥量 X *和*互斥量 Y 才能执行某项操作：

1. 任务 A 执行并成功获取互斥量 X。

2. 任务 A 被任务 B 抢占。

3. 任务 B 成功获取互斥量 Y，随后尝试获取互斥量 X。但 X 由任务 A 持有，因此任务 B 进入阻塞状态，等待 X 被释放。

4. 任务 A 继续执行并尝试获取互斥量 Y。但 Y 由任务 B 持有，因此任务 A 也进入阻塞状态，等待 Y 被释放。

最终，任务 A 等待任务 B 持有的互斥量，任务 B 又等待任务 A 持有的互斥量。两个任务都无法继续，系统发生死锁。

与优先级反转一样，避免死锁的最好方法是在设计阶段识别其可能性，并从系统结构上保证它不会发生。尤其需要注意，本书前文已经指出，让任务无限期等待互斥量通常不是良好做法。更稳妥的方法是设置一个略长于正常最大等待时间的超时；如果超时前仍未获得互斥量，就说明设计或运行状态存在错误，可能正是死锁。

在小型嵌入式系统中，死锁通常并不难处理，因为设计者往往能够掌握整个应用程序，从而识别并消除可能发生死锁的路径。

<a id="835-recursive-mutexes"></a>
### 8.3.5 递归互斥量

任务也可能让自己陷入死锁。如果任务尚未归还某个互斥量，又再次尝试获取同一个互斥量，就可能发生这种情况：

1. 一个任务成功获取了互斥量。

2. 在持有互斥量的同时，该任务调用了一个库函数。

3. 库函数内部尝试获取同一个互斥量，于是进入阻塞状态等待互斥量变为可用。

最终，该任务阻塞等待互斥量被归还，而它自己恰恰就是互斥量持有者。任务在等待自己释放资源，于是发生死锁。

使用递归互斥量代替标准互斥量，可以避免这类自死锁。同一任务可以多次“获取”递归互斥量；只有每一次获取都有一次对应的“归还”后，互斥量才真正释放。

标准互斥量和递归互斥量的创建和使用方式类似：

- 标准互斥量用 `xSemaphoreCreateMutex()` 创建，递归互斥量用 `xSemaphoreCreateRecursiveMutex()` 创建。两个 API 函数的原型相同。

- 标准互斥量用 `xSemaphoreTake()`“获取”，递归互斥量用 `xSemaphoreTakeRecursive()`“获取”。两个 API 函数的原型相同。

- 标准互斥量用 `xSemaphoreGive()`“归还”，递归互斥量用 `xSemaphoreGiveRecursive()`“归还”。两个 API 函数的原型相同。

代码清单 8.14 展示了如何创建和使用递归互斥量。

<a name="list8.14" title="代码清单 8.14 创建并使用递归互斥量"></a>

```c
/* 递归互斥量保存在 SemaphoreHandle_t 类型的变量中。 */
SemaphoreHandle_t xRecursiveMutex;

/* 创建并使用递归互斥量的任务实现。 */
void vTaskFunction( void *pvParameters )
{
    const TickType_t xMaxBlock20ms = pdMS_TO_TICKS( 20 );

    /* 使用递归互斥量之前必须显式创建它。 */
    xRecursiveMutex = xSemaphoreCreateRecursiveMutex();

    /* 检查信号量是否创建成功。第 11.2 节将介绍 configASSERT()。 */
    configASSERT( xRecursiveMutex );

    /* 与大多数任务一样，本任务在无限循环中实现。 */
    for( ;; )
    {
        /* ... */

        /* 获取递归互斥量。 */
        if( xSemaphoreTakeRecursive( xRecursiveMutex, xMaxBlock20ms ) == pdPASS )
        {
            /* 已成功获取递归互斥量，任务现在可以访问受其保护的资源。由于只获取
               过一次互斥量，此时递归调用计数，也就是嵌套调用
               xSemaphoreTakeRecursive() 的次数，为 1。 */

            /* 任务已经持有递归互斥量，又再次获取它。在实际应用中，这通常只会
               发生在任务调用的子函数中，因为没有理由有意重复获取同一互斥量。
               调用任务已经是持有者，所以第二次调用 xSemaphoreTakeRecursive()
               只会把递归调用计数增加到 2。 */
            xSemaphoreTakeRecursive( xRecursiveMutex, xMaxBlock20ms );

            /* ... */

            /* 任务访问完受保护资源后开始归还互斥量。此时递归调用计数为 2，
               所以第一次调用 xSemaphoreGiveRecursive() 不会真正释放互斥量，
               只会把计数减回 1。 */
            xSemaphoreGiveRecursive( xRecursiveMutex );

            /* 下一次调用 xSemaphoreGiveRecursive() 把递归调用计数减为 0，
               此时递归互斥量才真正归还。 */
            xSemaphoreGiveRecursive( xRecursiveMutex );

            /* 现在，每次先前的 xSemaphoreTakeRecursive() 调用都有一次对应的
               xSemaphoreGiveRecursive() 调用，任务不再是互斥量持有者。 */
        }
    }
}
```

### 8.3.6 互斥量与任务调度

如果两个优先级不同的任务使用同一个互斥量，FreeRTOS 调度策略会明确决定执行顺序：能够运行的最高优先级任务进入运行状态。例如，高优先级任务因等待低优先级任务持有的互斥量而阻塞时，低优先级任务一旦归还互斥量，高优先级任务就会抢占它，随后成为新的互斥量持有者。图 8.5 已展示这种情形。

但当两个任务优先级相同时，人们经常误判执行顺序。假设任务 1 和任务 2 优先级相同，任务 1 因等待任务 2 持有的互斥量而阻塞；任务 2“归还”互斥量时，任务 1 不会抢占任务 2。任务 2 会继续处于运行状态，任务 1 只会从阻塞状态转入就绪状态。图 8.6 展示了这种情形，竖线表示 Tick 中断发生的时刻。

在图 8.6 的场景中，互斥量变为可用时，FreeRTOS 调度器*不会*立即让任务 1 进入运行状态，原因如下：

- 任务 1 和任务 2 优先级相同。假设在 `FreeRTOSConfig.h` 中把 `configUSE_TIME_SLICING` 设为 1，那么除非任务 2 进入阻塞状态，否则下一次 Tick 中断之前不应切换到任务 1。

- 如果任务在紧密循环中使用互斥量，而且每次“归还”互斥量都会触发上下文切换，那么每个任务只能短暂处于运行状态。两个或多个任务会快速来回切换，浪费处理器时间。

```c
void vFunction( void *pvParameter )
{
    extern SemaphoreHandle_t xMutex;
    char cTextBuffer[ 128 ];
    TickType_t xTimeAtWhichMutexWasTaken;

    for( ;; )
    {
        /* 生成字符串，这是一个快速操作。 */
        vGenerateTextInALocalBuffer( cTextBuffer );

        /* 获取用于保护显示器访问的互斥量。 */
        xSemaphoreTake( xMutex, portMAX_DELAY );

        /* 记录获取互斥量时的时间。 */
        xTimeAtWhichMutexWasTaken = xTaskGetTickCount();

        /* 把生成的文本写入显示器，这是一个慢速操作。 */
        vCopyTextToFrameBuffer( cTextBuffer );

        /* 文本已写入显示器，归还互斥量。 */
        xSemaphoreGive( xMutex );

        /* 如果每次循环都调用 taskYIELD()，本任务每次只能短暂处于运行状态，
           处理器时间会浪费在任务间的快速切换上。因此，只有持有互斥量期间
           Tick 计数发生变化时才调用 taskYIELD()。 */
        if( xTaskGetTickCount() != xTimeAtWhichMutexWasTaken )
        {
            taskYIELD();
        }
    }
}
```

<a id="84-gatekeeper-tasks"></a>
## 8.4 门卫任务

门卫任务提供了一种简洁的互斥实现方式，不会带来优先级反转或死锁风险。

门卫任务是唯一拥有某项资源的任务。只有门卫任务可以直接访问该资源；其他任务若要使用资源，必须通过门卫任务提供的服务间接完成。

<a id="841-re-writing-vprintstring-to-use-a-gatekeeper-task"></a>
### 8.4.1 重写 vPrintString() 以使用门卫任务

示例 8.2 给出 `vPrintString()` 的另一种实现，这次由门卫任务管理标准输出访问。其他任务需要输出消息时，不再直接调用打印函数，而是把消息发送给门卫任务。

门卫任务使用 FreeRTOS 队列串行化标准输出访问。由于只有它能够直接访问标准输出，其内部实现不需要再考虑互斥。

门卫任务大部分时间处于阻塞状态，等待消息进入队列。消息到达后，它把消息写入标准输出，再回到阻塞状态等待下一条消息。代码清单 8.18 给出了门卫任务的实现。

中断也能向队列发送数据，因此中断服务程序可以安全地借助门卫任务向终端输出消息。本示例使用 Tick 钩子函数，每 200 个 Tick 发送一条消息。

Tick 钩子（或 Tick 回调）是内核在每次 Tick 中断期间调用的函数。要使用 Tick 钩子函数：

1. 在 `FreeRTOSConfig.h` 中把 `configUSE_TICK_HOOK` 设为 1。

***代码清单 8.17*** *Tick 钩子函数的名称和原型*

Tick 钩子函数在 Tick 中断上下文中执行，因此必须非常短，只能使用少量栈空间，并且不得调用名称不以 `FromISR` 结尾的 FreeRTOS API 函数。

调度器总会在 Tick 钩子函数结束后立即运行。因此，从 Tick 钩子调用中断安全 FreeRTOS API 时，无需使用 `pxHigherPriorityTaskWoken` 参数，可以将其设为 `NULL`。

<a name="list8.18" title="代码清单 8.18 门卫任务"></a>

```c
static void prvStdioGatekeeperTask( void *pvParameters )
{
    char *pcMessageToPrint;

    /* 只有本任务可以写标准输出。其他任务需要输出字符串时，不直接访问标准
       输出，而是把字符串发送给本任务。由于标准输出只由本任务访问，任务
       实现内部无需考虑互斥或串行化问题。 */
    for( ;; )
    {
        /* 等待消息到达。这里指定无限阻塞时间，因此无需检查返回值；只有成功
           接收到消息后，函数才会返回。 */
        xQueueReceive( xPrintQueue, &pcMessageToPrint, portMAX_DELAY );

        /* 输出收到的字符串。 */
        printf( "%s", pcMessageToPrint );
        fflush( stdout );

        /* 返回循环，等待下一条消息。 */
    }
}
```

***示例 8.2*** *打印任务的另一种实现*

---

代码清单 8.19 给出了写队列任务。与前一个示例一样，程序创建两个任务实例，并通过任务参数指定各实例要写入队列的字符串。

<a name="list8.19" title="代码清单 8.19 示例 8.2 的打印任务实现"></a>

```c
static void prvPrintTask( void *pvParameters )
{
    int iIndexToString;
    const TickType_t xMaxBlockTimeTicks = 0x20;

    /* 本任务会创建两个实例。任务参数用于传入字符串数组的索引，再转换为所需
       类型。 */
    iIndexToString = ( int ) pvParameters;

    for( ;; )
    {
        /* 不直接输出字符串，而是通过队列把字符串指针传给门卫任务。队列在
           调度器启动前创建，因此本任务首次执行时它已经存在。队列中应当始终
           有空位，所以这里不指定阻塞时间。 */
        xQueueSendToBack( xPrintQueue, &( pcStringsToPrint[ iIndexToString ]), 0 );

        /* 等待一段伪随机时间。注意，rand() 不一定可重入，但本例并不关心它返回
           的具体值，因此影响不大。安全性要求更高的应用应使用确认可重入的
           rand() 版本，或者用临界区保护 rand() 调用。 */
        vTaskDelay( ( rand() % xMaxBlockTimeTicks ) );
    }
}
```

***代码清单 8.19*** *示例 8.2 的打印任务实现*

Tick 钩子函数记录自己的调用次数，每当计数达到 200 时，就向门卫任务发送消息。仅为演示不同 API 的用法，Tick 钩子把消息写入队列前端，而任务把消息写入队列后端。代码清单 8.20 给出了 Tick 钩子的实现。

<a name="list8.20" title="代码清单 8.20 Tick 钩子实现"></a>

```c
void vApplicationTickHook( void )
{
    static int iCount = 0;

    /* 每 200 个 Tick 输出一条消息。消息不直接写出，而是发送给门卫任务。 */
    iCount++;

    if( iCount >= 200 )
    {
        /* xQueueSendToFrontFromISR() 从 Tick 钩子中调用，所以无需使用第三个
           参数 xHigherPriorityTaskWoken，将其设为 NULL。 */
        xQueueSendToFrontFromISR( xPrintQueue, 
                                  &( pcStringsToPrint[ 2 ] ), 
                                  NULL );

        /* 重置计数，准备在 200 个 Tick 后再次输出字符串。 */
        iCount = 0;
    }
}
```
***代码清单 8.20*** *Tick 钩子实现*

与往常一样，`main()` 创建运行示例所需的队列和任务，然后启动调度器。代码清单 8.21 给出了它的实现。

```c
/* 定义任务和中断要通过门卫任务输出的字符串。 */
static char *pcStringsToPrint[] =
{
    "Task 1 ****************************************************\r\n",
    "Task 2 ----------------------------------------------------\r\n",
    "Message printed from the tick hook interrupt ##############\r\n"
};

/*-----------------------------------------------------------*/

/* 声明 QueueHandle_t 类型的变量。打印任务和 Tick 中断通过该队列向门卫任务
   发送消息。 */
QueueHandle_t xPrintQueue;

/*-----------------------------------------------------------*/

int main( void )
{
    /* 使用队列之前必须显式创建它。本队列最多容纳 5 个字符指针。 */
    xPrintQueue = xQueueCreate( 5, sizeof( char * ) );

    /* 检查队列是否创建成功。 */
    if( xPrintQueue != NULL )
    {
        /* 创建两个向门卫任务发送消息的任务实例。任务使用的字符串索引通过任务
           参数，也就是 xTaskCreate() 的第 4 个参数传入。两个任务使用不同
           优先级，因此高优先级任务偶尔会抢占低优先级任务。 */
        xTaskCreate( prvPrintTask, "Print1", 1000, ( void * ) 0, 1, NULL );
        xTaskCreate( prvPrintTask, "Print2", 1000, ( void * ) 1, 2, NULL );

        /* 创建门卫任务。只有该任务可以直接访问标准输出。 */
        xTaskCreate( prvStdioGatekeeperTask, "Gatekeeper", 1000, NULL, 0, NULL );

        /* 启动调度器，使已创建的任务开始执行。 */
        vTaskStartScheduler();
    }

    /* 如果一切正常，调度器此时正在运行任务，main() 永远不会执行到这里。
       如果确实执行到这里，很可能是因为堆内存不足，无法创建空闲任务。
       第 3 章提供了更多堆内存管理信息。 */
    for( ;; );
}
```
