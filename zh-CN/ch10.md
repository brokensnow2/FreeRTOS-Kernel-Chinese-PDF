# 10 任务通知

<a id="101-introduction"></a>
## 10.1 简介

FreeRTOS 应用程序通常由一系列相互独立的任务组成，这些任务彼此通信，共同实现系统功能。任务通知是一种高效机制，允许一个任务直接通知另一个任务。

<a id="1011-communicating-through-intermediary-objects"></a>
### 10.1.1 通过中介对象通信

本书已经介绍了多种任务间通信方式。此前介绍的方法都要求先创建通信对象，例如队列、事件组和各种类型的信号量。

使用通信对象时，事件和数据不是直接发送给接收任务或接收 ISR，而是发送到通信对象。同样，任务和 ISR 从通信对象接收事件和数据，而不是直接从发送事件或数据的任务或 ISR 接收。图 10.1 展示了这一过程。

### 10.1.2 任务通知：直接面向任务的通信

“任务通知”让任务无需单独的通信对象即可与其他任务交互，并与 ISR 同步。借助任务通知，任务或 ISR 可以把事件直接发送给接收任务。图 10.2 展示了这一过程。

任务通知功能是可选的。要启用任务通知，请在 FreeRTOSConfig.h 中把 `configUSE_TASK_NOTIFICATIONS` 设为 1。

当 `configUSE_TASK_NOTIFICATIONS` 为 1 时，每个任务至少有一个“通知状态”和一个“通知值”。通知状态可以是“待处理”或“非待处理”，通知值是一个 32 位无符号整数。任务收到通知时，其通知状态变为待处理；任务读取通知值时，其通知状态变为非待处理。如果把 `configTASK_NOTIFICATION_ARRAY_ENTRIES` 设为大于 1 的值，每个任务就拥有多个按索引标识的通知状态和通知值。

任务可以进入阻塞状态，等待其通知状态变为待处理，并可选择设置超时时间。

<a id="102-task-notifications-benefits-and-limitations"></a>
## 10.2 任务通知的优点与局限

<a id="1021-performance-benefits-of-task-notifications"></a>
### 10.2.1 任务通知的性能优势

使用任务通知向任务发送事件或数据，明显快于使用队列、信号量或事件组执行等效操作。

<a id="1022-ram-footprint-benefits-of-task-notifications"></a>
### 10.2.2 任务通知的 RAM 占用优势

同样，使用任务通知向任务发送事件或数据，所需 RAM 明显少于使用队列、信号量或事件组执行等效操作。这是因为每个通信对象都必须先创建才能使用，而启用任务通知只会产生固定开销。每个任务的任务通知占用 `configTASK_NOTIFICATION_ARRAY_ENTRIES` * 5 字节 RAM。`configTASK_NOTIFICATION_ARRAY_ENTRIES` 的默认值为 1，因此默认情况下每个任务的任务通知占用 5 字节。

<a id="1023-limitations-of-task-notifications"></a>
### 10.2.3 任务通知的局限

任务通知比通信对象更快、占用的 RAM 更少，但并不适用于所有场景。以下场景不能使用任务通知：

- 向 ISR 发送事件或数据

  通信对象既可把事件和数据从 ISR 发送给任务，也可从任务发送给 ISR。

  任务通知可把事件和数据从 ISR 发送给任务，但不能从任务发送给 ISR。

- 允许多个任务接收

  任何知道通信对象句柄的任务或 ISR 都可以访问该对象。任意数量的任务和 ISR 都能处理发送到某个通信对象的事件或数据。

  任务通知直接发送给接收任务，因此只有通知的目标任务能够处理它。不过，这在实际应用中很少构成限制，因为多个任务和 ISR 向同一通信对象发送数据很常见，而多个任务和 ISR 从同一通信对象接收数据并不常见。

- 缓冲多个数据项

  队列是一种可同时保存多个数据项的通信对象。已经发送到队列但尚未被接收的数据，会缓存在队列对象中。

  任务通知通过更新接收任务的通知值来发送数据，而任务的通知值一次只能保存一个值。

- 向多个任务广播

  事件组是一种可同时向多个任务发送事件的通信对象。

  任务通知直接发送给接收任务，因此只有接收任务能够处理它。

- 在阻塞状态下等待发送完成

  如果通信对象暂时无法再写入数据或事件，例如队列已满，那么尝试写入该对象的任务可以选择进入阻塞状态，等待写操作完成。

  如果任务尝试向一个已经有待处理通知的任务发送通知，那么发送任务无法进入阻塞状态，等待接收任务复位其通知状态。后文会看到，在实际使用任务通知的场景中，这很少构成限制。

<a id="103-using-task-notifications"></a>
## 10.3 使用任务通知

<a id="1031-task-notification-api-options"></a>
### 10.3.1 任务通知 API 选项

任务通知功能非常强大，通常可以替代二值信号量、计数信号量、事件组，有时甚至可以替代队列。使用 `xTaskNotify()` API 函数发送任务通知，并使用 `xTaskNotifyWait()` API 函数接收任务通知，即可覆盖这些使用场景。

不过，大多数情况下并不需要 `xTaskNotify()` 和 `xTaskNotifyWait()` 提供的全部灵活性，使用更简单的函数已经足够。因此，FreeRTOS 提供 `xTaskNotifyGive()` 作为 `xTaskNotify()` 更简单但灵活性较低的替代函数，并提供 `ulTaskNotifyTake()` 作为 `xTaskNotifyWait()` 更简单但灵活性较低的替代函数。

任务通知系统不限于单个通知。配置参数 `configTASK_NOTIFICATION_ARRAY_ENTRIES` 默认值为 1；如果把它设为大于 1 的值，每个任务内部都会创建一个通知数组，从而可以按索引管理通知。每个任务通知 API 都有索引版本。调用非索引版本时访问的是 `notification[0]`，也就是数组中的第一个通知。索引版本的函数名带有 `Indexed` 后缀，例如 `xTaskNotify` 的索引版本是 `xTaskNotifyIndexed`。为简化说明，本书只使用各函数的非索引版本。

任务通知 API 实际上由宏实现，这些宏调用对应 API 类型底层的 `Generic` 版本。为简化表述，本书仍把这些 API 宏称为函数。

<a id="1032-the-xtasknotifygive-api-functions"></a>
### 10.3.2 xTaskNotifyGive() API 函数

`xTaskNotifyGive()` 直接向任务发送通知，并递增接收任务的通知值。如果接收任务的通知状态尚非待处理，调用 `xTaskNotifyGive()` 会把它设为待处理。

`xTaskNotifyGive()` 使任务通知能够作为二值信号量或计数信号量更轻量、更快速的替代方案。

<a name="list10.1" title="代码清单 10.1 xTaskNotifyGive() API 函数原型"></a>

```c
BaseType_t xTaskNotifyGive( TaskHandle_t xTaskToNotify );
BaseType_t xTaskNotifyGiveIndexed( TaskHandle_t xTaskToNotify, UBaseType_t uxIndexToNotify );
```

***代码清单 10.1*** *`xTaskNotifyGive()` API 函数原型*

**xTaskNotifyGive()/xTaskNotifyGiveIndexed() 参数和返回值**

- `xTaskToNotify`

  接收通知的任务句柄。有关如何获取任务句柄的信息，请参见 `xTaskCreate()` API 函数的 `pxCreatedTask` 参数。

- `uxIndexToNotify`

  通知数组中的索引。

- 返回值

  `xTaskNotifyGive()` 是一个调用 `xTaskNotify()` 的宏。该宏传给 `xTaskNotify()` 的参数决定了唯一可能的返回值是 `pdPASS`。本章稍后介绍 `xTaskNotify()`。

<a id="1033-the-vtasknotifygivefromisr-api-function"></a>
### 10.3.3 vTaskNotifyGiveFromISR() API 函数

`vTaskNotifyGiveFromISR()` 是可在中断服务程序中使用的 `xTaskNotifyGive()` 版本。

<a name="list10.2" title="代码清单 10.2 vTaskNotifyGiveFromISR() API 函数原型"></a>

```c
void vTaskNotifyGiveFromISR( TaskHandle_t xTaskToNotify,
                             BaseType_t *pxHigherPriorityTaskWoken );
```

***代码清单 10.2*** *`vTaskNotifyGiveFromISR()` API 函数原型*

**vTaskNotifyGiveFromISR() 参数和返回值**

- `xTaskToNotify`

  接收通知的任务句柄。有关如何获取任务句柄的信息，请参见 `xTaskCreate()` API 函数的 `pxCreatedTask` 参数。

- `pxHigherPriorityTaskWoken`

  如果接收通知的任务正处于阻塞状态，等待接收通知，那么发送通知会使该任务离开阻塞状态。

  如果调用 `vTaskNotifyGiveFromISR()` 使任务离开阻塞状态，而且该任务的优先级高于当前正在执行的任务（即被中断的任务），`vTaskNotifyGiveFromISR()` 会在内部把 `*pxHigherPriorityTaskWoken` 设为 `pdTRUE`。

  如果 `vTaskNotifyGiveFromISR()` 把该值设为 `pdTRUE`，则应在退出中断前执行上下文切换，以确保中断直接返回到处于就绪状态的最高优先级任务。

  与所有中断安全 API 函数一样，使用 `pxHigherPriorityTaskWoken` 参数之前必须先把它设为 `pdFALSE`。

<a id="1034-the-ultasknotifytake-api-function"></a>
### 10.3.4 ulTaskNotifyTake() API 函数

`ulTaskNotifyTake()` 允许任务进入阻塞状态，等待其通知值大于 0，并在返回前递减通知值或将其清零。

`ulTaskNotifyTake()` 使任务通知能够作为二值信号量或计数信号量更轻量、更快速的替代方案。

<a name="list10.3" title="代码清单 10.3 ulTaskNotifyTake() API 函数原型"></a>

```c
uint32_t ulTaskNotifyTake( BaseType_t xClearCountOnExit, TickType_t
xTicksToWait );
```

***代码清单 10.3*** *`ulTaskNotifyTake()` API 函数原型*

**ulTaskNotifyTake() 参数和返回值**

- `xClearCountOnExit`

  如果 `xClearCountOnExit` 为 `pdTRUE`，调用任务的通知值会在 `ulTaskNotifyTake()` 返回前清零。

  如果 `xClearCountOnExit` 为 `pdFALSE`，而调用任务的通知值大于 0，那么通知值会在 `ulTaskNotifyTake()` 返回前递减。

- `xTicksToWait`

  调用任务为了等待通知值大于 0 而保持阻塞状态的最长时间。

  阻塞时间以 Tick 周期为单位，因此它所代表的绝对时间取决于 Tick 频率。宏 `pdMS_TO_TICKS()` 可把以毫秒表示的时间转换为以 Tick 表示的时间。

  如果 `FreeRTOSConfig.h` 中的 `INCLUDE_vTaskSuspend` 设为 1，把 `xTicksToWait` 设为 `portMAX_DELAY` 会使任务无限期等待，不会超时。

- 返回值

  返回值是按照 `xClearCountOnExit` 参数的设置，将调用任务的通知值清零或递减*之前*的值。

  如果指定了阻塞时间，而且返回值非 0，那么调用任务可能曾进入阻塞状态等待通知值大于 0，随后通知值在阻塞时间到期前得到更新。

  如果指定了阻塞时间，而且返回值为 0，那么调用任务曾进入阻塞状态等待通知值大于 0，但在此之前指定的阻塞时间已经到期。

***示例 10.1*** *使用任务通知替代信号量：方法 1*

---

示例 7.1 使用二值信号量从中断服务程序解除任务的阻塞，相当于让任务与中断同步。本示例复现示例 7.1 的功能，但使用直接任务通知替代二值信号量。

代码清单 10.4 展示了与中断同步的任务实现。示例 7.1 中对 `xSemaphoreTake()` 的调用被替换为对 `ulTaskNotifyTake()` 的调用。

`ulTaskNotifyTake()` 的 `xClearCountOnExit` 参数设为 `pdTRUE`，因此接收任务的通知值会在函数返回前清零。所以，每次调用 `ulTaskNotifyTake()` 之间都必须处理所有已经出现的事件。在示例 7.1 中，由于使用二值信号量，必须从硬件确定待处理事件的数量，这并非总是可行。示例 10.1 则由 `ulTaskNotifyTake()` 返回待处理事件的数量。

两次调用 `ulTaskNotifyTake()` 之间发生的中断事件会锁存在任务的通知值中；如果调用任务已经有待处理通知，`ulTaskNotifyTake()` 会立即返回。

<a name="list10.4" title="代码清单 10.4 示例 10.1 中延迟执行中断处理的任务实现"></a>

```c
/* 周期任务产生软件中断的频率。 */
const TickType_t xInterruptFrequency = pdMS_TO_TICKS( 500UL );

static void vHandlerTask( void *pvParameters )
{
    /* xMaxExpectedBlockTime 略长于两次事件之间预计的最长时间。 */
    const TickType_t xMaxExpectedBlockTime = xInterruptFrequency +
                                             pdMS_TO_TICKS( 10 );
    uint32_t ulEventsToProcess;

    /* 与大多数任务一样，本任务在无限循环中实现。 */
    for( ;; )
    {
        /* 等待接收中断服务程序直接发给本任务的通知。 */
        ulEventsToProcess = ulTaskNotifyTake( pdTRUE, xMaxExpectedBlockTime );
        if( ulEventsToProcess != 0 )
        {
            /* 执行到这里说明至少发生了一个事件。循环处理所有待处理事件，
               本例只为每个事件输出一条消息。 */
            while( ulEventsToProcess > 0 )
            {
                vPrintString( "Handler task - Processing event.\r\n" );
                ulEventsToProcess--;
            }
        }
        else
        {
            /* 执行到这里说明中断没有在预期时间内到达。在实际应用中，
               可能需要执行某些错误恢复操作。 */
        }
    }
}
```

***代码清单 10.4*** *示例 10.1 中延迟执行中断处理的任务实现（与中断同步的任务）*

用于产生软件中断的周期任务会在产生中断前后分别输出一条消息，以便从输出中观察执行顺序。

代码清单 10.5 展示了中断处理程序。除了直接向延迟执行中断处理的任务发送通知外，它几乎不做其他工作。

<a name="list10.5" title="代码清单 10.5 示例 10.1 使用的中断服务程序实现"></a>

```c
static uint32_t ulExampleInterruptHandler( void )
{
    BaseType_t xHigherPriorityTaskWoken;

    /* 必须把 xHigherPriorityTaskWoken 参数初始化为 pdFALSE。如果需要上下文
       切换，中断安全 API 函数会在内部把它设为 pdTRUE。 */
    xHigherPriorityTaskWoken = pdFALSE;

    /* 直接向延迟执行中断处理的任务发送通知。 */
    vTaskNotifyGiveFromISR( /* 接收通知的任务句柄。创建任务时已经保存该句柄。 */
                            xHandlerTask,

                            /* 按通常方式使用 xHigherPriorityTaskWoken。 */
                            &xHigherPriorityTaskWoken );

    /* 把 xHigherPriorityTaskWoken 传给 portYIELD_FROM_ISR()。如果
       vTaskNotifyGiveFromISR() 在内部把它设为 pdTRUE，调用
       portYIELD_FROM_ISR() 会请求上下文切换；如果它仍为 pdFALSE，则调用
       不会产生任何效果。Windows 移植版本的 portYIELD_FROM_ISR() 实现
       包含 return 语句，因此本函数没有显式返回值。 */
    portYIELD_FROM_ISR( xHigherPriorityTaskWoken );
}
```

<a name="example10.2" title="示例 10.2 使用任务通知替代信号量：方法 2"></a>
---
***示例 10.2*** *使用任务通知替代信号量：方法 2*

---

示例 10.1 把 `ulTaskNotifyTake()` 的 `xClearOnExit` 参数设为 `pdTRUE`。示例 10.2 对示例 10.1 稍作修改，展示把该参数改为 `pdFALSE` 后的行为。

当 `xClearOnExit` 为 `pdFALSE` 时，调用 `ulTaskNotifyTake()` 只会把调用任务的通知值减 1，而不会将其清零。因此，通知计数等于已经发生的事件数减去已经处理的事件数。这样可以从两个方面简化 `vHandlerTask()` 的结构：

1. 等待处理的事件数量保存在通知值中，无需再保存到局部变量。

2. 每次调用 `ulTaskNotifyTake()` 之间只需处理一个事件。

示例 10.2 使用的 `vHandlerTask()` 实现见代码清单 10.6。

<a name="list10.6" title="代码清单 10.6 示例 10.2 中延迟执行中断处理的任务实现"></a>

```c
static void vHandlerTask( void *pvParameters )
{
    /* xMaxExpectedBlockTime 略长于两次事件之间预计的最长时间。 */
    const TickType_t xMaxExpectedBlockTime = xInterruptFrequency + 
                                             pdMS_TO_TICKS( 10 );

    /* 与大多数任务一样，本任务在无限循环中实现。 */
    for( ;; )
    {
        /* 等待接收中断服务程序直接发给本任务的通知。xClearCountOnExit 参数
           现在为 pdFALSE，因此 ulTaskNotifyTake() 会递减任务的通知值，
           而不会将其清零。 */
        if( ulTaskNotifyTake( pdFALSE, xMaxExpectedBlockTime ) != 0 )
        {
            /* 执行到这里说明发生了一个事件。处理该事件，本例只输出一条消息。 */
            vPrintString( "Handler task - Processing event.\r\n" );
        }
        else
        {
            /* 执行到这里说明中断没有在预期时间内到达。在实际应用中，
               可能需要执行某些错误恢复操作。 */
        }
    }
}
```

***代码清单 10.6*** *示例 10.2 中延迟执行中断处理的任务实现（与中断同步的任务）*

为便于演示，中断服务程序也经过修改，每次中断会发送多个任务通知，从而模拟多个中断高频发生。示例 10.2 使用的中断服务程序实现见代码清单 10.7。

<a name="list10.7" title="代码清单 10.7 示例 10.2 使用的中断服务程序实现"></a>

```c
static uint32_t ulExampleInterruptHandler( void )
{
    BaseType_t xHigherPriorityTaskWoken;

    xHigherPriorityTaskWoken = pdFALSE;

    /* 多次向处理任务发送通知。第一次“给出”通知会解除任务的阻塞，后续“给出”
       用于展示接收任务如何使用通知值对事件进行计数（锁存），从而逐个处理。 */
    vTaskNotifyGiveFromISR( xHandlerTask, &xHigherPriorityTaskWoken );
    vTaskNotifyGiveFromISR( xHandlerTask, &xHigherPriorityTaskWoken );
    vTaskNotifyGiveFromISR( xHandlerTask, &xHigherPriorityTaskWoken );

    portYIELD_FROM_ISR( xHigherPriorityTaskWoken );
}
```

<a id="1035-the-xtasknotify-and-xtasknotifyfromisr-api-functions"></a>
### 10.3.5 xTaskNotify() 和 xTaskNotifyFromISR() API 函数

`xTaskNotify()` 是功能更强的 `xTaskNotifyGive()` 版本，可以通过以下任一种方式更新接收任务的通知值：

- 递增接收任务的通知值，此时 `xTaskNotify()` 等效于 `xTaskNotifyGive()`。

- 设置接收任务通知值中的一个或多个位，使任务通知值能够作为事件组更轻量、更快速的替代方案。

- 仅当接收任务自上次更新后已经读取通知值时，才向通知值写入一个全新的数值。这使任务通知值能够提供类似长度为 1 的队列的功能。

- 即使接收任务自上次更新后尚未读取通知值，也向通知值写入一个全新的数值。这使任务通知值能够提供类似 `xQueueOverwrite()` API 函数的功能，产生的行为有时称为“邮箱”。

`xTaskNotify()` 比 `xTaskNotifyGive()` 更灵活、功能更强，因此使用起来也稍微复杂一些。

`xTaskNotifyFromISR()` 是可在中断服务程序中使用的 `xTaskNotify()` 版本，所以它多了一个 `pxHigherPriorityTaskWoken` 参数。

如果接收任务的通知状态尚非待处理，调用 `xTaskNotify()` 总会把它设为待处理。

<a name="list10.8" title="代码清单 10.8 xTaskNotify() 和 xTaskNotifyFromISR() API 函数原型"></a>

```c
BaseType_t xTaskNotify( TaskHandle_t xTaskToNotify,
                        uint32_t ulValue,
                        eNotifyAction eAction );

BaseType_t xTaskNotifyFromISR( TaskHandle_t xTaskToNotify,
                               uint32_t ulValue,
                               eNotifyAction eAction,
                               BaseType_t *pxHigherPriorityTaskWoken );
```

***代码清单 10.8*** *`xTaskNotify()` 和 `xTaskNotifyFromISR()` API 函数原型*

**xTaskNotify() 参数和返回值**

- `xTaskToNotify`

  接收通知的任务句柄。有关如何获取任务句柄的信息，请参见 `xTaskCreate()` API 函数的 `pxCreatedTask` 参数。

- `ulValue`

  `ulValue` 的用途取决于 `eNotifyAction` 的取值，详见下文。

- `eNotifyAction`

  一个枚举类型，指定如何更新接收任务的通知值，详见下文。

- 返回值

  除下文指出的一种情况外，`xTaskNotify()` 都返回 `pdPASS`。

**xTaskNotify() 的有效 eNotifyAction 参数值及其对接收任务通知值的影响**

- `eNoAction`

  把接收任务的通知状态设为待处理，但不更新通知值。此时不使用 `xTaskNotify()` 的 `ulValue` 参数。

  `eNoAction` 使任务通知能够作为二值信号量更快、更轻量的替代方案。

- `eSetBits`

  接收任务的通知值与 `xTaskNotify()` 的 `ulValue` 参数按位或。例如，如果 `ulValue` 为 0x01，则接收任务通知值中的位 0 被置位；如果 `ulValue` 为 0x06（二进制 0110），则位 1 和位 2 被置位。

  `eSetBits` 使任务通知能够作为事件组更快、更轻量的替代方案。

- `eIncrement`

  递增接收任务的通知值。此时不使用 `xTaskNotify()` 的 `ulValue` 参数。

  `eIncrement` 使任务通知能够作为二值信号量或计数信号量更快、更轻量的替代方案，并且等效于更简单的 `xTaskNotifyGive()` API 函数。

- `eSetValueWithoutOverwrite`

  如果调用 `xTaskNotify()` 之前接收任务已有待处理通知，则不执行任何操作，并返回 `pdFAIL`。

  如果调用前接收任务没有待处理通知，则把接收任务的通知值设为 `xTaskNotify()` 的 `ulValue` 参数值。

- `eSetValueWithOverwrite`

  无论调用 `xTaskNotify()` 前接收任务是否已有待处理通知，都把接收任务的通知值设为 `xTaskNotify()` 的 `ulValue` 参数值。

<a id="1036-the-xtasknotifywait-api-function"></a>
### 10.3.6 xTaskNotifyWait() API 函数

`xTaskNotifyWait()` 是功能更强的 `ulTaskNotifyTake()` 版本。如果调用任务的通知状态尚非待处理，它允许任务等待该状态变为待处理，并可选择设置超时时间。`xTaskNotifyWait()` 还可以选择在进入函数和退出函数时，分别清除调用任务通知值中的指定位。

<a name="list10.9" title="代码清单 10.9 xTaskNotifyWait() API 函数原型"></a>

```c
BaseType_t xTaskNotifyWait( uint32_t   ulBitsToClearOnEntry,
                            uint32_t   ulBitsToClearOnExit,
                            uint32_t   *pulNotificationValue,
                            TickType_t xTicksToWait );
```

***代码清单 10.9*** *`xTaskNotifyWait()` API 函数原型*

**xTaskNotifyWait() 参数和返回值**

- `ulBitsToClearOnEntry`

  如果调用 `xTaskNotifyWait()` 前调用任务没有待处理通知，那么进入函数时，会清除任务通知值中由 `ulBitsToClearOnEntry` 置位的各个位。

  例如，如果 `ulBitsToClearOnEntry` 为 0x01，则清除任务通知值中的位 0。把 `ulBitsToClearOnEntry` 设为 0xffffffff（`ULONG_MAX`）会清除通知值中的所有位，相当于把通知值清零。

- `ulBitsToClearOnExit`

  如果调用任务因为收到通知而退出 `xTaskNotifyWait()`，或者调用函数时已经有待处理通知，那么退出函数前，会清除任务通知值中由 `ulBitsToClearOnExit` 置位的各个位。

  这些位只会在任务通知值保存到 `*pulNotificationValue` 之后才被清除。

  例如，如果 `ulBitsToClearOnExit` 为 0x03，则函数退出前会清除任务通知值中的位 0 和位 1。

  把 `ulBitsToClearOnExit` 设为 0xffffffff（`ULONG_MAX`）会清除通知值中的所有位，相当于把通知值清零。

- `pulNotificationValue`

  用于传出任务的通知值。复制到 `*pulNotificationValue` 的值，是按照 `ulBitsToClearOnExit` 清除任何位之前的任务通知值。

  `pulNotificationValue` 是可选参数，不需要通知值时可设为 `NULL`。

- `xTicksToWait`

  调用任务为了等待通知状态变为待处理而保持阻塞状态的最长时间。

  阻塞时间以 Tick 周期为单位，因此它所代表的绝对时间取决于 Tick 频率。宏 `pdMS_TO_TICKS()` 可把以毫秒表示的时间转换为以 Tick 表示的时间。

  如果 `FreeRTOSConfig.h` 中的 `INCLUDE_vTaskSuspend` 设为 1，把 `xTicksToWait` 设为 `portMAX_DELAY` 会使任务无限期等待，不会超时。

- 返回值

  可能有两种返回值：

  - `pdTRUE`

    表示 `xTaskNotifyWait()` 因收到通知而返回，或者调用该函数时调用任务已经有待处理通知。

    如果指定了非 0 阻塞时间，调用任务可能曾进入阻塞状态等待通知状态变为待处理，随后通知状态在阻塞时间到期前变为待处理。

  - `pdFALSE`

    表示 `xTaskNotifyWait()` 返回时，调用任务没有收到任务通知。

    如果 `xTicksToWait` 非 0，调用任务曾保持在阻塞状态等待通知状态变为待处理，但在此之前指定的阻塞时间已经到期。

<a id="1037-task-notifications-used-in-peripheral-device-drivers-uart-example"></a>
### 10.3.7 在外设驱动程序中使用任务通知：UART 示例

外设驱动库为硬件接口提供执行常见操作的函数。经常配有驱动库的外设包括通用异步收发器（UART）、串行外设接口（SPI）、模数转换器（ADC）和以太网端口。这类库通常提供初始化外设、向外设发送数据以及从外设接收数据等函数。

某些外设操作需要较长时间才能完成，例如高精度 ADC 转换，或者通过 UART 发送大型数据包。驱动库函数可以通过轮询，也就是反复读取外设状态寄存器，来判断操作何时完成。但这种轮询几乎总是在浪费资源：没有执行有效处理时却占用了 100% 的处理器时间。在多任务系统中，这种浪费尤其严重，因为轮询外设的任务可能阻止真正有工作要做的低优先级任务执行。

为了避免浪费处理时间，高效且支持 RTOS 的设备驱动程序应由中断驱动，并允许发起长时间操作的任务进入阻塞状态等待操作完成。这样，在该任务处于阻塞状态时，较低优先级任务可以执行，没有任务会在无法有效利用处理器时占用处理时间。

支持 RTOS 的驱动库通常使用二值信号量使任务进入阻塞状态。代码清单 10.10 的伪代码展示了这种技术，其中给出了一个支持 RTOS、通过 UART 端口发送数据的库函数框架。在代码清单 10.10 中：

- `xUART` 是描述 UART 外设并保存状态信息的结构体，其 `xTxSemaphore` 成员是 `SemaphoreHandle_t` 类型变量。这里假定信号量已经创建。

- `xUART_Send()` 函数不包含互斥逻辑。如果多个任务要使用该函数，应用程序编写者必须在应用层管理互斥。例如，可以要求任务先获取互斥量，再调用 `xUART_Send()`。

- 启动 UART 传输后，使用 `xSemaphoreTake()` API 函数使调用任务进入阻塞状态。

- 传输完成时会执行 UART 外设的发送结束中断服务程序，该程序调用 `xSemaphoreGiveFromISR()` API 函数，使任务离开阻塞状态。

<a name="list10.10" title="代码清单 10.10 在驱动库发送函数中使用二值信号量的伪代码"></a>

```c
/* 向 UART 发送数据的驱动库函数。 */

BaseType_t xUART_Send( xUART *pxUARTInstance, 
                       uint8_t *pucDataSource, 
                       size_t uxLength )
{
    BaseType_t xReturn;

    /* 尝试以 0 超时获取信号量，确保 UART 发送信号量当前不可用。 */
    xSemaphoreTake( pxUARTInstance->xTxSemaphore, 0 );

    /* 启动传输。 */
    UART_low_level_send( pxUARTInstance, pucDataSource, uxLength );

    /* 阻塞在信号量上，等待传输完成。如果获得信号量，xReturn 会被设为
       pdPASS；如果获取信号量超时，xReturn 会被设为 pdFAIL。请注意，如果
       中断发生在调用 UART_low_level_send() 和调用 xSemaphoreTake() 之间，
       事件会锁存在二值信号量中，xSemaphoreTake() 随后会立即返回。 */
    xReturn = xSemaphoreTake( pxUARTInstance->xTxSemaphore, 
                              pxUARTInstance->xTxTimeout );

    return xReturn;
}
/*-----------------------------------------------------------*/

/* UART 发送结束中断的服务程序，在最后一个字节发送给 UART 后执行。 */
void xUART_TransmitEndISR( xUART *pxUARTInstance )
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* 清除中断。 */
    UART_low_level_interrupt_clear( pxUARTInstance );

    /* 给出 Tx 信号量，表示传输结束。如果有任务阻塞等待该信号量，则使该任务
       离开阻塞状态。 */
    xSemaphoreGiveFromISR( pxUARTInstance->xTxSemaphore, 
                           &xHigherPriorityTaskWoken );
    portYIELD_FROM_ISR( xHigherPriorityTaskWoken );
}
```

***代码清单 10.10*** *在驱动库发送函数中使用二值信号量的伪代码*

代码清单 10.10 所示技术完全可行，而且十分常见，但也有一些缺点：

- 驱动库使用多个信号量，会增加 RAM 占用。

- 信号量必须先创建才能使用，因此使用信号量的驱动库必须经过显式初始化才能使用。

- 信号量是适用于多种场景的通用对象，包含允许任意数量任务进入阻塞状态等待信号量，以及在信号量可用时以确定性方式选择解除哪个任务阻塞的逻辑。执行这些逻辑需要时间，而代码清单 10.10 的场景在任意时刻最多只有一个任务等待信号量，因此这些处理开销并无必要。

代码清单 10.11 展示了如何使用任务通知替代二值信号量，从而避免这些缺点。

> *注意：如果驱动库使用任务通知，其文档必须明确说明，调用库函数可能改变调用任务的通知状态和通知值。*

在代码清单 10.11 中：

- `xUART` 结构体的 `xTxSemaphore` 成员替换为 `xTaskToNotify` 成员。`xTaskToNotify` 是 `TaskHandle_t` 类型变量，用于保存等待 UART 操作完成的任务句柄。

- 使用 FreeRTOS API 函数 `xTaskGetCurrentTaskHandle()` 获取处于运行状态的任务句柄。

- 驱动库不创建任何 FreeRTOS 对象，因此不会产生额外 RAM 开销，也不需要显式初始化。

- 任务通知直接发送给等待 UART 操作完成的任务，因此不会执行不必要的逻辑。

任务和中断服务程序都会访问 `xUART` 结构体的 `xTaskToNotify` 成员，因此必须考虑处理器如何更新该值：

- 如果一次内存写操作即可更新 `xTaskToNotify`，就可以像代码清单 10.11 那样在临界区外更新。例如，当 `xTaskToNotify` 是 32 位变量且 FreeRTOS 运行在 32 位处理器上时，就是这种情况。

- 如果更新 `xTaskToNotify` 需要多次内存写操作，就只能在临界区内更新，否则中断服务程序可能在它处于不一致状态时访问它。例如，当 `xTaskToNotify` 是 32 位变量，而 FreeRTOS 运行在 16 位处理器上时，需要两次 16 位内存写操作才能更新全部 32 位。

在 FreeRTOS 内部实现中，`TaskHandle_t` 是指针，因此 `sizeof( TaskHandle_t )` 始终等于 `sizeof( void * )`。

<a name="list10.11" title="代码清单 10.11 在驱动库发送函数中使用任务通知的伪代码"></a>

```c
/* 向 UART 发送数据的驱动库函数。 */
BaseType_t xUART_Send( xUART *pxUARTInstance, 
                       uint8_t *pucDataSource, 
                       size_t uxLength )
{
    BaseType_t xReturn;

    /* 保存调用本函数的任务句柄。正文说明了下一行是否需要临界区保护。 */
    pxUARTInstance->xTaskToNotify = xTaskGetCurrentTaskHandle();

    /* 调用 ulTaskNotifyTake()，把 xClearCountOnExit 设为 pdTRUE，并把阻塞时间
       设为 0（不阻塞），确保调用任务当前没有待处理通知。 */
    ulTaskNotifyTake( pdTRUE, 0 );

    /* 启动传输。 */
    UART_low_level_send( pxUARTInstance, pucDataSource, uxLength );

    /* 阻塞等待传输完成通知。如果收到通知，xReturn 为 1，因为 ISR 已把本任务
       的通知值递增到 1（pdTRUE）。如果操作超时，xReturn 为 0（pdFALSE），
       因为本任务的通知值自上面清零后没有改变。请注意，如果 ISR 在调用
       UART_low_level_send() 与 ulTaskNotifyTake() 之间执行，事件会锁存在任务
       的通知值中，ulTaskNotifyTake() 随后会立即返回。 */
    xReturn = ( BaseType_t ) ulTaskNotifyTake( pdTRUE, 
                                               pxUARTInstance->xTxTimeout );

    return xReturn;
}
/*-----------------------------------------------------------*/

/* UART 发送完最后一个字节后执行的 ISR。 */
void xUART_TransmitEndISR( xUART *pxUARTInstance )
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* 除非有任务正在等待通知，否则不应执行本函数。使用断言检查该条件。
       这一步并非绝对必要，但有助于调试。第 12.2 节介绍 configASSERT()。 */
    configASSERT( pxUARTInstance->xTaskToNotify != NULL );

    /* 清除中断。 */
    UART_low_level_interrupt_clear( pxUARTInstance );

    /* 直接向调用 xUART_Send() 的任务发送通知。如果该任务正阻塞等待通知，
       则使其离开阻塞状态。 */
    vTaskNotifyGiveFromISR( pxUARTInstance->xTaskToNotify,
                            &xHigherPriorityTaskWoken );

    /* 现在没有任务等待通知。把 xUART 结构体的 xTaskToNotify 成员恢复为 NULL。
       这一步并非绝对必要，但有助于调试。 */
    pxUARTInstance->xTaskToNotify = NULL;
    portYIELD_FROM_ISR( xHigherPriorityTaskWoken );
}
```

***代码清单 10.11*** *在驱动库发送函数中使用任务通知的伪代码*

任务通知也可以在接收函数中替代信号量。代码清单 10.12 的伪代码给出了一个支持 RTOS、从 UART 端口接收数据的库函数框架。参见代码清单 10.12：

- `xUART_Receive()` 函数不包含互斥逻辑。如果多个任务要使用该函数，应用程序编写者必须在应用层管理互斥。例如，可以要求任务先获取互斥量，再调用 `xUART_Receive()`。

- UART 接收中断服务程序把 UART 接收到的字符放入 RAM 缓冲区，`xUART_Receive()` 函数则从该缓冲区返回字符。

- `xUART_Receive()` 的 `uxWantedBytes` 参数指定要接收的字符数。如果 RAM 缓冲区中尚无足够字符，调用任务就进入阻塞状态，等待通知缓冲区中的字符数已经增加。`while()` 循环反复执行这一过程，直到接收缓冲区包含所需数量的字符，或者发生超时。

- 调用任务可能多次进入阻塞状态，因此必须根据调用 `xUART_Receive()` 后已经过去的时间调整阻塞时间，确保函数内部花费的总时间不超过 `xUART` 结构体的 `xRxTimeout` 成员所指定的时间。阻塞时间通过 FreeRTOS 辅助函数 `vTaskSetTimeOutState()` 和 `xTaskCheckForTimeOut()` 调整。

<a name="list10.12" title="代码清单 10.12 在驱动库接收函数中使用任务通知的伪代码"></a>

```c
/* 从 UART 接收数据的驱动库函数。 */

size_t xUART_Receive( xUART *pxUARTInstance, 
                      uint8_t *pucBuffer,
                      size_t uxWantedBytes )
{
    size_t uxReceived = 0;
    TickType_t xTicksToWait;
    TimeOut_t xTimeOut;

    /* 记录进入本函数的时间。 */
    vTaskSetTimeOutState( &xTimeOut );

    /* xTicksToWait 是超时值，初始值为该 UART 实例的最长接收超时时间。 */
    xTicksToWait = pxUARTInstance->xRxTimeout;

    /* 保存调用本函数的任务句柄。正文说明了下一行是否需要临界区保护。 */
    pxUARTInstance->xTaskToNotify = xTaskGetCurrentTaskHandle();

    /* 循环，直到缓冲区包含所需数量的字节，或者发生超时。 */
    while( UART_bytes_in_rx_buffer( pxUARTInstance ) < uxWantedBytes )
    {
        /* 检查是否超时，并根据本函数目前已经花费的时间调整 xTicksToWait。 */
        if( xTaskCheckForTimeOut( &xTimeOut, &xTicksToWait ) != pdFALSE )
        {
            /* 在获得所需数量的字节前已经超时，退出循环。 */
            break;
        }

        /* 接收缓冲区中的字节数仍然不足。等待最多 xTicksToWait 个 Tick，直到
           收到通知，说明接收中断服务程序已把更多数据放入缓冲区。调用本函数
           时任务是否已有待处理通知并不重要；如果有，只会让 while 循环额外
           迭代一次。 */
        ulTaskNotifyTake( pdTRUE, xTicksToWait );
    }

    /* 没有任务在等待接收通知，因此把 xTaskToNotify 恢复为 NULL。正文说明了
       下一行是否需要临界区保护。 */
    pxUARTInstance->xTaskToNotify = NULL;

    /* 尝试从接收缓冲区读取 uxWantedBytes 个字节到 pucBuffer，并返回实际读取
       的字节数，该值可能小于 uxWantedBytes。 */
    uxReceived = UART_read_from_receive_buffer( pxUARTInstance, 
                                                pucBuffer,
                                                uxWantedBytes );
    return uxReceived;
}

/*-----------------------------------------------------------*/

/* UART 接收中断的中断服务程序。 */
void xUART_ReceiveISR( xUART *pxUARTInstance )
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* 把接收到的数据复制到该 UART 的接收缓冲区，并清除中断。 */
    UART_low_level_receive( pxUARTInstance );

    /* 如果有任务正在等待新数据通知，则立即通知它。 */
    if( pxUARTInstance->xTaskToNotify != NULL )
    {
        vTaskNotifyGiveFromISR( pxUARTInstance->xTaskToNotify,
                                &xHigherPriorityTaskWoken );
        portYIELD_FROM_ISR( xHigherPriorityTaskWoken );
    }
}
```

### 10.3.8 在外设驱动程序中使用任务通知：ADC 示例

上一节演示了如何使用 `vTaskNotifyGiveFromISR()` 从中断向任务发送通知。`vTaskNotifyGiveFromISR()` 使用简单，但功能有限：它只能发送没有附带数值的任务通知事件，不能发送数据。本节演示如何使用 `xTaskNotifyFromISR()` 随任务通知事件发送数据。代码清单 10.13 的伪代码给出了一个支持 RTOS 的模数转换器（ADC）中断服务程序框架。其中：

- 假定至少每 50 毫秒启动一次 ADC 转换。

- `ADC_ConversionEndISR()` 是 ADC 转换结束中断的服务程序，每当新的 ADC 值可用时都会执行。

- `vADCTask()` 实现的任务负责处理 ADC 生成的每个值。假定创建该任务时已经把任务句柄保存到 `xADCTaskToNotify`。

- `ADC_ConversionEndISR()` 调用 `xTaskNotifyFromISR()`，把 `eAction` 参数设为 `eSetValueWithoutOverwrite`，向 `vADCTask()` 发送任务通知，并把 ADC 转换结果写入任务的通知值。

- `vADCTask()` 使用 `xTaskNotifyWait()` 等待新 ADC 值可用的通知，并从任务通知值中取得 ADC 转换结果。

<a name="list10.13" title="代码清单 10.13 使用任务通知向任务传递数值的伪代码"></a>

```c
/* 使用 ADC 的任务。 */
void vADCTask( void *pvParameters )
{
    uint32_t ulADCValue;
    BaseType_t xResult;

    /* 触发 ADC 转换的频率。 */
    const TickType_t xADCConversionFrequency = pdMS_TO_TICKS( 50 );

    for( ;; )
    {
        /* 等待下一个 ADC 转换结果。 */
        xResult = xTaskNotifyWait(
                    /* 新 ADC 值会覆盖旧值，因此等待新通知值前无需清除任何位。 */
                    0,
                    /* 后续 ADC 值会覆盖现有值，因此退出 xTaskNotifyWait() 前
                       无需清除任何位。 */
                    0,
                    /* 用于接收任务通知值（即最新 ADC 转换结果）的变量地址。 */
                    &ulADCValue,
                    /* 每隔 xADCConversionFrequency 个 Tick 应收到一个新 ADC 值。 */
                    xADCConversionFrequency * 2 );

        if( xResult == pdPASS )
        {
            /* 收到新的 ADC 值，立即处理。 */
            ProcessADCResult( ulADCValue );
        }
        else
        {
            /* xTaskNotifyWait() 没有在预期时间内返回，可能是触发 ADC 转换的
               输入或 ADC 本身出现问题。在此处理错误。 */
        }
    }
}

/*-----------------------------------------------------------*/

/* 每次 ADC 转换完成时执行的中断服务程序。 */
void ADC_ConversionEndISR( xADC *pxADCInstance )
{
    uint32_t ulConversionResult;
    BaseType_t xHigherPriorityTaskWoken = pdFALSE, xResult;

    /* 读取新的 ADC 值并清除中断。 */
    ulConversionResult = ADC_low_level_read( pxADCInstance );

    /* 把通知和 ADC 转换结果直接发送给 vADCTask()。 */
    xResult = xTaskNotifyFromISR( xADCTaskToNotify, /* xTaskToNotify 参数 */
                                  ulConversionResult, /* ulValue 参数 */
                                  eSetValueWithoutOverwrite, /* eAction 参数。 */
                                  &xHigherPriorityTaskWoken );

    /* 如果 xTaskNotifyFromISR() 返回 pdFAIL，说明任务无法跟上 ADC 值的产生
       速度。第 12.2 节介绍 configASSERT()。 */
    configASSERT( xResult == pdPASS );
    portYIELD_FROM_ISR( xHigherPriorityTaskWoken );
}
```

### 10.3.9 在应用程序中直接使用任务通知

本节通过一个假想应用程序进一步展示任务通知的能力。该应用包含以下功能：

- 应用程序通过速度较慢的互联网连接向远程数据服务器发送数据，并从中请求数据。下文把远程数据服务器称为*云服务器*。

- 向云服务器请求数据后，请求任务必须进入阻塞状态，等待收到请求的数据。

- 向云服务器发送数据后，发送任务必须进入阻塞状态，等待云服务器确认已经正确接收数据。

图 10.6 展示了软件设计示意图。其中：

- 与云服务器建立并处理多个互联网连接的复杂逻辑被封装在单个 FreeRTOS 任务中。该任务在 FreeRTOS 应用程序内充当代理服务器，称为*服务器任务*。

- 应用任务调用 `CloudRead()` 从云服务器读取数据。`CloudRead()` 不直接与云服务器通信，而是通过队列把读取请求发送给服务器任务，再通过任务通知从服务器任务接收请求的数据。

- 应用任务调用 `CloudWrite()` 向云服务器写入数据。`CloudWrite()` 不直接与云服务器通信，而是通过队列把写入请求发送给服务器任务，再通过任务通知从服务器任务接收写操作结果。

```c
/* ulDataID 标识要读取的数据。pulValue 保存一个变量的地址，从云服务器接收
   到的数据将写入该变量。 */
BaseType_t CloudRead( uint32_t ulDataID, uint32_t *pulValue )
{
    CloudCommand_t xRequest;
    BaseType_t xReturn;

    /* 为本次读取请求正确设置 CloudCommand_t 结构体成员。 */
    xRequest.eOperation = eRead; /* 这是读取数据的请求。 */
    xRequest.ulDataID = ulDataID; /* 标识要读取数据的代码。 */
    xRequest.xTaskToNotify = xTaskGetCurrentTaskHandle(); /* 调用任务的句柄。 */

    /* 以 0 阻塞时间读取通知值，确保当前没有待处理通知，然后把结构体发送给
       服务器任务。 */
    xTaskNotifyWait( 0, 0, NULL, 0 );
    xQueueSend( xServerTaskQueue, &xRequest, portMAX_DELAY );

    /* 等待服务器任务的通知。服务器任务把从云服务器取得的值直接写入本任务
       的通知值，因此进入和退出 xTaskNotifyWait() 时都无需清除通知值中的位。
       接收值写入 *pulValue，所以把 pulValue 作为通知值的写入地址传入。 */
    xReturn = xTaskNotifyWait( 0, /* 进入时不清除任何位 */
                               0, /* 退出时不清除任何位 */
                               pulValue, /* 把通知值写入 *pulValue */
                               pdMS_TO_TICKS( 250 ) ); /* 最多等待 250ms */

    /* xReturn 为 pdPASS 表示已取得数值；为 pdFAIL 表示请求超时。 */
    return xReturn;
}
```

代码清单 10.17 给出了 `CloudWrite()` 的伪代码。为便于演示，`CloudWrite()` 返回一个按位状态码，其中每个位都有独立含义。代码清单开头的 `#define` 语句定义了四个示例状态位。

任务先清除四个状态位，再把请求发送给服务器任务，然后调用 `xTaskNotifyWait()` 进入阻塞状态等待状态通知。

<a name="list10.17" title="代码清单 10.17 CloudWrite API 函数的实现"></a>

```c
/* 云端写操作使用的状态位。 */
#define SEND_SUCCESSFUL_BIT ( 0x01 << 0 )
#define OPERATION_TIMED_OUT_BIT ( 0x01 << 1 )
#define NO_INTERNET_CONNECTION_BIT ( 0x01 << 2 )
#define CANNOT_LOCATE_CLOUD_SERVER_BIT ( 0x01 << 3 )

/* 四个状态位均置位的掩码。 */
#define CLOUD_WRITE_STATUS_BIT_MASK ( SEND_SUCCESSFUL_BIT |
                                      OPERATION_TIMED_OUT_BIT |
                                      NO_INTERNET_CONNECTION_BIT |
                                      CANNOT_LOCATE_CLOUD_SERVER_BIT )

uint32_t CloudWrite( uint32_t ulDataID, uint32_t ulDataValue )
{
    CloudCommand_t xRequest;
    uint32_t ulNotificationValue;

    /* 为本次写入请求正确设置 CloudCommand_t 结构体成员。 */
    xRequest.eOperation = eWrite; /* 这是写入数据的请求 */
    xRequest.ulDataID = ulDataID; /* 标识要写入数据的代码 */
    xRequest.ulDataValue = ulDataValue; /* 写入云服务器的数据值。 */
    xRequest.xTaskToNotify = xTaskGetCurrentTaskHandle(); /* 调用任务的句柄。 */

    /* 调用 xTaskNotifyWait()，把 ulBitsToClearOnExit 设为
       CLOUD_WRITE_STATUS_BIT_MASK、阻塞时间设为 0，清除与写操作有关的四个
       状态位。不需要当前通知值，所以 pulNotificationValue 设为 NULL。 */
    xTaskNotifyWait( 0, CLOUD_WRITE_STATUS_BIT_MASK, NULL, 0 );

    /* 把请求发送给服务器任务。 */
    xQueueSend( xServerTaskQueue, &xRequest, portMAX_DELAY );

    /* 等待服务器任务的通知。服务器任务把按位状态码写入本任务的通知值，
       再写入 ulNotificationValue。 */
    xTaskNotifyWait( 0, /* 进入时不清除任何位。 */
                     CLOUD_WRITE_STATUS_BIT_MASK, /* 退出时把相关位清零。 */
                     &ulNotificationValue, /* 通知值。 */
                     pdMS_TO_TICKS( 250 ) ); /* 最多等待 250ms。 */

    /* 把状态码返回给调用任务。 */
    return ( ulNotificationValue & CLOUD_WRITE_STATUS_BIT_MASK );
}
```
