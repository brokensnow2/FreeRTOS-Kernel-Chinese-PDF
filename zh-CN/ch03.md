# 3 堆内存管理

<a id="31-introduction"></a>
## 3.1 引言

<a id="311-prerequisites"></a>
### 3.1.1 先决条件

成为熟练的 C 语言程序员是使用 FreeRTOS 的先决条件，因此本章假设读者熟悉以下概念：

- 构建 C 项目的不同编译和链接阶段。
- 栈和堆是什么。
- 标准 C 库的 `malloc()` 和 `free()` 函数。

<a id="312-scope"></a>
### 3.1.2 范围

本章涵盖：

- FreeRTOS 何时分配 RAM。
- FreeRTOS 提供的五种示例内存分配方案。
- 选择哪种内存分配方案。

<a id="313-switching-between-static-and-dynamic-memory-allocation"></a>
### 3.1.3 静态与动态内存分配的切换

以下章节将介绍内核对象，如任务、队列、信号量和事件组。保存这些对象所需的 RAM 可以在编译时静态分配，也可以在运行时动态分配。动态分配减少了设计和规划工作，简化了 API，并最小化了 RAM 占用。静态分配更具确定性，无需处理内存分配失败，并消除了堆碎片化的风险（即堆中有足够的空闲内存，但不在一个可用的连续块中）。

使用静态分配内存创建内核对象的 FreeRTOS API 函数仅在 `configSUPPORT_STATIC_ALLOCATION` 在 FreeRTOSConfig.h 中设置为 1 时可用。使用动态分配内存创建内核对象的 FreeRTOS API 函数仅在 `configSUPPORT_DYNAMIC_ALLOCATION` 在 FreeRTOSConfig.h 中设置为 1 或未定义时可用。两个常量可以同时设置为 1。

有关 `configSUPPORT_STATIC_ALLOCATION` 的更多信息，请参见第 3.4 节 使用静态内存分配。

<a id="314-using-dynamic-memory-allocation"></a>
### 3.1.4 使用动态内存分配

动态内存分配是一个 C 编程概念，不是 FreeRTOS 或多任务处理特有的概念。它与 FreeRTOS 相关，因为内核对象可以选择使用动态分配的内存创建，而通用的 C 库函数 `malloc()` 和 `free()` 可能因以下一个或多个原因不适用：

- 它们并不总是适用于小型嵌入式系统。
- 它们的实现可能相对较大，占用宝贵的代码空间。
- 它们很少是线程安全的。
- 它们不是确定性的；执行这些函数所需的时间每次调用都会不同。
- 它们可能遭受碎片化问题（堆中有足够的空闲内存，但不在一个可用的连续块中）。
- 它们可能使链接器配置复杂化。
- 如果堆空间允许增长到被其他变量使用的内存中，它们可能成为难以调试的错误来源。

<a id="315-options-for-dynamic-memory-allocation"></a>
### 3.1.5 动态内存分配的选项

早期版本的 FreeRTOS 使用内存池分配方案，其中不同大小的内存块池在编译时预分配，然后由内存分配函数返回。尽管块分配在实时系统中很常见，但它已从 FreeRTOS 中移除，因为在非常小的嵌入式系统中，它对 RAM 的低效使用导致了大量的支持请求。

FreeRTOS 现在将内存分配视为可移植层的一部分（而不是核心代码库的一部分）。这是因为不同的嵌入式系统有不同的动态内存分配和时序要求，因此单一的动态内存分配算法只适用于一部分应用程序。此外，从核心代码库中移除动态内存分配使应用程序编写者能够在适当的时候提供自己的特定实现。

当 FreeRTOS 需要 RAM 时，它调用 `pvPortMalloc()` 而不是 `malloc()`。同样，当 FreeRTOS 释放之前分配的 RAM 时，它调用 `vPortFree()` 而不是 `free()`。`pvPortMalloc()` 具有与标准 C 库 `malloc()` 函数相同的原型，`vPortFree()` 具有与标准 C 库 `free()` 函数相同的原型。

`pvPortMalloc()` 和 `vPortFree()` 是公开函数，因此也可以从应用程序代码中调用。

FreeRTOS 附带了五个 `pvPortMalloc()` 和 `vPortFree()` 的示例实现，所有这些都在本章中记录。FreeRTOS 应用程序可以使用其中一个示例实现，或提供自己的实现。

五个示例分别在 heap\_1.c、heap\_2.c、heap\_3.c、heap\_4.c 和 heap\_5.c 源文件中定义，所有这些文件都位于 FreeRTOS/Source/portable/MemMang 目录中。

## 3.2 示例内存分配方案

<a id="321-heap1"></a>
### 3.2.1 Heap\_1

小型专用嵌入式系统通常只在启动 FreeRTOS 调度器之前创建任务和其他内核对象。在这种情况下，内存在应用程序开始执行任何实时功能之前仅由内核（动态）分配，并且该内存在应用程序的整个生命周期中保持分配状态。这意味着所选分配方案不必考虑更复杂的内存分配问题，如确定性和碎片化，而是可以优先考虑代码大小和简洁性等属性。

Heap\_1.c 实现了一个非常基本的 `pvPortMalloc()` 版本，并且不实现 `vPortFree()`。从不删除任务或其他内核对象的应用程序有可能使用 heap\_1。一些商业关键和安全关键系统通常会禁止使用动态内存分配，但也可以使用 heap\_1。关键系统通常禁止动态内存分配，因为存在与非确定性、内存碎片化和分配失败相关的不确定性。Heap\_1 始终是确定性的，并且不会导致内存碎片化。

Heap\_1 的 `pvPortMalloc()` 实现每次被调用时，只是简单地将一个名为 FreeRTOS 堆的 `uint8_t` 数组细分为更小的块。FreeRTOSConfig.h 中的常量 `configTOTAL_HEAP_SIZE` 设置数组的大小（以字节为单位）。将堆实现为静态分配的数组使得 FreeRTOS 看起来消耗了大量 RAM，因为堆成为了 FreeRTOS 数据的一部分。

每个动态分配的任务会导致两次调用 `pvPortMalloc()`。第一次分配任务控制块（TCB），第二次分配任务的栈。图 3.1 演示了 heap\_1 如何在创建任务时细分简单数组。

- **B** 显示了创建一个任务后的数组。

### 3.2.2 Heap\_2

Heap\_2 已被 heap\_4 取代，后者包含增强的功能。Heap\_2 保留在 FreeRTOS 发行版中是为了向后兼容，不建议用于新设计。

Heap\_2.c 也通过细分由 `configTOTAL_HEAP_SIZE` 常量确定大小的数组来工作。它使用最佳匹配算法分配内存，并且与 heap\_1 不同，它确实实现了 `vPortFree()`。同样，将堆实现为静态分配的数组使得 FreeRTOS 看起来消耗了大量 RAM，因为堆成为了 FreeRTOS 数据的一部分。

最佳匹配算法确保 `pvPortMalloc()` 使用与请求字节数大小最接近的空闲内存块。例如，考虑以下场景：

- 堆包含三个空闲内存块，分别为 5 字节、25 字节和 100 字节。
- `pvPortMalloc()` 请求 20 字节的 RAM。

能够容纳所请求字节数的最小空闲 RAM 块是 25 字节的块，因此 `pvPortMalloc()` 将 25 字节的块分割成一个 20 字节的块和一个 5 字节的块，然后返回指向 20 字节块的指针[^2]。新的 5 字节块仍可用于将来的 `pvPortMalloc()` 调用。

[^2]: 这是一个过度简化，因为 heap\_2 在堆区域内存储块大小的信息，因此两个分割块的总和实际上将小于 25。

与 heap\_4 不同，heap\_2 不会将相邻的空闲块合并成一个更大的块，因此它比 heap\_4 更容易受到碎片化的影响。然而，如果分配和随后释放的块始终是相同的大小，则碎片化不是问题。

图 3.2 演示了在创建、删除和再次创建任务时最佳匹配算法的工作方式。参考图 3.2：

- **A** 显示了分配三个任务后的数组。数组顶部保留了一个大的空闲块。

- **B** 显示了删除其中一个任务后的数组。数组顶部的大空闲块仍然存在。现在还有两个较小的空闲块，它们之前保存了被删除任务的 TCB 和栈。

- **C** 显示了创建另一个任务后的情况。创建任务导致了从 `xTaskCreate()` API 函数内部两次调用 `pvPortMalloc()`，一次分配新的 TCB，另一次分配任务栈。本书第 3.4 节描述了 `xTaskCreate()`。

  每个 TCB 的大小相同，因此最佳匹配算法重用之前保存被删除任务 TCB 的 RAM 块来保存创建任务的 TCB。

  如果分配给新创建任务的栈大小与分配给之前删除任务的栈大小相同，则最佳匹配算法重用之前保存被删除任务栈的 RAM 块来保存创建任务的栈。

  数组顶部较大的未分配块保持不变。

Heap\_2 不是确定性的，但比大多数标准库实现的 `malloc()` 和 `free()` 更快。


<a id="323-heap3"></a>
### 3.2.3 Heap\_3

Heap\_3.c 使用标准库的 `malloc()` 和 `free()` 函数，因此链接器配置定义堆大小，而不使用 `configTOTAL_HEAP_SIZE` 常量。

Heap\_3 通过在执行期间临时挂起 FreeRTOS 调度器来使 `malloc()` 和 `free()` 成为线程安全的。第 8 章 资源管理涵盖了线程安全和调度器挂起。


<a id="324-heap4"></a>
### 3.2.4 Heap\_4

与 heap\_1 和 heap\_2 一样，heap\_4 通过将数组细分为更小的块来工作。和之前一样，该数组是静态分配的，并由 `configTOTAL_HEAP_SIZE` 确定大小，这使得 FreeRTOS 看起来使用了大量 RAM，因为堆成为了 FreeRTOS 数据的一部分。

Heap\_4 使用首次适应算法分配内存。与 heap\_2 不同，heap\_4 将相邻的空闲内存块合并（结合）成一个更大的块，从而最小化内存碎片化的风险。

首次适应算法确保 `pvPortMalloc()` 使用第一个足够大以容纳所请求字节数的空闲内存块。例如，考虑以下场景：

- 堆包含三个空闲内存块，按照它们在数组中出现的顺序，分别为 5 字节、200 字节和 100 字节。
- `pvPortMalloc()` 请求 20 字节的 RAM。

能够容纳所请求字节数的第一个空闲 RAM 块是 200 字节的块，因此 `pvPortMalloc()` 将 200 字节的块分割成一个 20 字节的块和一个 180 字节的块[^3]，然后返回指向 20 字节块的指针。新的 180 字节块仍可用于将来的 `pvPortMalloc()` 调用。

[^3]: 这是一个过度简化，因为 heap\_4 在堆区域内存储块大小的信息，因此两个分割块的总和实际上将小于 200 字节。

Heap\_4 将相邻的空闲块合并（结合）成一个更大的块，最小化碎片化的风险，使其适用于重复分配和释放不同大小 RAM 块的应用程序。

- **A** 显示了创建三个任务后的数组。数组顶部保留了一个大的空闲块。

Heap\_4 不是确定性的，但比大多数标准库实现的 `malloc()` 和 `free()` 更快。


<a id="325-heap5"></a>
### 3.2.5 Heap\_5

Heap\_5 使用与 heap\_4 相同的分配算法。与 heap\_4 不同，heap\_4 仅限于从单个数组分配内存，而 heap\_5 可以将来自多个分离内存空间的内存组合成单个堆。当运行 FreeRTOS 的系统提供的 RAM 在系统内存映射中不作为单个连续（无间隔）块出现时，Heap\_5 非常有用。


<a id="326-initialising-heap5-the-vportdefineheapregions-api-function"></a>
### 3.2.6 初始化 heap\_5：vPortDefineHeapRegions() API 函数

`vPortDefineHeapRegions()` 通过指定构成 heap\_5 管理的堆的每个独立内存区域的起始地址和大小来初始化 heap\_5。Heap\_5 是唯一需要显式初始化且在调用 `vPortDefineHeapRegions()` 之后才能使用的堆分配方案。这意味着内核对象，如任务、队列和信号量，不能在调用 `vPortDefineHeapRegions()` 之前动态创建。


<a name="list3.1" title="代码清单 3.1 vPortDefineHeapRegions() API 函数原型"></a>


```c
void vPortDefineHeapRegions( const HeapRegion_t * const pxHeapRegions );
```
***代码清单 3.1*** *vPortDefineHeapRegions() API 函数原型*


`vPortDefineHeapRegions()` 将 `HeapRegion_t` 结构数组作为其唯一参数。每个结构定义将成为堆一部分的内存块的起始地址和大小——整个结构数组定义了整个堆空间。


<a name="list3.2" title="代码清单 3.2 HeapRegion\_t 结构"></a>


```c
typedef struct HeapRegion
{
    /* 将成为堆一部分的内存块的起始地址。*/
    uint8_t *pucStartAddress;

    /* 内存块的大小（以字节为单位）。 */
    size_t xSizeInBytes;

} HeapRegion_t;
```
***代码清单 3.2*** *HeapRegion\_t 结构*


**参数：**

- `pxHeapRegions`

  指向 `HeapRegion_t` 结构数组起始位置的指针。每个结构定义将成为堆一部分的内存块的起始地址和大小。

  数组中的 `HeapRegion_t` 结构必须按起始地址排序；描述具有最低起始地址的内存区域的 `HeapRegion_t` 结构必须是数组中的第一个结构，描述具有最高起始地址的内存区域的 `HeapRegion_t` 结构必须是数组中的最后一个结构。
  
  使用 `pucStartAddress` 成员设置为 `NULL` 的 `HeapRegion_t` 结构标记数组的结束。

举例说明，考虑图 3.4 **A** 中所示的假设内存映射，其中包含三个独立的 RAM 块：RAM1、RAM2 和 RAM3。假设可执行代码放在只读存储器中，图中未显示。

<a name="list3.3" title="代码清单 3.3 一个 HeapRegion\_t 结构数组，共同完整描述 3 个 RAM 区域"></a>


```c
/* 定义三个 RAM 区域的起始地址和大小。 */
#define RAM1_START_ADDRESS ( ( uint8_t * ) 0x00010000 )
#define RAM1_SIZE ( 64 * 1024 )

#define RAM2_START_ADDRESS ( ( uint8_t * ) 0x00020000 )
#define RAM2_SIZE ( 32 * 1024 )

#define RAM3_START_ADDRESS ( ( uint8_t * ) 0x00030000 )
#define RAM3_SIZE ( 32 * 1024 )

/* 创建一个 HeapRegion_t 定义数组，为三个 RAM 区域各有一个索引，
   并以包含 NULL 地址的 HeapRegion_t 结构终止数组。HeapRegion_t 结构必须
   按起始地址顺序出现，包含最低起始地址的结构最先出现。 */
const HeapRegion_t xHeapRegions[] =
{
    { RAM1_START_ADDRESS, RAM1_SIZE },
    { RAM2_START_ADDRESS, RAM2_SIZE },
    { RAM3_START_ADDRESS, RAM3_SIZE },
    { NULL,               0         } /* 标记数组的结束。 */
};

int main( void )
{
    /* 初始化 heap_5。 */
    vPortDefineHeapRegions( xHeapRegions );

    /* 在此处添加应用程序代码。 */
}
```
***代码清单 3.3*** *一个 HeapRegion\_t 结构数组，共同完整描述 3 个 RAM 区域*


尽管代码清单 3.3 正确地描述了 RAM，但它并没有演示一个可用的示例，因为它将所有 RAM 分配给了堆，没有留下任何 RAM 供其他变量使用。

构建过程的链接阶段为每个变量分配一个 RAM 地址。链接器可用的 RAM 通常由链接器配置文件（如链接器脚本）描述。在图 3.4 **B** 中，假设链接器脚本包含了 RAM1 的信息，但没有包含 RAM2 或 RAM3 的信息。因此，链接器将变量放置在 RAM1 中，只留下 RAM1 中地址 0x0001nnnn 以上的部分可供 heap\_5 使用。0x0001nnnn 的实际值取决于应用程序中包含的所有变量的总大小。链接器没有使用 RAM2 和 RAM3 的全部空间，因此整个 RAM2 和整个 RAM3 都可供 heap\_5 使用。

代码清单 3.3 中显示的代码会导致 heap\_5 分配在地址 0x0001nnnn 以下的 RAM 与用于保存变量的 RAM 重叠。如果您将 `xHeapRegions[]` 数组中第一个 `HeapRegion_t` 结构的起始地址设置为 0x0001nnnn，而不是起始地址 0x00010000，则堆不会与链接器使用的 RAM 重叠。但是，这不是推荐的解决方案，因为：

- 起始地址可能不容易确定。
- 链接器使用的 RAM 量可能在将来的构建中发生变化，这将需要更新 `HeapRegion_t` 结构中使用的起始地址。
- 构建工具将不知道（因此无法警告）链接器使用的 RAM 和 heap\_5 使用的 RAM 是否重叠。

代码清单 3.4 演示了一个更方便和可维护的示例。它声明了一个名为 `ucHeap` 的数组。`ucHeap` 是一个普通变量，因此它成为链接器分配给 RAM1 的数据的一部分。`xHeapRegions` 数组中的第一个 `HeapRegion_t` 结构描述了 `ucHeap` 的起始地址和大小，因此 `ucHeap` 成为 heap\_5 管理的内存的一部分。`ucHeap` 的大小可以增加，直到链接器使用的 RAM 消耗完所有 RAM1，如图 3.4 **C** 所示。


<a name="list3.4" title="代码清单 3.4 一个 HeapRegion\_t 结构数组，描述所有 RAM2、所有 RAM3，但仅部分 RAM1"></a>

```c
/* 定义链接器未使用的两个 RAM 区域的起始地址和大小。 */
#define RAM2_START_ADDRESS ( ( uint8_t * ) 0x00020000 )
#define RAM2_SIZE ( 32 * 1024 )

#define RAM3_START_ADDRESS ( ( uint8_t * ) 0x00030000 )
#define RAM3_SIZE ( 32 * 1024 )

/* 声明一个将成为 heap_5 使用的堆的一部分的数组。该数组将由链接器放置在 RAM1 中。 */
#define RAM1_HEAP_SIZE ( 30 * 1024 )
static uint8_t ucHeap[ RAM1_HEAP_SIZE ];

/* 创建一个 HeapRegion_t 定义数组。在代码清单 3.3 中，第一个条目描述了整个 RAM1，
   因此 heap_5 将使用整个 RAM1，而这次第一个条目只描述了 ucHeap 数组，因此
   heap_5 只会使用 RAM1 中包含 ucHeap 数组的部分。HeapRegion_t 结构仍然必须按
   起始地址顺序出现，包含最低起始地址的结构最先出现。 */

const HeapRegion_t xHeapRegions[] =
{
    { ucHeap,             RAM1_HEAP_SIZE },
    { RAM2_START_ADDRESS, RAM2_SIZE },
    { RAM3_START_ADDRESS, RAM3_SIZE },
    { NULL,               0 }           /* 标记数组的结束。 */
};
```
***代码清单 3.4*** *一个 HeapRegion\_t 结构数组，描述所有 RAM2、所有 RAM3，但仅部分 RAM1*


代码清单 3.4 中演示的技术的优点包括：

- 不需要使用硬编码的起始地址。
- `HeapRegion_t` 结构中使用的地址将由链接器自动设置，因此即使在将来的构建中链接器使用的 RAM 量发生变化，它也始终保持正确。
- heap\_5 分配的 RAM 不可能与链接器放入 RAM1 的数据重叠。
- 如果 `ucHeap` 太大，应用程序将无法链接。

### 3.3.1 定义堆起始地址

Heap\_1、heap\_2 和 heap\_4 从由 `configTOTAL_HEAP_SIZE` 确定大小的静态分配数组中分配内存。本节将这些分配方案统称为 heap\_n。

有时需要将堆放置在特定的内存地址。例如，动态创建的任务的栈来自堆，因此可能需要将堆定位在快速的内部存储器中，而不是慢速的外部存储器中。（请参见下面的子章节 将任务栈放置在快速内存中，了解在快速内存中分配任务栈的另一种方法）。`configAPPLICATION_ALLOCATED_HEAP` 编译时常量使应用程序能够声明数组，取代原本在 heap\_n.c 源文件中的声明。在应用程序代码中声明数组使应用程序编写者能够指定其起始地址。

如果在 FreeRTOSConfig.h 中将 `configAPPLICATION_ALLOCATED_HEAP` 设置为 1，则使用 FreeRTOS 的应用程序必须分配一个名为 `ucHeap` 且由 `configTOTAL_HEAP_SIZE` 常量确定大小的 `uint8_t` 数组。

将变量放置在特定内存地址所需的语法取决于所使用的编译器，因此请参考编译器的文档。以下是两个编译器的示例：

- 代码清单 3.5 显示了 GCC 编译器声明数组并将数组放置在名为 `.my_heap` 的内存段中所需的语法。
- 代码清单 3.6 显示了 IAR 编译器声明数组并将数组放置在绝对内存地址 0x20000000 所需的语法。

### 3.3.3 xPortGetMinimumEverFreeHeapSize() API 函数

`xPortGetMinimumEverFreeHeapSize()` API 函数返回自 FreeRTOS 应用程序开始执行以来，堆中曾存在过的未分配字节的最小数量。

`xPortGetMinimumEverFreeHeapSize()` 返回的值指示应用程序曾经有多接近耗尽堆空间。例如，如果 `xPortGetMinimumEverFreeHeapSize()` 返回 200，则自应用程序开始执行以来的某个时间，它离耗尽堆空间只差 200 字节。

`xPortGetMinimumEverFreeHeapSize()` 也可用于优化堆大小。例如，如果在执行您知道具有最高堆使用率的代码后，`xPortGetMinimumEverFreeHeapSize()` 返回 2000，则 `configTOTAL_HEAP_SIZE` 可以减少最多 2000 字节。

`xPortGetMinimumEverFreeHeapSize()` 仅在 heap\_4 和 heap\_5 中实现。

### 3.3.6 Malloc 失败钩子函数

与标准库的 `malloc()` 函数一样，如果 `pvPortMalloc()` 无法分配所请求的 RAM 量，则返回 NULL。malloc 失败钩子（或回调）是一个应用程序提供的函数，在 `pvPortMalloc()` 返回 NULL 时被调用。您必须在 FreeRTOSConfig.h 中将 `configUSE_MALLOC_FAILED_HOOK` 设置为 1 才能使回调发生。如果在使用动态内存分配创建内核对象的 FreeRTOS API 函数内部调用了 malloc 失败钩子，则该对象不会被创建。

如果 `configUSE_MALLOC_FAILED_HOOK` 在 FreeRTOSConfig.h 中设置为 1，则应用程序必须提供一个具有代码清单 3.11 所示名称和原型的 malloc 失败钩子函数。应用程序可以以适合应用程序的任何方式实现该函数。许多提供的 FreeRTOS 演示应用程序将分配失败视为致命错误，但对于生产系统来说这不是最佳实践，生产系统应从分配失败中优雅地恢复。

<a id="34-using-static-memory-allocation"></a>
## 3.4 使用静态内存分配

第 3.1.4 节列出了动态内存分配带来的一些缺点。为了避免这些问题，静态内存分配允许开发人员显式创建应用程序所需的每个内存块。这具有以下优点：

- 所有所需的内存在编译时已知。
- 所有内存都是确定性的。

还有其他优点，但这些优点也带来了一些复杂性。主要的复杂性是增加了一些额外的用户函数来管理一些内核内存，第二个复杂性是需要确保所有静态内存在合适的作用域中声明。


<a id="341-enabling-static-memory-allocation"></a>
### 3.4.1 启用静态内存分配

静态内存分配通过在 FreeRTOSConfig.h 中将 `configSUPPORT_STATIC_ALLOCATION` 设置为 1 来启用。启用此配置后，内核会启用所有内核函数的 `static` 版本。这些函数包括：

- `xTaskCreateStatic`
- `xEventGroupCreateStatic`
- `xEventGroupGetStaticBuffer`
- `xQueueGenericCreateStatic`
- `xQueueGenericGetStaticBuffers`
- `xQueueCreateMutexStatic`
  - *如果 `configUSE_MUTEXES` 为 1*
- `xQueueCreateCountingSemaphoreStatic`
  - *如果 `configUSE_COUNTING_SEMAPHORES` 为 1*
- `xStreamBufferGenericCreateStatic`
- `xStreamBufferGetStaticBuffers`
- `xTimerCreateStatic`
  - *如果 `configUSE_TIMERS` 为 1*
- `xTimerGetStaticBuffer`
  - *如果 `configUSE_TIMERS` 为 1*

这些函数将在本书的相应章节中解释。

<a id="342-static-internal-kernel-memory"></a>
### 3.4.2 静态内部内核内存

当启用静态内存分配器时，空闲任务和定时器任务（如果启用）将使用用户函数提供的静态内存。这些用户函数是：

- `vApplicationGetTimerTaskMemory`
  - *如果 `configUSE_TIMERS` 为 1*
- `vApplicationGetIdleTaskMemory`


<a id="3421-vapplicationgettimertaskmemory"></a>
#### 3.4.2.1 vApplicationGetTimerTaskMemory

如果同时启用了 `configSUPPORT_STATIC_ALLOCATION` 和 `configUSE_TIMERS`，内核将调用 `vApplicationGetTimerTaskMemory()` 以允许应用程序创建并返回用于定时器任务 TCB 和定时器任务栈的内存缓冲区。该函数还将返回定时器任务栈的大小。代码清单 3.13 显示了定时器任务内存函数的一个建议实现。


<a name="list3.13" title="代码清单 3.13 vApplicationGetTimerTaskMemory 的典型实现"></a>


```c
void vApplicationGetTimerTaskMemory( StaticTask_t **ppxTimerTaskTCBBuffer,
                                     StackType_t **ppxTimerTaskStackBuffer,
                                     uint32_t *pulTimerTaskStackSize )
{
  /* 如果要提供给定时器任务的缓冲区在此函数内部声明，则必须声明为 static -
  否则它们将在栈上分配，因此在退出此函数后将不存在。 */
  static StaticTask_t xTimerTaskTCB;
  static StackType_t uxTimerTaskStack[ configMINIMAL_STACK_SIZE ];

  /* 传递指向 StaticTask_t 结构的指针，定时器任务的状态将存储在该结构中。 */
  *ppxTimerTaskTCBBuffer = &xTimerTaskTCB;

  /* 传递将用作定时器任务栈的数组。 */
  *ppxTimerTaskStackBuffer = uxTimerTaskStack;

  /* 传递 *ppxTimerTaskStackBuffer 所指向数组的栈大小。
  注意栈大小是 StackType_t 的计数。 */
  *pulTimerTaskStackSize = sizeof(uxTimerTaskStack) / sizeof(*uxTimerTaskStack);
}
```
***代码清单 3.13*** *vApplicationGetTimerTaskMemory 的典型实现*
