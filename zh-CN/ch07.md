# 7 中断管理

<a id="71-introduction"></a>
## 7.1 引言

<a id="711-events"></a>
### 7.1.1 事件

嵌入式实时系统需要响应源自环境的事件。例如，以太网外设上到达的数据包（事件）可能需要将其传递给 TCP/IP 协议栈进行处理（操作）。非平凡系统必须服务于源自多个来源的事件，所有这些事件都有不同的处理开销和响应时间要求。每种情况都需要判断最佳的事件处理实现策略：

- 如何检测事件？通常使用中断，但输入也可以轮询。

- 使用中断时，多少处理应在中断服务例程（ISR）内部执行，多少应在外部执行？通常希望每个 ISR 尽可能短。

- 事件如何传递给主（非 ISR）代码，以及如何构建此代码以最佳方式处理潜在的异步发生？

FreeRTOS 不对应用程序设计者强加任何特定的事件处理策略，但确实提供了允许以简单且可维护的方式实现所选策略的特性。

区分任务优先级和中断优先级非常重要：

- 任务是一种软件特性，与运行 FreeRTOS 的硬件无关。任务的优先级由应用程序编写者在软件中分配，软件算法（调度器）决定哪个任务将进入运行态。

- 虽然用软件编写，但中断服务例程是一种硬件特性，因为硬件控制哪个中断服务例程将运行以及何时运行。任务只有在没有 ISR 运行时才会运行，因此最低优先级的中断也会中断最高优先级的任务，任务无法抢占 ISR。

所有可以运行 FreeRTOS 的架构都能够处理中断，但与中断进入和中断优先级分配相关的细节因架构而异。

<a id="712-scope"></a>
### 7.1.2 范围

本章涵盖：

- 哪些 FreeRTOS API 函数可以在中断服务例程中使用。
- 将中断处理推迟到任务的方法。

<a id="72-using-the-freertos-api-from-an-isr"></a>
## 7.2 从 ISR 中使用 FreeRTOS API

<a id="721-the-interrupt-safe-api"></a>
### 7.2.1 中断安全 API

通常需要在中断服务例程（ISR）中使用 FreeRTOS API 函数提供的功能，但许多 FreeRTOS API 函数执行的操在 ISR 内是无效的。最值得注意的是将调用 API 函数的任务放入阻塞态——如果从 ISR 调用 API 函数，则不是从任务调用的，因此没有可放入阻塞态的调用任务。FreeRTOS 通过提供某些 API 函数的两个版本来解决此问题；一个版本供任务使用，一个版本供 ISR 使用。用于 ISR 的函数在其名称后附加了"FromISR"。

> *注意：切勿从 ISR 调用名称中不包含"FromISR"的 FreeRTOS API 函数。*

<a id="722-the-benefits-of-using-a-separate-interrupt-safe-api"></a>
### 7.2.2 使用单独的中断安全 API 的好处

拥有单独的中断 API 可以使任务代码更高效、ISR 代码更高效，并使中断进入更简单。要理解原因，请考虑另一种解决方案：提供每个 API 函数的单一版本，既可以从任务调用，也可以从 ISR 调用。如果同一版本的 API 函数可以从任务和 ISR 调用，那么：

- API 函数需要额外的逻辑来确定它们是从任务还是 ISR 调用的。额外的逻辑将引入新的函数路径，使函数更长、更复杂、更难测试。

- 某些 API 函数参数在从任务调用时会变得多余，而其他参数在从 ISR 调用时会变得多余。

- 每个 FreeRTOS 端口都需要提供一种机制来确定执行上下文（任务或 ISR）。

- 在难以确定执行上下文（任务或 ISR）的架构上，将需要额外的、浪费的、更复杂使用且非标准的中断进入代码，以允许通过软件提供执行上下文。

<a id="723-the-disadvantages-of-using-a-separate-interrupt-safe-api"></a>
### 7.2.3 使用单独的中断安全 API 的缺点

拥有某些 API 函数的两个版本使任务和 ISR 都能更高效，但引入了一个新问题；有时需要从任务和 ISR 调用不属于 FreeRTOS API 但使用了 FreeRTOS API 的函数。

这通常只在集成第三方代码时成为问题，因为那是应用程序编写者无法控制软件设计的唯一时刻。如果这确实成为问题，可以通过以下技术之一来解决：

- 将中断处理推迟到任务[^12]，以便 API 函数仅在任务上下文中被调用。

- 如果您使用的是支持中断嵌套的 FreeRTOS 端口，则使用以"FromISR"结尾的 API 函数版本，因为该版本可以从任务和 ISR 调用。（反之则不成立，不以"FromISR"结尾的 API 函数不得从 ISR 调用。）

- 第三方代码通常包含一个 RTOS 抽象层，可以实现该抽象层来测试调用函数的上下文（任务或中断），然后调用适合该上下文的 API 函数。

[^12]: 推迟中断处理将在本书的下一节中介绍。

<a id="724-the-xhigherprioritytaskwoken-parameter"></a>
### 7.2.4 xHigherPriorityTaskWoken 参数

本节介绍 `xHigherPriorityTaskWoken` 参数的概念。如果您尚未完全理解本节，请不要担心，后续章节将提供实际示例。

如果中断执行了上下文切换，那么中断退出时运行的任务可能与进入中断时运行的任务不同——中断中断了一个任务，但返回到另一个任务。

某些 FreeRTOS API 函数可以将任务从阻塞态移动到就绪态。这在诸如 `xQueueSendToBack()` 等函数中已经看到，如果有任务在阻塞态等待数据在相关队列上可用，该函数将解除阻塞该任务。

如果被 FreeRTOS API 函数解除阻塞的任务的优先级高于运行态任务的优先级，那么根据 FreeRTOS 调度策略，应切换到更高优先级的任务。切换到更高优先级任务的实际发生时间取决于调用 API 函数的上下文：

- 如果从任务调用 API 函数：

  如果 FreeRTOSConfig.h 中的 `configUSE_PREEMPTION` 设置为 1，则切换到更高优先级任务会在 API 函数内部自动发生，换句话说，在 API 函数退出之前。这在图 6.6 中已经看到，对定时器命令队列的写入导致在写入命令队列的函数退出之前切换到 RTOS 守护任务。

- 如果从中断调用 API 函数：

  切换到更高优先级任务不会在中断内部自动发生。相反，会设置一个变量来通知应用程序编写者应执行上下文切换。中断安全 API 函数（以"FromISR"结尾的函数）有一个名为 `pxHigherPriorityTaskWoken` 的指针参数用于此目的。

  如果应执行上下文切换，则中断安全 API 函数会将 `*pxHigherPriorityTaskWoken` 设置为 `pdTRUE`。为了能够检测到这种情况，`pxHigherPriorityTaskWoken` 指向的变量必须在首次使用前初始化为 `pdFALSE`。

  如果应用程序编写者选择不从 ISR 请求上下文切换，则更高优先级的任务将保持在就绪态，直到下次调度器运行，在最坏情况下将在下一次 tick 中断期间。

  FreeRTOS API 函数只能将 `*pxHigherPriorityTaskWoken` 设置为 `pdTRUE`。如果 ISR 调用多个 FreeRTOS API 函数，则可以将同一个变量作为每个 API 函数调用的 `pxHigherPriorityTaskWoken` 参数传递，并且该变量只需在首次使用前初始化为 `pdFALSE`。

上下文切换不在中断安全版本的 API 函数内部自动发生有几个原因：

- 避免不必要的上下文切换

  中断可能在任务需要执行任何处理之前执行多次。例如，考虑一个任务处理由中断驱动的 UART 接收到的字符串的场景；每次接收到一个字符就切换到该任务会很浪费，因为任务只有在接收到完整字符串后才需要进行处理。

- 控制执行顺序

  中断可能偶尔发生，且发生在不可预测的时间。专家级 FreeRTOS 用户可能希望在应用程序的特定点暂时避免不可预测地切换到不同任务，尽管这也可以使用 FreeRTOS 调度器锁定机制来实现。

- 可移植性

  这是可以在所有 FreeRTOS 端口上使用的最简单机制。

- 效率

  针对较小处理器架构的端口只允许在 ISR 的最末尾请求上下文切换，取消该限制将需要额外且更复杂的代码。它还允许在同一 ISR 内多次调用 FreeRTOS API 函数，而不会在同一 ISR 内生成多个上下文切换请求。

- 在 RTOS tick 中断中执行

  正如本书后面将看到的，可以将应用程序代码添加到 RTOS tick 中断中。在 tick 中断内尝试上下文切换的结果取决于所使用的 FreeRTOS 端口。最好情况下，它会导致对调度器的不必要调用。

`pxHigherPriorityTaskWoken` 参数的使用是可选的。如果不需要，则将 `pxHigherPriorityTaskWoken` 设置为 NULL。

<a id="725-the-portyieldfromisr-and-portendswitchingisr-macros"></a>
### 7.2.5 portYIELD_FROM_ISR() 和 portEND_SWITCHING_ISR() 宏

本节介绍用于从 ISR 请求上下文切换的宏。如果您尚未完全理解本节，请不要担心，后续章节将提供实际示例。

`taskYIELD()` 是一个可以在任务中调用以请求上下文切换的宏。`portYIELD_FROM_ISR()` 和 `portEND_SWITCHING_ISR()` 都是 `taskYIELD()` 的中断安全版本。`portYIELD_FROM_ISR()` 和 `portEND_SWITCHING_ISR()` 的使用方式相同，并且执行相同的操作[^13]。某些 FreeRTOS 端口只提供这两个宏之一。较新的 FreeRTOS 端口同时提供这两个宏。本书中的示例使用 `portYIELD_FROM_ISR()`。

[^13]: 历史上，`portEND_SWITCHING_ISR()` 是要求中断处理程序使用汇编代码包装的 FreeRTOS 端口中使用的名称，而 `portYIELD_FROM_ISR()` 是允许整个中断处理程序用 C 编写的 FreeRTOS 端口中使用的名称。

<a name="list7.1" title="Listing 7.1 The portEND\_SWITCHING\_ISR() macros"></a>

```c
portEND_SWITCHING_ISR( xHigherPriorityTaskWoken );
```
***Listing 7.1*** *The portEND\_SWITCHING\_ISR() macros*

<a name="list7.2" title="Listing 7.2 The portYIELD\_FROM\_ISR() macros"></a>

```c
portYIELD_FROM_ISR( xHigherPriorityTaskWoken );
```
***Listing 7.2*** *The portYIELD\_FROM\_ISR() macros*

从中断安全 API 函数传出的 `xHigherPriorityTaskWoken` 参数可以直接用作调用 `portYIELD_FROM_ISR()` 时的参数。

如果 `portYIELD_FROM_ISR()` 的 `xHigherPriorityTaskWoken` 参数是 `pdFALSE`（零），则不请求上下文切换，宏不产生任何效果。如果 `portYIELD_FROM_ISR()` 的 `xHigherPriorityTaskWoken` 参数不是 `pdFALSE`，则请求上下文切换，运行态的任务可能会改变。中断将始终返回到运行态的任务，即使运行态的任务在中断执行期间已更改。

大多数 FreeRTOS 端口允许在 ISR 内的任何位置调用 `portYIELD_FROM_ISR()`。少数 FreeRTOS 端口（主要是针对较小架构的端口）只允许在 ISR 的最末尾调用 `portYIELD_FROM_ISR()`。

<a id="73-deferred-interrupt-processing"></a>
## 7.3 推迟中断处理

通常认为最佳实践是保持 ISR 尽可能短。原因包括：

- 即使任务已被分配非常高的优先级，它们也只有在硬件没有服务任何中断时才会运行。

- ISR 可能会干扰（增加"抖动"）任务的开始时间和执行时间。

- 根据运行 FreeRTOS 的架构，在执行 ISR 时可能无法接受任何新中断，或至少是部分新中断。

- 应用程序编写者需要考虑并防范任务和 ISR 同时访问变量、外设和内存缓冲区等资源带来的后果。

- 某些 FreeRTOS 端口允许中断嵌套，但中断嵌套会增加复杂性并降低可预测性。中断越短，嵌套的可能性就越小。

中断服务例程必须记录中断的原因并清除中断。中断所需的任何其他处理通常可以在任务中执行，从而使中断服务例程尽可能快地退出。这称为"推迟中断处理"，因为中断所需的处理从 ISR"推迟"到任务。

将中断处理推迟到任务还允许应用程序编写者相对于应用程序中的其他任务对处理进行优先级排序，并使用所有 FreeRTOS API 函数。

如果中断处理被推迟到的任务的优先级高于任何其他任务，则该处理将立即执行，就像处理是在 ISR 本身中执行的一样。此场景如图 7.1 所示，其中任务 1 是普通的应用程序任务，任务 2 是中断处理被推迟到的任务。

关于何时最好在 ISR 中执行中断所需的全部处理，以及何时最好将部分处理推迟到任务，没有绝对的规则。将处理推迟到任务在以下情况最有用：

- 中断所需的处理不是微不足道的。例如，如果中断只是存储模数转换的结果，那么几乎可以肯定最好在 ISR 内部执行，但如果转换结果还必须通过软件滤波器，则最好在任务中执行滤波器。

- 方便中断处理执行无法在 ISR 内执行的操作，例如写入控制台或分配内存。

- 中断处理不是确定性的——意味着无法事先知道处理需要多长时间。

## 7.4 用于同步的二值信号量

二值信号量的中断安全版本可用于在每次特定中断发生时解除阻塞一个任务，从而有效地将任务与中断同步。这允许在同步任务中实现大部分中断事件处理，只有非常快速和简短的部分保留在 ISR 中。如前一节所述，二值信号量用于将中断处理"推迟"到任务[^14]。

[^14]: 使用直接任务通知从中断解除阻塞任务比使用二值信号量更高效。直接任务通知将在第 10 章"任务通知"中介绍。

如图 7.1 之前所示，如果中断处理特别时间紧迫，则可以将推迟处理任务的优先级设置为确保该任务始终抢占系统中的其他任务。然后可以实现在 ISR 中包含对 `portYIELD_FROM_ISR()` 的调用，确保 ISR 直接返回到中断处理被推迟到的任务。这具有确保整个事件处理在时间上连续（不间断）执行的效果，就像全部在 ISR 本身中实现一样。图 7.2 重复了图 7.1 中所示的场景，但更新了文本来描述如何使用信号量控制推迟处理任务的执行。

推迟处理任务使用信号量的阻塞"获取"调用作为进入阻塞态等待事件发生的手段。当事件发生时，ISR 对同一信号量执行"给出"操作以解除阻塞任务，以便所需的事件处理可以继续进行。

"获取信号量"和"给出信号量"是根据使用场景具有不同含义的概念。在此中断同步场景中，二值信号量在概念上可以视为长度为 1 的队列。该队列在任何时候最多只能包含一个项目，因此总是为空或已满（因此称为二值）。通过调用 `xSemaphoreTake()`，中断处理被推迟到的任务有效地尝试从队列中读取数据并带有阻塞时间，如果队列为空，则导致任务进入阻塞态。当事件发生时，ISR 使用 `xSemaphoreGiveFromISR()` 函数将一个令牌（信号量）放入队列，使队列变满。这导致任务退出阻塞态并移除令牌，使队列再次为空。当任务完成其处理后，它再次尝试从队列中读取数据，发现队列为空，则重新进入阻塞态以等待下一个事件。此序列在图 7.3 中演示。

图 7.3 显示了中断"给出"信号量，即使它之前没有"获取"它，而任务"获取"信号量，但从不归还它。这就是为什么该场景被描述为在概念上类似于对队列的写入和读取。这经常引起混淆，因为它不遵循其他信号量使用场景的规则，在这些场景中，获取信号量的任务必须总是归还它——例如第 8 章"资源管理"中描述的场景。

### 7.4.1 xSemaphoreCreateBinary() API 函数

FreeRTOS 还包括 `xSemaphoreCreateBinaryStatic()` 函数，它在编译时静态分配创建二值信号量所需的内存：所有各种类型的 FreeRTOS 信号量的句柄都存储在 `SemaphoreHandle_t` 类型的变量中。

在使用信号量之前，必须先创建它。要创建二值信号量，请使用 `xSemaphoreCreateBinary()` API 函数[^15]。

[^15]: 某些信号量 API 函数实际上是宏，而不是函数。为简单起见，本书中统称为函数。

<a name="list7.3" title="Listing 7.3 The xSemaphoreCreateBinary() API function prototype"></a>

```c
SemaphoreHandle_t xSemaphoreCreateBinary( void );
```
***Listing 7.3*** *The xSemaphoreCreateBinary() API function prototype*

**xSemaphoreCreateBinary() 返回值**

- 返回值

  如果返回 NULL，则无法创建信号量，因为没有足够的堆内存可供 FreeRTOS 分配信号量数据结构。

  如果返回非 NULL 值，则表示信号量已成功创建。返回的值应存储为所创建信号量的句柄。

<a id="742-the-xsemaphoretake-api-function"></a>
### 7.4.2 xSemaphoreTake() API 函数

"获取"信号量意味着"获得"或"接收"信号量。只有在信号量可用时才能获取。

所有各种类型的 FreeRTOS 信号量，除了递归互斥量，都可以使用 `xSemaphoreTake()` 函数"获取"。

`xSemaphoreTake()` 不得从中断服务例程中使用。

<a name="list7.4" title="Listing 7.4 The xSemaphoreTake() API function prototype"></a>

```c
BaseType_t xSemaphoreTake( SemaphoreHandle_t xSemaphore, TickType_t xTicksToWait );
```
***Listing 7.4*** *The xSemaphoreTake() API function prototype*

**xSemaphoreTake() 参数和返回值**

- `xSemaphore`

  正在被"获取"的信号量。

  信号量通过 `SemaphoreHandle_t` 类型的变量引用。它必须在使用前显式创建。

- `xTicksToWait`

  如果信号量尚不可用，任务应保持在阻塞态等待信号量的最长时间。

  如果 `xTicksToWait` 为零，则当信号量不可用时，`xSemaphoreTake()` 将立即返回。

  阻塞时间以 tick 周期为单位指定，因此其表示的绝对时间取决于 tick 频率。宏 `pdMS_TO_TICKS()` 可用于将以毫秒为单位的时间转换为以 tick 为单位的时间。

  如果将 `xTicksToWait` 设置为 `portMAX_DELAY`，并且 FreeRTOSConfig.h 中将 `INCLUDE_vTaskSuspend` 设置为 1，则任务将无限期等待（无超时）。

- 返回值

  有两种可能的返回值：

  - `pdPASS`

    仅当 `xSemaphoreTake()` 调用成功获取信号量时才返回 `pdPASS`。

    如果指定了阻塞时间（`xTicksToWait` 不为零），则调用任务可能被放入阻塞态等待信号量（如果信号量未立即可用），但信号量在阻塞时间到期前变得可用。

  - `pdFALSE`

    信号量不可用。

    如果指定了阻塞时间（`xTicksToWait` 不为零），则调用任务将被放入阻塞态等待信号量变为可用，但阻塞时间在此发生前已到期。

### 7.4.3 xSemaphoreGiveFromISR() API 函数

二值和计数信号量[^16]可以使用 `xSemaphoreGiveFromISR()` 函数"给出"。

[^16]: 计数信号量将在本书后续章节中描述。

`xSemaphoreGiveFromISR()` 是 `xSemaphoreGive()` 的中断安全版本，因此具有本章开头描述的 `pxHigherPriorityTaskWoken` 参数。

<a name="list" title="Listing 7.5 The xSemaphoreGiveFromISR() API function prototype"></a>

```c

                                  BaseType_t *pxHigherPriorityTaskWoken );
```
***Listing 7.5*** *The xSemaphoreGiveFromISR() API function prototype*

**xSemaphoreGiveFromISR() 参数和返回值**

- `xSemaphore`

  正在被"给出"的信号量。

  信号量通过 `SemaphoreHandle_t` 类型的变量引用，并且必须在使用前显式创建。

- `pxHigherPriorityTaskWoken`

  可能有一个或多个任务阻塞在单个信号量上等待它变为可用。调用 `xSemaphoreGiveFromISR()` 可以使信号量可用，从而导致等待该信号量的任务离开阻塞态。如果调用 `xSemaphoreGiveFromISR()` 导致任务离开阻塞态，并且被解除阻塞的任务具有比当前执行任务（被中断的任务）更高的优先级，则在内部 `xSemaphoreGiveFromISR()` 会将 `*pxHigherPriorityTaskWoken` 设置为 `pdTRUE`。

  如果 `xSemaphoreGiveFromISR()` 将此值设置为 `pdTRUE`，则通常应在中断退出前执行上下文切换。这将确保中断直接返回到最高优先级的就绪态任务。

- 返回值

  有两种可能的返回值：

  - `pdPASS`

    仅当 `xSemaphoreGiveFromISR()` 调用成功时才返回 `pdPASS`。

  - `pdFAIL`

    如果信号量已经可用，则无法给出，`xSemaphoreGiveFromISR()` 将返回 `pdFAIL`。

```c
{
```

```c
       pdFALSE as it will get set to pdTRUE inside the interrupt safe 
       API function if a context switch is required. */

       xHigherPriorityTaskWoken as the interrupt safe API function's
       pxHigherPriorityTaskWoken parameter. */
    xSemaphoreGiveFromISR( xBinarySemaphore, &xHigherPriorityTaskWoken );

       xSemaphoreGiveFromISR() then calling portYIELD_FROM_ISR() will request 
       a context switch. If xHigherPriorityTaskWoken is still pdFALSE then 
       calling portYIELD_FROM_ISR() will have no effect. Unlike most FreeRTOS 
       ports, the Windows port requires the ISR to return a value - the return 
       statement is inside the Windows version of portYIELD_FROM_ISR(). */
```

示例 7.1 使用二值信号量来同步任务与中断。执行顺序如下：

示例 7.1 中使用的并在清单 7.7 中显示的推迟中断处理任务的结构化方式使其仅在每次调用 `xSemaphoreTake()` 之间处理一个事件。这对于示例 7.1 来说是足够的，因为产生事件的中断是由软件触发的，并且发生在可预测的时间。在实际应用中，中断由硬件生成，并且在不可预测的时间发生。因此，为了最小化错过中断的可能性，推迟中断处理任务必须结构化，以便在每次调用 `xSemaphoreTake()` 之间处理所有已经可用的事件[^17]。清单 7.10 演示了这一点，它显示了如何构建 UART 的推迟中断处理程序。在清单 7.10 中，假设 UART 在每次接收到字符时产生一个接收中断，并且 UART 将接收到的字符放入硬件 FIFO（硬件缓冲区）中。

[^17]: 或者，可以使用计数信号量或直接任务通知来计数事件。计数信号量在下一节中描述。直接任务通知在第 9 章"任务通知"中描述。直接任务通知是首选方法，因为它们在运行时和 RAM 使用方面最高效。

示例 7.1 中使用的推迟中断处理任务还有一个弱点；它在调用 `xSemaphoreTake()` 时没有使用超时。相反，该任务将 `portMAX_DELAY` 作为 `xSemaphoreTake()` 的 `xTicksToWait` 参数传递，这导致任务无限期等待（无超时）信号量变为可用。无限期超时通常在示例代码中使用，因为它们的使示例结构更简单，从而使示例更容易理解。然而，在实际应用中，无限期超时通常是不良实践，因为它们使从错误中恢复变得困难。例如，考虑一个任务正在等待中断给出信号量，但硬件中的错误状态阻止了中断生成的场景：

- 如果任务无限期等待（无超时），它将不会知道错误状态，并将永远等待。

- 如果任务使用超时等待，则当超时到期时 `xSemaphoreTake()` 将返回 `pdFAIL`，并且任务可以在下次执行时检测并清除错误。此场景也在清单 7.10 中演示。

<a name="list7.10" title="Listing 7.10 The recommended structure of a deferred interrupt processing task, using a UART receive..."></a>

```c
static void vUARTReceiveHandlerTask( void *pvParameters )
{
    /* xMaxExpectedBlockTime holds the maximum time expected between two
       interrupts. */
    const TickType_t xMaxExpectedBlockTime = pdMS_TO_TICKS( 500 );

    /* As per most tasks, this task is implemented within an infinite loop. */
    for( ;; )
    {
        /* The semaphore is 'given' by the UART's receive (Rx) interrupt. 
           Wait a maximum of xMaxExpectedBlockTime ticks for the next 
           interrupt. */
        if( xSemaphoreTake( xBinarySemaphore, xMaxExpectedBlockTime ) == pdPASS)
        {
            /* The semaphore was obtained. Process ALL pending Rx events before
               calling xSemaphoreTake() again. Each Rx event will have placed a
               character in the UART's receive FIFO, and UART_RxCount() is 
               assumed to return the number of characters in the FIFO. */
            while( UART_RxCount() > 0 )
            {
                /* UART_ProcessNextRxEvent() is assumed to process one Rx 
                   character, reducing the number of characters in the FIFO 
                   by 1. */
                UART_ProcessNextRxEvent();
            }

            /* No more Rx events are pending (there are no more characters in 
               the FIFO), so loop back and call xSemaphoreTake() to wait for 
               the next interrupt. Any interrupts occurring between this point
               in the code and the call to xSemaphoreTake() will be latched in 
               the semaphore, so will not be lost. */
        }
        else
        {
            /* An event was not received within the expected time. Check for, 
               and if necessary clear, any error conditions in the UART that 
               might be preventing the UART from generating any more 
               interrupts. */
            UART_ClearErrors();
        }
    }
}
```

## 7.5 计数信号量

正如二值信号量可以被视为长度为 1 的队列，计数信号量可以被视为长度大于 1 的队列。任务对队列中存储的数据不感兴趣——只对队列中的项目数感兴趣。必须在 FreeRTOSConfig.h 中将 `configUSE_COUNTING_SEMAPHORES` 设置为 1，计数信号量才可用。

每次"给出"计数信号量时，其队列中的另一个空间被使用。队列中的项目数就是信号量的"计数"值。

计数信号量通常用于两件事：

1. 计数事件[^18]

   在此场景中，事件处理程序每次事件发生时"给出"信号量，导致每次"给出"时信号量的计数值递增。任务每次处理事件时"获取"信号量，导致每次"获取"时信号量的计数值递减。计数值是已发生事件数与已处理事件数之差。此机制如图 7.8 所示。

   用于计数事件的计数信号量创建时初始计数值为零。

   [^18]: 使用直接任务通知计数事件比使用计数信号量更高效。直接任务通知将在第 9 章中介绍。

1. 资源管理。

   在此场景中，计数值表示可用资源的数量。要获得对资源的控制，任务必须首先获取信号量，这将递减信号量的计数值。当计数值达到零时，没有空闲资源。当任务使用完资源后，它"给出"信号量，这将递增信号量的计数值。

   用于管理资源的计数信号量创建时其初始计数值等于可用的资源数量。第 7 章涵盖了使用信号量管理资源。

**xSemaphoreCreateCounting() 参数和返回值**

- `uxMaxCount`

   当信号量用于计数或锁存事件时，`uxMaxCount` 是可以锁存的最大事件数。

- `uxInitialCount`

   创建后信号量的初始计数值。

  如果返回非 NULL 值，则表示信号量已成功创建。返回的值应存储为所创建信号量的句柄。

```c
       as it will get set to pdTRUE inside the interrupt safe API function if 
       a context switch is required. */
    xHigherPriorityTaskWoken = pdFALSE;

    /* 'Give' the semaphore multiple times. The first will unblock the deferred
       interrupt handling task, the following 'gives' are to demonstrate that 
       the semaphore latches the events to allow the task to which interrupts 
       are deferred to process them in turn, without events getting lost. This 
       simulates multiple interrupts being received by the processor, even 
       though in this case the events are simulated within a single interrupt 
       occurrence. */
    xSemaphoreGiveFromISR( xCountingSemaphore, &xHigherPriorityTaskWoken );
    xSemaphoreGiveFromISR( xCountingSemaphore, &xHigherPriorityTaskWoken );
    xSemaphoreGiveFromISR( xCountingSemaphore, &xHigherPriorityTaskWoken );

    /* Pass the xHigherPriorityTaskWoken value into portYIELD_FROM_ISR().
       If xHigherPriorityTaskWoken was set to pdTRUE inside
       xSemaphoreGiveFromISR() then calling portYIELD_FROM_ISR() will request 
       a context switch. If xHigherPriorityTaskWoken is still pdFALSE then 
       calling portYIELD_FROM_ISR() will have no effect. Unlike most FreeRTOS 
       ports, the Windows port requires the ISR to return a value - the return
       statement is inside the Windows version of portYIELD_FROM_ISR(). */
    portYIELD_FROM_ISR( xHigherPriorityTaskWoken );
}
```

<a id="76-deferring-work-to-the-rtos-daemon-task"></a>
## 7.6 将工作推迟到 RTOS 守护任务

迄今为止介绍的推迟中断处理示例要求应用程序编写者为每个使用推迟处理技术的中断创建一个任务。也可以使用 `xTimerPendFunctionCallFromISR()`[^19] API 函数将中断处理推迟到 RTOS 守护任务，这消除了为每个中断创建单独任务的需要。将中断处理推迟到守护任务称为"集中式推迟中断处理"。

[^19]: 守护任务最初称为定时器服务任务，因为它最初仅用于执行软件定时器回调函数。因此，`xTimerPendFunctionCall()` 在 timers.c 中实现，并且根据在函数名称前添加实现该函数的文件名称的约定，该函数的名称以"Timer"为前缀。

第 6 章描述了与软件定时器相关的 FreeRTOS API 函数如何通过定时器命令队列向守护任务发送命令。`xTimerPendFunctionCall()` 和 `xTimerPendFunctionCallFromISR()` API 函数使用相同的定时器命令队列向守护任务发送"执行函数"命令。发送给守护任务的函数随后在守护任务的上下文中执行。

集中式推迟中断处理的优点包括：

- 更低的资源使用

  它消除了为每个推迟的中断创建单独任务的需要。

- 简化的用户模型

  推迟中断处理函数是一个标准的 C 函数。

集中式推迟中断处理的缺点包括：

- 灵活性较低

  无法单独设置每个推迟中断处理任务的优先级。每个推迟中断处理函数在守护任务的优先级下执行。如第 6 章所述，守护任务的优先级由 FreeRTOSConfig.h 中的编译时配置常量 `configTIMER_TASK_PRIORITY` 设置。

- 确定性较低

  `xTimerPendFunctionCallFromISR()` 将命令发送到定时器命令队列的末尾。已经在定时器命令队列中的命令将在 `xTimerPendFunctionCallFromISR()` 发送到队列的"执行函数"命令之前由守护任务处理。

不同的中断有不同的时序约束，因此通常在同一个应用程序中同时使用两种推迟中断处理的方法。

<a id="761-the-xtimerpendfunctioncallfromisr-api-function"></a>

  有两种可能的返回值：

  - `pdPASS`

  - `pdFAIL`

    如果由于定时器命令队列已满而无法写入"执行函数"命令，则返回 `pdFAIL`。第 6 章描述了如何设置定时器命令队列的长度。

- 返回值

  有两种可能的返回值：

  - `pdPASS`

    仅当数据已成功发送到队列时才返回 `pdPASS`。

  - `errQUEUE_FULL`

    如果由于队列已满而无法发送数据，则返回 `errQUEUE_FULL`。

<a id="772-considerations-when-using-a-queue-from-an-isr"></a>
### 7.7.2 从 ISR 使用队列时的考虑

队列提供了一种从中断向任务传递数据的简便方法，但如果数据以高频率到达，使用队列并不高效。

FreeRTOS 下载中的许多演示应用程序包含一个简单的 UART 驱动程序，该驱动程序使用队列将字符从 UART 的接收 ISR 中传递出来。在这些演示中，使用队列有两个原因：演示从 ISR 中使用队列，以及有意加载系统以测试 FreeRTOS 端口。以这种方式使用队列的 ISR 绝对不旨在表示高效的设计，除非数据到达缓慢，否则建议生产代码不要复制此技术。适用于生产代码的更高效技术包括：

- 使用直接内存访问（DMA）硬件来接收和缓冲字符。此方法几乎没有软件开销。然后可以使用直接任务通知[^20]来解除阻塞将在检测到传输中断后处理缓冲区的任务。

  [^20]: 直接任务通知提供了从 ISR 解除阻塞任务的最高效方法。直接任务通知在第 9 章"任务通知"中介绍。

- 将每个接收到的字符复制到线程安全的 RAM 缓冲区[^21]中。同样，可以使用直接任务通知来解除阻塞将在收到完整消息后或检测到传输中断后处理缓冲区的任务。

  [^21]: 作为 FreeRTOS+TCP 一部分提供的"流缓冲区"（[https://www.FreeRTOS.org/tcp](http://www.FreeRTOS.org/tcp)）可用于此目的。

- 在 ISR 内直接处理接收到的字符，然后使用队列仅将数据处理的结果（而不是原始数据）发送到任务。这在之前通过图 5.4 进行了演示。

***Example 7.4*** *Sending and receiving on a queue from within an interrupt*

---

此示例演示了在同一中断中使用 `xQueueSendToBackFromISR()` 和 `xQueueReceiveFromISR()`。与之前一样，为方便起见，中断由软件生成。

创建一个周期性任务，每 200 毫秒向队列发送五个数字。它仅在发送完所有五个值后才生成一个软件中断。任务实现如清单 7.21 所示。

<a name="list7.21" title="Listing 7.21 The implementation of the task that writes to the queue in Example 7.4"></a>

```c
static void vIntegerGenerator( void *pvParameters )
{
    TickType_t xLastExecutionTime;
    uint32_t ulValueToSend = 0;
    int i;

    /* Initialize the variable used by the call to vTaskDelayUntil(). */
    xLastExecutionTime = xTaskGetTickCount();

    for( ;; )
    {
        /* This is a periodic task. Block until it is time to run again. The
           task will execute every 200ms. */
        vTaskDelayUntil( &xLastExecutionTime, pdMS_TO_TICKS( 200 ) );

        /* Send five numbers to the queue, each value one higher than the
           previous value. The numbers are read from the queue by the interrupt
           service routine. The interrupt service routine always empties the 
           queue, so this task is guaranteed to be able to write all five 
           values without needing to specify a block time. */
        for( i = 0; i < 5; i++ )
        {
            xQueueSendToBack( xIntegerQueue, &ulValueToSend, 0 );
            ulValueToSend++;
        }

        /* Generate the interrupt so the interrupt service routine can read the
           values from the queue. The syntax used to generate a software 
           interrupt is dependent on the FreeRTOS port being used. The syntax 
           used below can only be used with the FreeRTOS Windows port, in which
           such interrupts are only simulated. */
        vPrintString( "Generator task - About to generate an interrupt.\r\n" );
        vPortGenerateSimulatedInterrupt( mainINTERRUPT_NUMBER );
        vPrintString( "Generator task - Interrupt generated.\r\n\r\n\r\n" );
    }
}
```
***Listing 7.21*** *The implementation of the task that writes to the queue in Example 7.4*

中断服务例程重复调用 `xQueueReceiveFromISR()`，直到周期性任务写入队列的所有值都被读取出来，队列变为空。每个接收值的最后两位用作字符串数组的索引。然后使用对 `xQueueSendFromISR()` 的调用将对应索引位置处的字符串指针发送到不同的队列。中断服务例程的实现如清单 7.22 所示。

<a name="list7.22" title="Listing 7.22 The implementation of the interrupt service routine used by Example 7.4"></a>

```c
static uint32_t ulExampleInterruptHandler( void )
{
    BaseType_t xHigherPriorityTaskWoken;
    uint32_t ulReceivedNumber;

    /* The strings are declared static const to ensure they are not allocated
       on the interrupt service routine's stack, and so exist even when the 
       interrupt service routine is not executing. */

    static const char *pcStrings[] =
    {
        "String 0\r\n",
        "String 1\r\n",
        "String 2\r\n",
        "String 3\r\n"
    };

    /* As always, xHigherPriorityTaskWoken is initialized to pdFALSE to be 
       able to detect it getting set to pdTRUE inside an interrupt safe API 
       function.  Note that as an interrupt safe API function can only set 
       xHigherPriorityTaskWoken to pdTRUE, it is safe to use the same 
       xHigherPriorityTaskWoken variable in both the call to 
       xQueueReceiveFromISR() and the call to xQueueSendToBackFromISR(). */
    xHigherPriorityTaskWoken = pdFALSE;

    /* Read from the queue until the queue is empty. */
    while( xQueueReceiveFromISR( xIntegerQueue,
                                 &ulReceivedNumber,
                                 &xHigherPriorityTaskWoken ) != errQUEUE_EMPTY )
    {
        /* Truncate the received value to the last two bits (values 0 to 3
           inclusive), then use the truncated value as an index into the
           pcStrings[] array to select a string (char *) to send on the other 
           queue. */
        ulReceivedNumber &= 0x03;
        xQueueSendToBackFromISR( xStringQueue,
                                 &pcStrings[ ulReceivedNumber ],
                                 &xHigherPriorityTaskWoken );
    }

    /* If receiving from xIntegerQueue caused a task to leave the Blocked 
       state, and if the priority of the task that left the Blocked state is 
       higher than the priority of the task in the Running state, then 
       xHigherPriorityTaskWoken will have been set to pdTRUE inside 
       xQueueReceiveFromISR().

       If sending to xStringQueue caused a task to leave the Blocked state, and
       if the priority of the task that left the Blocked state is higher than 
       the priority of the task in the Running state, then 
       xHigherPriorityTaskWoken will have been set to pdTRUE inside 
       xQueueSendToBackFromISR().

       xHigherPriorityTaskWoken is used as the parameter to portYIELD_FROM_ISR().
       If xHigherPriorityTaskWoken equals pdTRUE then calling portYIELD_FROM_ISR()
       will request a context switch. If xHigherPriorityTaskWoken is still 
       pdFALSE then calling portYIELD_FROM_ISR() will have no effect.

       The implementation of portYIELD_FROM_ISR() used by the Windows port
```

## 7.8 中断嵌套

任务优先级和中断优先级之间经常产生混淆。本节讨论中断优先级，即中断服务例程（ISR）相对于彼此执行的优先级。分配给任务的优先级与分配给中断的优先级没有任何关系。硬件决定何时执行 ISR，而软件决定何时执行任务。响应硬件中断而执行的 ISR 会中断任务，但任务不能抢占 ISR。

支持中断嵌套的端口需要在 FreeRTOSConfig.h 中定义以下一个或两个常量。`configMAX_SYSCALL_INTERRUPT_PRIORITY` 和 `configMAX_API_CALL_INTERRUPT_PRIORITY` 都定义相同的属性。较旧的 FreeRTOS 端口使用 `configMAX_SYSCALL_INTERRUPT_PRIORITY`，较新的 FreeRTOS 端口使用 `configMAX_API_CALL_INTERRUPT_PRIORITY`。

**控制中断嵌套的常量**

- `configMAX_SYSCALL_INTERRUPT_PRIORITY` 或 `configMAX_API_CALL_INTERRUPT_PRIORITY`

  设置可以从中调用中断安全 FreeRTOS API 函数的最高中断优先级。

- `configKERNEL_INTERRUPT_PRIORITY`

  设置 tick 中断使用的中断优先级，并且必须始终设置为可能的最低中断优先级。

  如果所使用的 FreeRTOS 端口未同时使用 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 常量，则任何使用中断安全 FreeRTOS API 函数的中断也必须在 `configKERNEL_INTERRUPT_PRIORITY` 定义的优先级下执行。

每个中断源都有一个数字优先级和一个逻辑优先级：

- 数字优先级

  数字优先级只是分配给中断优先级的编号。例如，如果中断被分配优先级 7，则其数字优先级为 7。同样，如果中断被分配优先级 200，则其数字优先级为 200。

- 逻辑优先级

  中断的逻辑优先级描述了该中断相对于其他中断的优先顺序。

  如果两个不同优先级的中断同时发生，则处理器将首先执行具有较高逻辑优先级的中断的 ISR，然后执行具有较低逻辑优先级的中断的 ISR。

  一个中断可以中断（嵌套）任何具有较低逻辑优先级的中断，但一个中断不能中断（嵌套）任何具有相等或更高逻辑优先级的中断。

中断的数字优先级和逻辑优先级之间的关系取决于处理器架构；在某些处理器上，分配给中断的数字优先级越高，该中断的逻辑优先级*越高*，而在其他处理器架构上，分配给中断的数字优先级越高，该中断的逻辑优先级*越低*。

通过将 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 设置为比 `configKERNEL_INTERRUPT_PRIORITY` 更高的逻辑中断优先级，可以创建完整的中断嵌套模型。图 7.14 演示了这一点，其中显示了一个场景：

- 处理器有七个唯一的中断优先级。
- 分配数字优先级 7 的中断具有比分配数字优先级 1 的中断更高的逻辑优先级。
- `configKERNEL_INTERRUPT_PRIORITY` 设置为 1。
- `configMAX_SYSCALL_INTERRUPT_PRIORITY` 设置为 3。

<a id="781-a-note-to-arm-cortex-m22-and-arm-gic-users"></a>
### 7.8.1 ARM Cortex-M[^22] 和 ARM GIC 用户注意事项

[^22]: 本节仅部分适用于 Cortex-M0 和 Cortex-M0+ 内核。

Cortex-M 处理器上的中断配置令人困惑，且容易出错。为帮助您的开发，FreeRTOS Cortex-M 端口会自动检查中断配置，但仅当定义了 `configASSERT()` 时才进行检查。`configASSERT()` 在第 11.2 节中描述。

ARM Cortex 内核和 ARM 通用中断控制器（GIC）使用数字上*低*的优先级编号来表示逻辑上*高*优先级的中断。这看起来违反直觉，并且容易忘记。如果您希望为中断分配逻辑上的低优先级，则必须分配数值高的值。如果您希望为中断分配逻辑上的高优先级，则必须分配数值低的值。

Cortex-M 中断控制器允许最多使用八位来指定每个中断优先级，使 255 成为可能的最低优先级。零是最高优先级。然而，Cortex-M 微控制器通常只实现八个可能位中的一个子集。实际实现的位数取决于微控制器系列。

当只实现了八位中的一部分时，只能使用字节的最高有效位——最低有效位未实现。未实现的位可以采用任何值，但通常将它们设置为 1。图 7.15 演示了这一点，其中显示了在实现四个优先级位的 Cortex-M 微控制器中如何存储二进制 101 的优先级。

在图 7.15 中，二进制值 101 已被移位到最高有效的四位中，因为最低有效的四位未实现。未实现的位已被设置为 1。

某些库函数期望在优先级值已经上移到已实现的（最高有效）位之后指定它们。使用此类函数时，图 7.15 中显示的优先级可以指定为十进制 95。十进制 95 是二进制 101 上移四位得到二进制 101nnnn（其中'n'是未实现的位），并将未实现的位设置为 1 得到二进制 1011111。

某些库函数期望在优先级值上移到已实现的（最高有效）位之前指定它们。使用此类函数时，图 7.15 中显示的优先级必须指定为十进制 5。十进制 5 是二进制 101，无需移位。

`configMAX_SYSCALL_INTERRUPT_PRIORITY` 和 `configKERNEL_INTERRUPT_PRIORITY` 必须以允许它们直接写入 Cortex-M 寄存器的方式指定，即在优先级值已上移到已实现位之后。

`configKERNEL_INTERRUPT_PRIORITY` 必须始终设置为可能的最低中断优先级。未实现的优先级位可以设置为 1，因此无论实际实现了多少优先级位，该常量始终可以设置为 255。

Cortex-M 中断将默认为优先级零——可能的最高优先级。Cortex-M 硬件的实现不允许将 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 设置为 0，因此使用 FreeRTOS API 的中断的优先级绝不能保留为其默认值。
