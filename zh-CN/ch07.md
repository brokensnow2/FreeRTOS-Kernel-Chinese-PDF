# 7 中断管理

<a id="71-introduction"></a>
## 7.1 引言

<a id="711-events"></a>
### 7.1.1 事件

嵌入式实时系统必须响应来自外部环境的事件。例如，以太网外设收到数据包（事件）后，可能需要将其传递给 TCP/IP 协议栈进行处理（操作）。稍具复杂度的系统都必须处理来自多个数据源的事件，而每类事件的处理开销和响应时间要求各不相同。因此，需要针对每种情况确定最佳的事件处理策略：

- 如何检测事件？通常使用中断，但输入也可以轮询。

- 使用中断时，应当在中断服务程序（ISR）内部完成多少处理，又应当把多少处理放到 ISR 外部？通常应使每个 ISR 尽可能短。

- 如何把事件传递给主体（非 ISR）代码，以及如何组织这部分代码，才能妥善处理可能异步发生的事件？

FreeRTOS 不会强制应用程序设计者采用某一种事件处理策略，但它提供了相应功能，使选定的策略能够以简洁且易于维护的方式实现。

区分任务优先级和中断优先级非常重要：

- 任务是一种软件特性，与运行 FreeRTOS 的硬件无关。任务优先级由应用程序开发者在软件中指定，软件算法（调度器）决定哪个任务进入运行状态。

- 中断服务程序虽然由软件编写，但中断本身是硬件特性，因为硬件决定哪个 ISR 在何时运行。任务只能在没有 ISR 运行时执行，因此即使是最低优先级的中断也能中断最高优先级的任务，而任务无法抢占 ISR。

所有能够运行 FreeRTOS 的架构都支持中断，但中断入口和中断优先级分配的具体方式因架构而异。

<a id="712-scope"></a>
### 7.1.2 范围

本章涵盖：

- 哪些 FreeRTOS API 函数可以在中断服务程序中使用。
- 如何把中断处理延迟到任务中执行。

- 某些 FreeRTOS 移植版本提供的中断嵌套模型。

<a id="72-using-the-freertos-api-from-an-isr"></a>
## 7.2 从 ISR 中使用 FreeRTOS API

<a id="721-the-interrupt-safe-api"></a>
### 7.2.1 中断安全 API

中断服务程序（ISR）经常需要使用 FreeRTOS API 提供的功能，但许多 FreeRTOS API 函数执行的操作在 ISR 中没有意义。最明显的例子是把调用 API 的任务置于阻塞状态：从 ISR 调用 API 时，并不存在可以被阻塞的调用任务。FreeRTOS 为部分 API 函数分别提供任务版本和 ISR 版本，以解决这一问题。供 ISR 使用的版本在函数名末尾带有 `FromISR`。

> *注意：切勿从 ISR 调用函数名中不含 `FromISR` 的 FreeRTOS API 函数。*

<a id="722-the-benefits-of-using-a-separate-interrupt-safe-api"></a>
### 7.2.2 使用单独的中断安全 API 的好处

独立的中断安全 API 能提高任务代码和 ISR 代码的效率，同时简化中断入口。要理解其中原因，可以设想另一种方案：每个 API 函数只提供一个版本，并允许从任务和 ISR 调用。如果采用这种方案：

- API 函数需要额外逻辑判断调用来自任务还是 ISR。这会引入新的执行路径，使函数更长、更复杂，也更难测试。

- 某些参数在从任务调用时会显得多余，另一些参数则在从 ISR 调用时没有意义。

- 每个 FreeRTOS 移植版本都需要提供一种机制来确定执行上下文（任务或 ISR）。

- 对于难以判断执行上下文的架构，还需要额外、低效、复杂且非标准的中断入口代码，才能让软件获知当前处于任务还是 ISR 上下文。

<a id="723-the-disadvantages-of-using-a-separate-interrupt-safe-api"></a>
### 7.2.3 使用单独的中断安全 API 的缺点

为部分 API 函数提供两个版本提高了任务和 ISR 的效率，但也带来一个问题：有时某个并非 FreeRTOS API、但内部调用了 FreeRTOS API 的函数，需要同时从任务和 ISR 调用。

这通常只在集成第三方代码时才会成为问题，因为此时应用程序开发者无法控制原有软件设计。可以采用以下方法之一解决：

- 将中断处理延迟到任务[^12]，使 API 函数只在任务上下文中调用。

- 如果使用支持中断嵌套的 FreeRTOS 移植版本，可使用函数名以 `FromISR` 结尾的 API 版本，因为该版本既能从任务调用，也能从 ISR 调用。反过来则不成立：函数名不以 `FromISR` 结尾的 API 不得从 ISR 调用。

- 第三方代码通常包含一个 RTOS 抽象层，可以实现该抽象层来测试调用函数的上下文（任务或中断），然后调用适合该上下文的 API 函数。

[^12]: 下一节将介绍延迟中断处理。

<a id="724-the-xhigherprioritytaskwoken-parameter"></a>
### 7.2.4 xHigherPriorityTaskWoken 参数

本节介绍 `xHigherPriorityTaskWoken` 参数。如果暂时没有完全理解也不必担心，后续各节会给出实际示例。

如果中断引发了上下文切换，那么中断退出后运行的任务可能与进入中断前运行的任务不同：中断打断了一个任务，却返回到另一个任务。

某些 FreeRTOS API 函数能够把任务从阻塞状态转入就绪状态。例如，如果有任务阻塞在某个队列上等待数据，`xQueueSendToBack()` 向该队列写入数据后就会解除该任务的阻塞。

如果被 FreeRTOS API 函数解除阻塞的任务优先级高于当前运行任务，那么根据 FreeRTOS 调度策略，应当切换到这个更高优先级的任务。切换实际发生的时机取决于调用 API 的上下文：

- 如果从任务调用 API 函数：

  如果在 `FreeRTOSConfig.h` 中将 `configUSE_PREEMPTION` 设为 1，则 API 函数会在返回前自动切换到更高优先级的任务。图 6.6 已展示这种情况：向定时器命令队列写入数据后，写队列函数还没有返回，系统就切换到了 RTOS 守护任务。

- 如果从中断调用 API 函数：

  系统不会在中断安全 API 内部自动切换到更高优先级的任务，而是通过一个变量通知应用程序应当执行上下文切换。函数名以 `FromISR` 结尾的中断安全 API 都为此提供一个名为 `pxHigherPriorityTaskWoken` 的指针参数。

  如果需要执行上下文切换，中断安全 API 会把 `*pxHigherPriorityTaskWoken` 设为 `pdTRUE`。为了可靠检测这一结果，必须在首次使用前把 `pxHigherPriorityTaskWoken` 所指向的变量初始化为 `pdFALSE`。

  如果应用程序没有从 ISR 请求上下文切换，则更高优先级的任务会保持就绪状态，直到调度器下一次运行，最坏情况下要等到下一次 Tick 中断。

  FreeRTOS API 只会把 `*pxHigherPriorityTaskWoken` 设为 `pdTRUE`，绝不会将其重置为 `pdFALSE`。因此，如果一个 ISR 调用多个 FreeRTOS API，可以把同一个变量传给每次调用的 `pxHigherPriorityTaskWoken` 参数，而且只需在首次使用前把该变量初始化为 `pdFALSE`。

中断安全 API 不在函数内部自动执行上下文切换，原因包括：

- 避免不必要的上下文切换

  在任务真正需要处理数据之前，中断可能已经发生多次。例如，一个任务负责处理由中断驱动的 UART 接收到的字符串，只有收到完整字符串后才需要运行。如果每收到一个字符就切换到该任务，会造成浪费。

- 控制执行顺序

  中断可能零星发生，而且时机不可预测。经验丰富的 FreeRTOS 用户有时希望在应用程序的特定位置暂时避免这种不可预测的任务切换，尽管也可以通过锁定 FreeRTOS 调度器实现。

- 可移植性

  这是可以在所有 FreeRTOS 移植版本上使用的最简单机制。

- 效率

  面向小型处理器架构的移植版本可能只允许在 ISR 末尾请求上下文切换。取消这一限制需要额外而复杂的代码。当前机制还允许在同一个 ISR 中多次调用 FreeRTOS API，而不会产生多个上下文切换请求。

- 在 RTOS Tick 中断中执行

  后文将介绍如何把应用程序代码加入 RTOS Tick 中断。在 Tick 中断内部尝试上下文切换的结果取决于所用 FreeRTOS 移植版本，即使在最好的情况下，也会造成一次不必要的调度器调用。

`pxHigherPriorityTaskWoken` 参数是可选的。如果不需要，可将其设为 `NULL`。

<a id="725-the-portyieldfromisr-and-portendswitchingisr-macros"></a>
### 7.2.5 portYIELD_FROM_ISR() 和 portEND_SWITCHING_ISR() 宏

本节介绍用于从 ISR 请求上下文切换的宏。后续各节会给出实际示例。

`taskYIELD()` 是任务用于请求上下文切换的宏。`portYIELD_FROM_ISR()` 和 `portEND_SWITCHING_ISR()` 则是它的中断安全版本，两者用法相同，执行的操作也相同[^13]。某些 FreeRTOS 移植版本只提供其中一个宏，较新的移植版本通常两者都提供。本书示例使用 `portYIELD_FROM_ISR()`。

[^13]: 从历史上看，要求用汇编代码封装中断处理程序的 FreeRTOS 移植版本使用 `portEND_SWITCHING_ISR()`；允许整个中断处理程序使用 C 编写的移植版本则使用 `portYIELD_FROM_ISR()`。

<a name="list7.1" title="代码清单 7.1 portEND_SWITCHING_ISR() 宏"></a>

```c
portEND_SWITCHING_ISR( xHigherPriorityTaskWoken );
```
***代码清单 7.1*** *`portEND_SWITCHING_ISR()` 宏*

<a name="list7.2" title="代码清单 7.2 portYIELD_FROM_ISR() 宏"></a>

```c
portYIELD_FROM_ISR( xHigherPriorityTaskWoken );
```
***代码清单 7.2*** *`portYIELD_FROM_ISR()` 宏*

中断安全 API 输出的 `xHigherPriorityTaskWoken` 变量可以直接传给 `portYIELD_FROM_ISR()`。

如果传给 `portYIELD_FROM_ISR()` 的 `xHigherPriorityTaskWoken` 为 `pdFALSE`（零），宏不会请求上下文切换，也不会产生任何效果。如果该参数不为 `pdFALSE`，宏将请求上下文切换，当前运行任务可能随之改变。中断始终返回到切换后的运行任务，即使它与进入中断前的运行任务不同。

大多数 FreeRTOS 移植版本允许在 ISR 内的任意位置调用 `portYIELD_FROM_ISR()`。少数移植版本（主要面向小型架构）只允许在 ISR 的最末尾调用 `portYIELD_FROM_ISR()`。

<a id="73-deferred-interrupt-processing"></a>
## 7.3 延迟中断处理

通常认为最佳实践是保持 ISR 尽可能短。原因包括：

- 即使任务已被分配非常高的优先级，它们也只有在硬件没有服务任何中断时才会运行。

- ISR 可能会干扰任务的启动时间和执行时间，增加时间“抖动”。

- 根据运行 FreeRTOS 的架构，在执行 ISR 时可能无法接受任何新中断，或至少是部分新中断。

- 应用程序编写者需要考虑并防范任务和 ISR 同时访问变量、外设和内存缓冲区等资源带来的后果。

- 某些 FreeRTOS 移植版本允许中断嵌套，但嵌套会增加复杂性并降低可预测性。中断越短，发生嵌套的可能性就越小。

中断服务程序必须记录中断原因并清除中断。中断所需的其他处理通常可以在任务中执行，从而让中断服务程序尽快退出。这称为“延迟中断处理”，因为中断所需的处理从 ISR 延迟到了任务中。

将中断处理延迟到任务中，还允许应用程序开发者相对于其他任务安排处理优先级，并使用全部 FreeRTOS API 函数。

如果延迟处理中断的任务优先级高于其他所有任务，那么它会立即执行，就像处理工作仍在 ISR 中完成一样。图 7.1 展示了这种情形，其中任务 1 是普通应用程序任务，任务 2 是延迟处理中断的任务。

对于何时应在 ISR 中完成中断所需的全部处理、何时应把部分处理延迟到任务中，并没有绝对规则。在以下情况下，延迟到任务中处理尤其有用：

- 中断所需的处理并非微不足道。例如，如果只需保存模数转换结果，那么几乎肯定应在 ISR 中完成；但如果还要用软件滤波器处理转换结果，则最好在任务中执行滤波。

- 中断处理需要执行无法在 ISR 中完成的操作，例如向控制台输出或分配内存。

- 中断处理不具备确定性，也就是无法预先知道处理需要多长时间。

<a id="74-binary-semaphores-used-for-synchronization"></a>
## 7.4 用于同步的二值信号量

中断每次发生时，都可以通过中断安全 API 给出二值信号量并解除一个任务的阻塞，从而有效地使该任务与中断同步。这样，大部分中断事件处理都能放在同步任务中完成，ISR 只保留极快且极短的部分。如前一节所述，二值信号量可用于把中断处理延迟到任务中[^14]。

[^14]: 使用直接任务通知从中断中解除任务的阻塞，比使用二值信号量更高效。直接任务通知将在第 10 章“任务通知”中介绍。

如图 7.1 所示，如果中断处理对时序要求极高，可以把延迟处理任务的优先级设得足够高，使它始终抢占系统中的其他任务。随后在 ISR 中调用 `portYIELD_FROM_ISR()`，即可确保 ISR 直接返回到延迟处理中断的任务。这样，整个事件处理过程在时间上连续、不被打断，效果就像全部工作都在 ISR 中完成一样。图 7.2 仍采用图 7.1 的场景，但更新了图中文字，以说明如何用信号量控制延迟处理任务的执行。

延迟处理任务通过阻塞式“获取”信号量进入阻塞状态，等待事件发生。事件发生时，ISR“给出”同一个信号量以解除任务的阻塞，使所需的事件处理得以继续。

“获取”和“给出”信号量是两个概念，其具体含义取决于使用场景。在这里的中断同步场景中，可以把二值信号量看作长度为 1 的队列。队列最多容纳一个项目，所以不是空就是满，这也是“二值”一词的由来。延迟处理中断的任务调用 `xSemaphoreTake()`，相当于尝试从队列读取数据，并指定一段阻塞时间；如果队列为空，任务便进入阻塞状态。事件发生时，ISR 调用 `xSemaphoreGiveFromISR()`，把一个令牌（信号量）放入队列，使队列变满。任务因而离开阻塞状态并取走令牌，队列再次变空。任务处理完事件后再次尝试读取队列；由于队列为空，任务重新进入阻塞状态，等待下一个事件。图 7.3 展示了这一过程。

图 7.3 中，中断即使从未“获取”过信号量，也会“给出”信号量；任务则“获取”信号量，却从不将其归还。因此，这种场景在概念上更像队列的写入和读取。它经常令人困惑，因为它不遵循其他信号量使用场景的规则。在那些场景中，获取信号量的任务必须始终归还信号量，例如第 8 章“资源管理”介绍的用法。

### 7.4.1 xSemaphoreCreateBinary() API 函数

所有类型的 FreeRTOS 信号量句柄都保存在 `SemaphoreHandle_t` 类型的变量中。使用信号量之前必须先创建它。要创建二值信号量，可以使用 `xSemaphoreCreateBinary()` API 函数[^15]。该函数从 FreeRTOS 堆中动态分配信号量所需的内存；FreeRTOS 还提供 `xSemaphoreCreateBinaryStatic()`，使用调用者预先提供的内存创建二值信号量。

[^15]: 某些信号量 API 函数实际上是宏，而不是函数。为简单起见，本书中统称为函数。

<a name="list7.3" title="代码清单 7.3 xSemaphoreCreateBinary() API 函数原型"></a>

```c
SemaphoreHandle_t xSemaphoreCreateBinary( void );
```
***代码清单 7.3*** *`xSemaphoreCreateBinary()` API 函数原型*

**xSemaphoreCreateBinary() 返回值**

- 返回值

  如果返回 `NULL`，则信号量创建失败，因为 FreeRTOS 没有足够的堆内存用于分配信号量数据结构。

  如果返回非 `NULL` 值，则表示信号量创建成功。该返回值是所创建信号量的句柄。

<a id="742-the-xsemaphoretake-api-function"></a>
### 7.4.2 xSemaphoreTake() API 函数

“获取”信号量意味着“取得”或“接收”信号量。只有信号量可用时才能将其获取。

除递归互斥量外，所有类型的 FreeRTOS 信号量都可以用 `xSemaphoreTake()` 函数“获取”。

不得从中断服务程序中调用 `xSemaphoreTake()`。

<a name="list7.4" title="代码清单 7.4 xSemaphoreTake() API 函数原型"></a>

```c
BaseType_t xSemaphoreTake( SemaphoreHandle_t xSemaphore, TickType_t xTicksToWait );
```
***代码清单 7.4*** *`xSemaphoreTake()` API 函数原型*

**xSemaphoreTake() 参数和返回值**

- `xSemaphore`

  要“获取”的信号量。

  信号量通过 `SemaphoreHandle_t` 类型的变量引用。它必须在使用前显式创建。

- `xTicksToWait`

  如果信号量尚不可用，任务为等待信号量而保持阻塞状态的最长时间。

  如果 `xTicksToWait` 为零，则当信号量不可用时，`xSemaphoreTake()` 将立即返回。

  阻塞时间以 Tick 周期为单位，因此它表示的绝对时间取决于 Tick 频率。宏 `pdMS_TO_TICKS()` 可将毫秒转换为 Tick 数。

  如果将 `xTicksToWait` 设为 `portMAX_DELAY`，并在 `FreeRTOSConfig.h` 中将 `INCLUDE_vTaskSuspend` 设为 1，任务将无限期等待，不会超时。

- 返回值

  有两种可能的返回值：

  - `pdPASS`

    仅当 `xSemaphoreTake()` 调用成功获取信号量时才返回 `pdPASS`。

    如果指定了阻塞时间（`xTicksToWait` 不为零），而信号量又没有立即可用，调用任务可能进入阻塞状态等待；只要信号量在阻塞时间到期前变为可用，调用便会成功。

  - `pdFALSE`

    信号量不可用，获取失败。

    如果指定了阻塞时间（`xTicksToWait` 不为零），调用任务会进入阻塞状态等待信号量，但阻塞时间在信号量变为可用之前已经到期。

### 7.4.3 xSemaphoreGiveFromISR() API 函数

可以使用 `xSemaphoreGiveFromISR()` 函数“给出”二值信号量和计数信号量[^16]。

[^16]: 下一节将介绍计数信号量。

`xSemaphoreGiveFromISR()` 是 `xSemaphoreGive()` 的中断安全版本，因此具有本章开头描述的 `pxHigherPriorityTaskWoken` 参数。

<a name="list7.5" title="代码清单 7.5 xSemaphoreGiveFromISR() API 函数原型"></a>

```c
BaseType_t xSemaphoreGiveFromISR( SemaphoreHandle_t xSemaphore,
                                  BaseType_t *pxHigherPriorityTaskWoken );
```
***代码清单 7.5*** *`xSemaphoreGiveFromISR()` API 函数原型*

**xSemaphoreGiveFromISR() 参数和返回值**

- `xSemaphore`

  要“给出”的信号量。

  信号量通过 `SemaphoreHandle_t` 类型的变量引用，并且必须在使用前显式创建。

- `pxHigherPriorityTaskWoken`

  一个信号量上可能阻塞着一个或多个等待它变为可用的任务。调用 `xSemaphoreGiveFromISR()` 可以使信号量变为可用，从而让等待它的任务离开阻塞状态。如果被解除阻塞的任务优先级高于当前执行的任务（即被中断的任务），`xSemaphoreGiveFromISR()` 会在内部把 `*pxHigherPriorityTaskWoken` 设为 `pdTRUE`。

  如果 `xSemaphoreGiveFromISR()` 把该值设为 `pdTRUE`，通常应在退出中断前执行上下文切换，确保中断直接返回到优先级最高的就绪状态任务。

- 返回值

  有两种可能的返回值：

  - `pdPASS`

    仅当 `xSemaphoreGiveFromISR()` 调用成功时才返回 `pdPASS`。

  - `pdFAIL`

    如果信号量已经可用，就无法再次给出，此时 `xSemaphoreGiveFromISR()` 返回 `pdFAIL`。

代码清单 7.7 所示的延迟中断处理任务，在相邻两次 `xSemaphoreTake()` 调用之间只处理一个事件。对于示例 7.1，这样已经足够，因为事件由软件中断产生，发生时刻可以预测。但在实际应用中，中断通常由硬件产生，时机不可预测。因此，为尽量避免遗漏中断，延迟中断处理任务应在相邻两次 `xSemaphoreTake()` 调用之间处理所有已经到达的事件[^17]。代码清单 7.10 以 UART 接收处理程序为例展示了这种结构。它假定 UART 每接收一个字符就产生一次接收中断，并把收到的字符放入硬件 FIFO（硬件缓冲区）。

[^17]: 也可以使用计数信号量或直接任务通知来计数事件。下一节将介绍计数信号量，第 10 章“任务通知”将介绍直接任务通知。直接任务通知在运行时间和 RAM 占用方面效率最高，因此是首选方法。

示例 7.1 的延迟中断处理任务还有一个弱点：调用 `xSemaphoreTake()` 时没有设置超时。任务把 `portMAX_DELAY` 作为 `xTicksToWait` 参数传入，因此会无限期等待信号量变为可用。示例代码经常采用无限等待，因为这样结构更简单、更易理解；但在实际应用中，这通常不是良好做法，因为系统会更难从错误中恢复。例如，假设任务正在等待中断给出信号量，而硬件错误又阻止了中断产生：

- 如果任务无限期等待，它不会察觉错误状态，只会一直等待。

- 如果任务设置了超时，超时到期时 `xSemaphoreTake()` 会返回 `pdFAIL`，任务便可检测并清除错误。代码清单 7.10 也演示了这种处理方式。

<a name="list7.10" title="代码清单 7.10 以 UART 接收处理程序为例的延迟中断处理任务推荐结构"></a>

```c
static void vUARTReceiveHandlerTask( void *pvParameters )
{
    /* xMaxExpectedBlockTime 保存两次中断之间预期的最长时间。 */
    const TickType_t xMaxExpectedBlockTime = pdMS_TO_TICKS( 500 );

    /* 与大多数任务一样，本任务在无限循环中实现。 */
    for( ;; )
    {
        /* UART 接收（Rx）中断会“给出”信号量。等待下一次中断的时间最多为
           xMaxExpectedBlockTime 个 Tick。 */
        if( xSemaphoreTake( xBinarySemaphore, xMaxExpectedBlockTime ) == pdPASS)
        {
            /* 已获取信号量。在再次调用 xSemaphoreTake() 前处理所有待处理的 Rx
               事件。每个 Rx 事件都会把一个字符放入 UART 接收 FIFO；这里假定
               UART_RxCount() 返回 FIFO 中的字符数。 */
            while( UART_RxCount() > 0 )
            {
                /* 假定 UART_ProcessNextRxEvent() 处理一个 Rx 字符，使 FIFO 中
                   的字符数减 1。 */
                UART_ProcessNextRxEvent();
            }

            /* 已无待处理的 Rx 事件（FIFO 中没有字符），因此返回循环并调用
               xSemaphoreTake() 等待下一次中断。从此处到调用 xSemaphoreTake()
               之间发生的任何中断都会锁存在信号量中，不会丢失。 */
        }
        else
        {
            /* 未在预期时间内收到事件。检查 UART 是否存在可能阻止其继续生成
               中断的错误状态，并在必要时清除错误。 */
            UART_ClearErrors();
        }
    }
}
```

## 7.5 计数信号量

正如二值信号量可视为长度为 1 的队列，计数信号量也可视为长度大于 1 的队列。任务并不关心队列中存储的数据，只关心其中的项目数。必须在 `FreeRTOSConfig.h` 中将 `configUSE_COUNTING_SEMAPHORES` 设为 1，才能使用计数信号量。

每“给出”一次计数信号量，它所对应的队列就会多占用一个位置。队列中的项目数就是信号量的“计数”值。

计数信号量通常用于两件事：

1. 对事件计数[^18]

   在这种场景中，事件处理程序每遇到一个事件就“给出”一次信号量，使计数值加 1。任务每处理一个事件就“获取”一次信号量，使计数值减 1。因此，计数值等于已发生事件数与已处理事件数之差。图 7.8 展示了这一机制。

   用于计数事件的计数信号量创建时初始计数值为零。

   [^18]: 使用直接任务通知对事件计数比使用计数信号量更高效。第 10 章将介绍直接任务通知。

1. 资源管理

   在这种场景中，计数值表示可用资源的数量。任务要取得资源的控制权，必须先获取信号量，使信号量计数值减 1。计数值为零时，表示没有空闲资源。任务用完资源后“给出”信号量，使计数值加 1。

   用于管理资源的计数信号量，其初始计数值应等于可用资源数量。第 8 章将介绍如何使用信号量管理资源。

### 7.5.1 xSemaphoreCreateCounting() API 函数

所有类型的 FreeRTOS 信号量句柄都保存在 `SemaphoreHandle_t` 类型的变量中。使用信号量之前必须先创建它。要创建计数信号量，可以使用 `xSemaphoreCreateCounting()` API 函数。该函数从 FreeRTOS 堆中动态分配信号量所需的内存；FreeRTOS 还提供 `xSemaphoreCreateCountingStatic()`，使用调用者预先提供的内存创建计数信号量。

<a name="list7.11" title="代码清单 7.11 xSemaphoreCreateCounting() API 函数原型"></a>

```c
SemaphoreHandle_t xSemaphoreCreateCounting( UBaseType_t uxMaxCount,
                                            UBaseType_t uxInitialCount );
```
***代码清单 7.11*** *`xSemaphoreCreateCounting()` API 函数原型*

**xSemaphoreCreateCounting() 参数和返回值**

- `uxMaxCount`

   信号量可以达到的最大计数值。沿用队列类比，`uxMaxCount` 实际上就是队列长度。

   信号量用于对事件计数或锁存事件时，`uxMaxCount` 是能够锁存的最大事件数。

   当信号量用于管理对一组资源的访问时，`uxMaxCount` 应设置为可用的资源总数。

- `uxInitialCount`

   信号量创建后的初始计数值。

   信号量用于对事件计数或锁存事件时，应把 `uxInitialCount` 设为零，因为创建信号量时假定尚未发生任何事件。

   信号量用于管理一组资源的访问时，应把 `uxInitialCount` 设为 `uxMaxCount`，因为创建信号量时假定所有资源均可用。

- 返回值

  如果返回 `NULL`，则信号量创建失败，因为 FreeRTOS 没有足够的堆内存用于分配信号量数据结构。第 3 章提供了更多堆内存管理信息。

  如果返回非 `NULL` 值，则表示信号量创建成功。该返回值是所创建信号量的句柄。

<a id="76-deferring-work-to-the-rtos-daemon-task"></a>
## 7.6 将工作延迟到 RTOS 守护任务

前面介绍的延迟中断处理示例要求应用程序开发者为每个采用这种技术的中断创建一个任务。也可以使用 `xTimerPendFunctionCallFromISR()`[^19] API 函数，把中断处理延迟到 RTOS 守护任务中执行，从而不必为每个中断分别创建任务。把中断处理延迟到守护任务称为“集中式延迟中断处理”。

[^19]: 守护任务最初称为定时器服务任务，因为它起初只用于执行软件定时器回调函数。因此，`xTimerPendFunctionCall()` 实现在 `timers.c` 中。按照函数名前缀采用实现文件名称的惯例，该函数以 `Timer` 为前缀。

第 6 章介绍了软件定时器相关的 FreeRTOS API 如何通过定时器命令队列向守护任务发送命令。`xTimerPendFunctionCall()` 和 `xTimerPendFunctionCallFromISR()` 使用同一个队列向守护任务发送“执行函数”命令，指定的函数随后在守护任务上下文中执行。

集中式延迟中断处理的优点包括：

- 更低的资源使用

  不必为每个需要延迟处理的中断创建单独的任务。

- 简化的用户模型

  延迟中断处理函数就是普通的 C 函数。

集中式延迟中断处理的缺点包括：

- 灵活性较低

  无法为各个延迟中断处理函数单独设置优先级。所有这类函数都以守护任务的优先级执行。如第 6 章所述，守护任务优先级由 `FreeRTOSConfig.h` 中的编译时配置常量 `configTIMER_TASK_PRIORITY` 设置。

- 确定性较低

  `xTimerPendFunctionCallFromISR()` 把命令发送到定时器命令队列尾部。守护任务会先处理队列中已有的命令，再处理该函数发出的“执行函数”命令。

不同中断的时序约束各异，因此同一个应用程序通常会同时使用两种延迟中断处理方法。

<a id="761-the-xtimerpendfunctioncallfromisr-api-function"></a>

  `xTimerPendFunctionCallFromISR()` 会写入定时器命令队列。如果 RTOS 守护任务正处于阻塞状态，等待队列中出现数据，这次写入会使它离开阻塞状态。如果守护任务的优先级高于当前执行的任务（即被中断的任务），`xTimerPendFunctionCallFromISR()` 会在内部把 `*pxHigherPriorityTaskWoken` 设为 `pdTRUE`。

- 返回值

  有两种可能的返回值：

  - `pdPASS`

    如果“执行函数”命令已成功写入定时器命令队列，则返回 `pdPASS`。

  - `pdFAIL`

    如果定时器命令队列已满，无法写入“执行函数”命令，则返回 `pdFAIL`。第 6 章介绍了如何设置定时器命令队列长度。

  一个队列上可能阻塞着一个或多个等待数据到达的任务。调用 `xQueueSendToFrontFromISR()` 或 `xQueueSendToBackFromISR()` 可以使数据变为可用，让这些任务离开阻塞状态。如果被解除阻塞的任务优先级高于当前执行的任务（即被中断的任务），API 函数会在内部把 `*pxHigherPriorityTaskWoken` 设为 `pdTRUE`。

  如果 `xQueueSendToFrontFromISR()` 或 `xQueueSendToBackFromISR()` 把该值设为 `pdTRUE`，应在退出中断前执行上下文切换，确保中断直接返回到优先级最高的就绪状态任务。

- 返回值

  有两种可能的返回值：

  - `pdPASS`

    仅当数据已成功发送到队列时才返回 `pdPASS`。

  - `errQUEUE_FULL`

    如果由于队列已满而无法发送数据，则返回 `errQUEUE_FULL`。

<a id="772-considerations-when-using-a-queue-from-an-isr"></a>
### 7.7.2 从 ISR 使用队列时的注意事项

队列为从中断向任务传递数据提供了简便方法，但当数据以较高频率到达时，这种方法效率不高。

FreeRTOS 下载包中的许多演示应用程序都包含一个简单的 UART 驱动程序，它通过队列逐个传出 UART 接收 ISR 收到的字符。这些演示使用队列有两个目的：展示如何从 ISR 使用队列，以及有意增加系统负载以测试 FreeRTOS 移植版本。这样的 ISR 并不代表高效设计。除非数据到达速度很慢，否则不建议在生产代码中照搬这种技术。更适合生产代码的高效方法包括：

- 使用直接内存访问（DMA）硬件接收并缓冲字符。这种方法几乎没有软件开销。检测到传输结束中断后，再用直接任务通知[^20]解除负责处理缓冲区的任务的阻塞。

  [^20]: 直接任务通知是从 ISR 中解除任务阻塞最高效的方法。第 10 章“任务通知”将介绍这一功能。

- 把每个接收到的字符复制到线程安全的 RAM 缓冲区[^21]。收到完整消息或检测到传输结束中断后，同样可以用直接任务通知解除负责处理缓冲区的任务的阻塞。

  [^21]: FreeRTOS+TCP 提供的“流缓冲区”（[https://www.FreeRTOS.org/tcp](http://www.FreeRTOS.org/tcp)）可用于此目的。

- 直接在 ISR 中处理收到的字符，再通过队列把处理结果而不是原始数据发送给任务。图 5.4 已经演示了这种方法。

```c
{

    uint32_t ulValueToSend = 0;
    int i;

    /* 初始化 vTaskDelayUntil() 调用使用的变量。 */
    xLastExecutionTime = xTaskGetTickCount();

    for( ;; )
    {
        /* 这是一个周期性任务。阻塞到下一次运行时刻，每 200 毫秒执行一次。 */
        vTaskDelayUntil( &xLastExecutionTime, pdMS_TO_TICKS( 200 ) );

           保证本任务成功写入全部五个值。 */
        for( i = 0; i < 5; i++ )
        {
            xQueueSendToBack( xIntegerQueue, &ulValueToSend, 0 );
            ulValueToSend++;
        }

        /* 生成中断，让中断服务程序从队列读取这些值。生成软件中断所用的语法
           取决于当前 FreeRTOS 移植版本。以下语法仅适用于 FreeRTOS Windows

        vPrintString( "Generator task - About to generate an interrupt.\r\n" );
        vPortGenerateSimulatedInterrupt( mainINTERRUPT_NUMBER );
        vPrintString( "Generator task - Interrupt generated.\r\n\r\n\r\n" );
    }
}
```

```c
        "String 3\r\n"
    };

    /* 与往常一样，把 xHigherPriorityTaskWoken 初始化为 pdFALSE，以便检测
       中断安全 API 函数是否在内部将其设为 pdTRUE。中断安全 API 只能把
       xHigherPriorityTaskWoken 设为 pdTRUE，因此 xQueueReceiveFromISR()
       和 xQueueSendToBackFromISR() 调用可以安全地共用同一个变量。 */
    xHigherPriorityTaskWoken = pdFALSE;

    /* 不断读取队列，直到队列为空。 */
    while( xQueueReceiveFromISR( xIntegerQueue,
                                 &ulReceivedNumber,
                                 &xHigherPriorityTaskWoken ) != errQUEUE_EMPTY )
    {
        /* 只保留接收值的最低两位（取值为 0 到 3），再把截断后的值作为
           pcStrings[] 数组索引，选出要发送到另一个队列的字符串（char *）。 */
        ulReceivedNumber &= 0x03;
        xQueueSendToBackFromISR( xStringQueue,
                                 &pcStrings[ ulReceivedNumber ],
                                 &xHigherPriorityTaskWoken );
    }

    /* 如果从 xIntegerQueue 接收数据使一个任务离开阻塞状态，并且该任务的
       优先级高于运行状态任务，xQueueReceiveFromISR() 会在内部把
       xHigherPriorityTaskWoken 设为 pdTRUE。

       如果向 xStringQueue 发送数据使一个任务离开阻塞状态，并且该任务的
       优先级高于运行状态任务，xQueueSendToBackFromISR() 会在内部把
       xHigherPriorityTaskWoken 设为 pdTRUE。

       xHigherPriorityTaskWoken 作为参数传给 portYIELD_FROM_ISR()。如果它
       等于 pdTRUE，调用 portYIELD_FROM_ISR() 将请求上下文切换；如果仍为
       pdFALSE，则调用不会产生任何效果。

       Windows 移植版本使用的 portYIELD_FROM_ISR() 实现包含返回语句，因此
       本函数没有显式返回值。 */
    portYIELD_FROM_ISR( xHigherPriorityTaskWoken );
}
```

## 7.8 中断嵌套

任务优先级和中断优先级经常被混淆。本节讨论的是中断优先级，也就是各个中断服务程序（ISR）彼此之间的执行优先级。任务优先级与中断优先级没有任何关系：硬件决定 ISR 何时执行，软件决定任务何时执行。硬件中断触发的 ISR 可以中断任务，但任务不能抢占 ISR。

支持中断嵌套的 FreeRTOS 移植版本要求在 `FreeRTOSConfig.h` 中定义下面一个或两个常量。`configMAX_SYSCALL_INTERRUPT_PRIORITY` 和 `configMAX_API_CALL_INTERRUPT_PRIORITY` 定义的是同一项属性：较旧的移植版本使用前者，较新的移植版本使用后者。

**控制中断嵌套的常量**

- `configMAX_SYSCALL_INTERRUPT_PRIORITY` 或 `configMAX_API_CALL_INTERRUPT_PRIORITY`

  设置能够调用中断安全 FreeRTOS API 函数的最高中断优先级。

- `configKERNEL_INTERRUPT_PRIORITY`

  设置 Tick 中断使用的中断优先级，并且必须始终设为可用的最低中断优先级。

  如果当前 FreeRTOS 移植版本不使用 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 常量，那么所有调用中断安全 FreeRTOS API 的中断也必须以 `configKERNEL_INTERRUPT_PRIORITY` 定义的优先级执行。

每个中断源都有一个数字优先级和一个逻辑优先级：

- 数字优先级

  数字优先级就是分配给中断的优先级编号。例如，中断被设为优先级 7，其数字优先级就是 7；被设为优先级 200，其数字优先级就是 200。

- 逻辑优先级

  逻辑优先级表示一个中断相对于其他中断的优先顺序。

  如果两个优先级不同的中断同时发生，处理器先执行逻辑优先级较高的 ISR，再执行逻辑优先级较低的 ISR。

  一个中断可以抢占（嵌套于）逻辑优先级更低的中断，但不能抢占逻辑优先级相同或更高的中断。

数字优先级与逻辑优先级之间的关系取决于处理器架构。在某些处理器上，数字优先级越大，逻辑优先级*越高*；在另一些处理器上，数字优先级越大，逻辑优先级反而*越低*。

把 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 设为逻辑上高于 `configKERNEL_INTERRUPT_PRIORITY` 的中断优先级，即可建立完整的中断嵌套模型。图 7.14 展示了以下场景：

- 处理器有七个唯一的中断优先级。
- 分配数字优先级 7 的中断具有比分配数字优先级 1 的中断更高的逻辑优先级。
- `configKERNEL_INTERRUPT_PRIORITY` 设置为 1。
- `configMAX_SYSCALL_INTERRUPT_PRIORITY` 设置为 3。

- 当内核或应用程序处于临界区时，优先级为 1 到 3（含）的中断会被禁止执行。以这些优先级运行的 ISR 可以调用中断安全 FreeRTOS API。第 8 章将介绍临界区。

- 优先级为 4 或更高的中断不受临界区影响。因此，在硬件能力允许的范围内，无论调度器正在做什么，这些中断都能立即执行。以这些优先级运行的 ISR 不能调用任何 FreeRTOS API。

- 对时序精度要求极高的功能（例如电机控制）通常使用逻辑上高于 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 的优先级，以确保调度器不会给中断响应时间引入抖动。

<a id="781-a-note-to-arm-cortex-m22-and-arm-gic-users"></a>
### 7.8.1 ARM Cortex-M[^22] 和 ARM GIC 用户注意事项

[^22]: 本节只有部分内容适用于 Cortex-M0 和 Cortex-M0+ 内核。

Cortex-M 处理器的中断配置容易令人困惑，也很容易出错。为帮助开发者发现问题，FreeRTOS Cortex-M 移植版本会自动检查中断配置，但只有定义了 `configASSERT()` 才会执行这些检查。第 11.2 节将介绍 `configASSERT()`。

ARM Cortex 内核和 ARM 通用中断控制器（GIC）用数值*较小*的优先级编号表示逻辑优先级*较高*的中断。这看似违反直觉，也很容易忘记。要给中断分配较低的逻辑优先级，必须使用较大的数值；要分配较高的逻辑优先级，则必须使用较小的数值。

Cortex-M 中断控制器最多允许使用 8 位表示每个中断的优先级，因此 255 是可表示的最低逻辑优先级，0 是最高逻辑优先级。不过，Cortex-M 微控制器通常只实现这 8 位中的一部分，实际位数取决于微控制器系列。

如果只实现 8 个优先级位中的一部分，可用的是字节中的最高有效位，最低有效位没有实现。未实现位可以取任意值，但通常设为 1。图 7.15 展示了在只实现 4 个优先级位的 Cortex-M 微控制器中，如何存储二进制优先级 101。

* * *

图 7.15 中，由于最低 4 位没有实现，二进制值 101 被左移到最高有效的 4 位，未实现位则设为 1。

某些库函数要求传入已经左移到已实现（最高有效）位的优先级值。使用这类函数时，图 7.15 的优先级可指定为十进制 95：把二进制 101 左移 4 位得到 101nnnn（`n` 表示未实现位），再把未实现位设为 1，得到二进制 1011111，也就是十进制 95。

另一些库函数要求传入左移之前的优先级值。使用这类函数时，图 7.15 的优先级必须指定为十进制 5，即无需移位的二进制 101。

`configMAX_SYSCALL_INTERRUPT_PRIORITY` 和 `configKERNEL_INTERRUPT_PRIORITY` 必须采用可直接写入 Cortex-M 寄存器的形式，也就是把优先级值左移到已实现位之后的形式。

`configKERNEL_INTERRUPT_PRIORITY` 必须始终设为可用的最低中断优先级。未实现的优先级位可以设为 1，因此无论实际实现了多少位，该常量始终可以设为 255。

Cortex-M 中断的默认优先级为 0，也就是可用的最高优先级。Cortex-M 硬件不允许把 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 设为 0，因此任何调用 FreeRTOS API 的中断都绝不能保留默认优先级。
