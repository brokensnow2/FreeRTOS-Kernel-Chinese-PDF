# 13 故障排除

<a id="131-chapter-introduction-and-scope"></a>
## 13.1 章节介绍和范围

本章重点介绍 FreeRTOS 新手最常见的问题。首先，它侧重于多年来被证明是最频繁的支持请求来源的三个问题：不正确的中断优先级分配、栈溢出以及不恰当地使用 printf()。然后，它以 FAQ 风格简要涉及其他常见错误、它们的可能原因以及解决方案。

> *使用 `configASSERT()` 可以通过立即捕获和识别许多最常见的错误源来提高生产力。强烈建议在开发或调试 FreeRTOS 应用程序时定义 `configASSERT()`。`configASSERT()` 在第 12.2 节中描述。*

<a id="132-interrupt-priorities"></a>
## 13.2 中断优先级

> *注意：这是支持请求的头号原因，在大多数端口中，定义 `configASSERT()` 将立即捕获该错误！*

如果使用的 FreeRTOS 端口支持中断嵌套，并且中断的服务例程使用了 FreeRTOS API，那么*至关重要的是*中断的优先级必须设置在第 7.8 节中断嵌套中描述的 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 或更低。否则将导致临界区无效，进而导致间歇性故障。

如果在以下处理器上运行 FreeRTOS，请特别小心：

- 中断优先级默认为最高可能优先级，某些 ARM Cortex 处理器以及可能其他处理器就是这种情况。在此类处理器上，使用 FreeRTOS API 的中断的优先级不能保持未初始化状态。

- 数值高的优先级编号表示逻辑上低的中断优先级，这似乎违反直觉，因此可能引起混淆。同样，ARM Cortex 处理器以及可能其他处理器就是这种情况。

- 例如，在此类处理器上，以优先级 5 执行的中断本身可以被优先级为 4 的中断中断。因此，如果 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 设置为 5，任何使用 FreeRTOS API 的中断只能分配数值上大于或等于 5 的优先级。在这种情况下，中断优先级 5 或 6 是有效的，但中断优先级 3 绝对是无效的。

  ![](media/image91.png)

- 不同的库实现期望以不同方式指定中断的优先级。同样，这与针对 ARM Cortex 处理器的库特别相关，其中中断优先级在写入硬件寄存器之前会进行位移。有些库会自己执行位移，而其他库则期望在将优先级传递给库函数之前执行位移。

- 同一架构的不同实现实现了不同数量的中断优先级位。例如，来自一个制造商的 Cortex-M 处理器可能实现 3 个优先级位，而来自另一制造商的 Cortex-M 处理器可能实现 4 个优先级位。

- 定义中断优先级的位可以分割为定义抢占优先级的位和定义子优先级的位。确保所有位都分配给指定抢占优先级，以便不使用子优先级。

在某些 FreeRTOS 端口中，`configMAX_SYSCALL_INTERRUPT_PRIORITY` 的替代名称为 `configMAX_API_CALL_INTERRUPT_PRIORITY`。

<a id="133-stack-overflow"></a>
## 13.3 栈溢出

栈溢出是第二常见的支持请求来源。FreeRTOS 提供了几个功能来帮助捕获和调试与栈相关的问题[^28]。

[^28]: 这些功能在 FreeRTOS Windows 端口中不可用。

<a id="1331-the-uxtaskgetstackhighwatermark-api-function"></a>
### 13.3.1 uxTaskGetStackHighWaterMark() API 函数

每个任务维护自己的栈，创建任务时指定栈的总大小。`uxTaskGetStackHighWaterMark()` 用于查询任务接近耗尽分配给它的栈空间的程度。此值称为栈"高水位线"。

<a name="list13.1" title="Listing 13.1 The uxTaskGetStackHighWaterMark() API function prototype"></a>

```c
UBaseType_t uxTaskGetStackHighWaterMark( TaskHandle_t xTask );
```
***清单 13.1*** *uxTaskGetStackHighWaterMark() API 函数原型*

**uxTaskGetStackHighWaterMark() 参数和返回值**

- `xTask`

  正在查询其栈高水位线的任务（主体任务）的句柄——有关获取任务句柄的信息，请参阅 `xTaskCreate()` API 函数的 pxCreatedTask 参数。

  任务可以通过传递 NULL 代替有效的任务句柄来查询自己的栈高水位线。

- 返回值

  任务使用的栈空间量随着任务执行和中断处理而增减。`uxTaskGetStackHighWaterMark()` 返回自任务开始执行以来可用的最小剩余栈空间量。这是在栈使用量最大（或最深）时未使用的栈空间量。高水位线越接近零，任务越接近栈溢出。

也可以使用 `uxTaskGetStackHighWaterMark2()` API，它仅在返回类型上有所不同。

<a name="list13.2" title="Listing 13.2 The uxTaskGetStackHighWaterMark2() API function prototype"></a>

```c
configSTACK_DEPTH_TYPE uxTaskGetStackHighWaterMark2( TaskHandle_t xTask );
```
***清单 13.2*** *uxTaskGetStackHighWaterMark2() API 函数原型*

使用 `configSTACK_DEPTH_TYPE` 允许应用程序编写者控制用于栈深度的类型。

<a id="1332-run-time-stack-checkingoverview"></a>
### 13.3.2 运行时栈检查——概述

FreeRTOS 包括三个可选的运行时栈检查机制。这些由 FreeRTOSConfig.h 中的编译时常量 `configCHECK_FOR_STACK_OVERFLOW` 控制。两种方法都会增加执行上下文切换所需的时间。

栈溢出钩子（或栈溢出回调）是内核在检测到栈溢出时调用的函数。要使用栈溢出钩子函数：

1. 在 FreeRTOSConfig.h 中将 `configCHECK_FOR_STACK_OVERFLOW` 设置为 1、2 或 3，如下节所述。

2. 使用清单 13.3 所示的确切函数名称和原型提供钩子函数的实现。

<a name="list13.3" title="Listing 13.3 The stack overflow hook function prototype"></a>

```c
void vApplicationStackOverflowHook( TaskHandle_t *pxTask, signed char *pcTaskName );
```
***清单 13.3*** *栈溢出钩子函数原型*

提供栈溢出钩子是为了更容易捕获和调试栈错误，但在发生栈溢出时没有真正的方法可以恢复。该函数的参数将溢出了栈的任务的句柄和名称传递给钩子函数。

栈溢出钩子从中断上下文调用。

一些微控制器在检测到不正确的内存访问时会产生故障异常，并且有可能在内核有机会调用栈溢出钩子函数之前触发故障。

<a id="1333-run-time-stack-checkingmethod-1"></a>
### 13.3.3 运行时栈检查——方法 1

当 `configCHECK_FOR_STACK_OVERFLOW` 设置为 1 时选择方法 1。

任务每次被换出时，其整个执行上下文都会保存到其栈上。这很可能是栈使用达到峰值的时候。当 `configCHECK_FOR_STACK_OVERFLOW` 设置为 1 时，内核在上下文保存后检查栈指针是否保持在有效的栈空间内。如果发现栈指针超出其有效范围，则调用栈溢出钩子。

方法 1 执行速度快，但可能会遗漏上下文切换之间发生的栈溢出。

<a id="1334-run-time-stack-checkingmethod-2"></a>
### 13.3.4 运行时栈检查——方法 2

方法 2 执行方法 1 已有检查之外的额外检查。当 `configCHECK_FOR_STACK_OVERFLOW` 设置为 2 时选择此方法。

创建任务时，其栈会被填充已知模式。方法 2 测试任务栈空间的最后 20 个有效字节，以验证此模式未被覆盖。如果 20 个字节中有任何一个与其预期值不同，则调用栈溢出钩子函数。

方法 2 执行速度不如方法 1 快，但仍然相对较快，因为只测试 20 个字节。它很可能会捕获所有栈溢出；但是，有可能（尽管可能性极小）会遗漏某些溢出。

<a id="1334-run-time-stack-checkingmethod-3"></a>
### 13.3.4 运行时栈检查——方法 3

当 `configCHECK_FOR_STACK_OVERFLOW` 设置为 3 时选择方法 3。

此方法仅适用于选定的端口。当可用时，此方法启用 ISR 栈检查。当检测到 ISR 栈溢出时，会触发断言。请注意，在这种情况下不会调用栈溢出钩子函数，因为它特定于任务栈而非 ISR 栈。

<a id="134-use-of-printf-and-sprintf"></a>
## 13.4 printf() 和 sprintf() 的使用

通过 `printf()` 记录日志是一个常见的错误来源，并且对此不了解的应用程序开发者通常会添加更多的 `printf()` 调用来帮助调试，从而加剧问题。

许多交叉编译器供应商会提供适用于小型嵌入式系统的 `printf()` 实现。即使如此，该实现可能不是线程安全的，可能不适合在中断服务例程内使用，并且根据输出目标的位置，可能需要相对较长的执行时间。

如果没有专门为小型嵌入式系统设计的 `printf()` 实现，而是使用了通用的 `printf()` 实现，则必须特别小心，因为：

- 仅仅包含对 `printf()` 或 `sprintf()` 的调用就可能会大幅增加应用程序可执行文件的大小。

- `printf()` 和 `sprintf()` 可能调用 `malloc()`，如果使用 heap\_3 以外的内存分配方案，这可能无效。有关更多信息，请参见第 3.2 节示例内存分配方案。

- `printf()` 和 `sprintf()` 可能需要比正常情况下大得多的栈。

<a id="1341-printf-stdargc"></a>
### 13.4.1 Printf-stdarg.c

许多 FreeRTOS 演示项目使用一个名为 printf-stdarg.c 的文件，该文件提供了 `sprintf()` 的最小且栈高效的实现，可以替代标准库版本。在大多数情况下，这将允许为每个调用 `sprintf()` 和相关函数的任务分配更小的栈。

printf-stdarg.c 还提供了一种机制，用于逐字符将 `printf()` 输出定向到端口，虽然速度较慢，但允许进一步减少栈使用。

请注意，并非 FreeRTOS 下载中包含的所有 printf-stdarg.c 副本都实现了 `snprintf()`。未实现 `snprintf()` 的副本只是忽略缓冲区大小参数，因为它们直接映射到 `sprintf()`。

printf-stdarg.c 是开源的，但由第三方拥有，因此与 FreeRTOS 分开许可。许可条款包含在源文件的顶部。

<a id="135-other-common-sources-of-error"></a>
## 13.5 其他常见错误源

<a id="1351-symptom-adding-a-simple-task-to-a-demo-causes-the-demo-to-crash"></a>
### 13.5.1 症状：向演示中添加简单任务导致演示崩溃

创建任务需要从堆中获取内存。许多演示应用程序项目将堆的大小精确设置为刚好足以创建演示任务——因此，在创建任务后，将没有足够的堆剩余来添加任何其他任务、队列、事件组或信号量。

空闲任务（可能还有 RTOS 守护任务）在调用 `vTaskStartScheduler()` 时自动创建。仅当没有足够的堆内存剩余来创建这些任务时，`vTaskStartScheduler()` 才会返回。在调用 `vTaskStartScheduler()` 之后包含一个空循环 `[ for(;;); ]` 可以使此错误更易于调试。

为了能够添加更多任务，您必须增加堆大小，或删除一些现有的演示任务。堆大小的增加总是受限于可用的 RAM 量。有关更多信息，请参见第 3.2 节示例内存分配方案。

<a id="1352-symptom-using-an-api-function-within-an-interrupt-causes-the-application-to-crash"></a>
### 13.5.2 症状：在中断中使用 API 函数导致应用程序崩溃

不要在中断服务例程中使用 API 函数，除非 API 函数的名称以 '...FromISR()' 结尾。特别是，不要在中断内创建临界区，除非使用中断安全宏。有关更多信息，请参见第 7.2 节从 ISR 使用 FreeRTOS API。

在支持中断嵌套的 FreeRTOS 端口中，不要在分配了高于 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 的中断优先级的任何中断中使用任何 API 函数。有关更多信息，请参见第 7.8 节中断嵌套。

<a id="1353-symptom-sometimes-the-application-crashes-within-an-interrupt-service-routine"></a>
### 13.5.3 症状：应用程序有时在中断服务例程中崩溃

首先要检查的是中断是否导致栈溢出。某些端口只检查任务内的栈溢出，而不检查中断内的栈溢出。

中断的定义和使用方式因端口和编译器而异。因此，第二要检查的是中断服务例程中使用的语法、宏和调用约定是否完全符合所用端口文档页面的描述，以及是否与该端口提供的演示应用程序中的示例完全一致。

如果应用程序运行在使用数值小的优先级编号表示逻辑上高优先级的处理器上，请确保分配给每个中断的优先级考虑到了这一点，因为这可能看起来违反直觉。如果应用程序运行在默认每个中断的优先级为最大可能优先级的处理器上，请确保每个中断的优先级没有保持其默认值。有关更多信息，请参见第 7.8 节中断嵌套和第 13.2 节中断优先级。

<a id="1354-symptom-the-scheduler-crashes-when-attempting-to-start-the-first-task"></a>
### 13.5.4 症状：调度器在尝试启动第一个任务时崩溃

确保 FreeRTOS 中断处理程序已安装。有关信息，请参考所用 FreeRTOS 端口的文档页面，并参考该端口提供的演示应用程序示例。

某些处理器必须在特权模式下才能启动调度器。实现此目的的最简单方法是在调用 main() 之前，在 C 启动代码中将处理器置于特权模式。

<a id="1355-symptom-interrupts-are-unexpectedly-left-disabled-or-critical-sections-do-not-nest-correctly"></a>
### 13.5.5 症状：中断意外保持禁用状态，或临界区未正确嵌套

如果在调度器启动之前调用了 FreeRTOS API 函数，则中断将被有意保持禁用状态，并且直到第一个任务开始执行时才会重新启用。这样做是为了保护系统免受在系统初始化期间、调度器启动之前以及调度器可能处于不一致状态时尝试使用 FreeRTOS API 函数的中断所导致的崩溃。

不要使用除调用 `taskENTER_CRITICAL()` 和 `taskEXIT_CRITICAL()` 之外的任何方法更改微控制器的中断使能位或优先级标志。这些宏维护其调用嵌套深度的计数，以确保仅当调用嵌套完全展开到零时才重新启用中断。请注意，某些库函数本身可能会启用和禁用中断。

<a id="1356-symptom-the-application-crashes-even-before-the-scheduler-is-started"></a>
### 13.5.6 症状：应用程序甚至在调度器启动之前就崩溃了

可能导致上下文切换的中断服务例程不得在调度器启动之前执行。这同样适用于任何尝试向 FreeRTOS 对象（如队列或信号量）发送或从中接收的中断服务例程。在调度器启动之前无法发生上下文切换。

许多 API 函数在调度器启动之后才能调用。最好将 API 使用限制在创建对象（如任务、队列和信号量），而不是使用这些对象，直到调用 `vTaskStartScheduler()` 之后。

<a id="1357-symptom-calling-api-functions-while-the-scheduler-is-suspended-or-from-inside-a-critical-section-causes-the-application-to-crash"></a>
### 13.5.7 症状：在调度器挂起期间或在临界区内调用 API 函数导致应用程序崩溃

调度器通过调用 `vTaskSuspendAll()` 挂起，并通过调用 `xTaskResumeAll()` 恢复（取消挂起）。临界区通过调用 `taskENTER_CRITICAL()` 进入，并通过调用 `taskEXIT_CRITICAL()` 退出。

不要在调度器挂起期间或在临界区内调用 API 函数。

<a id="136-additional-debugging-steps"></a>
## 13.6 其他调试步骤

如果您遇到上述常见原因未涵盖的问题，可以尝试使用以下一些调试步骤。

- 在应用程序的 FreeRTOSConfig 文件中定义 `configASSERT()`，启用 malloc 失败检查和栈溢出检查。
- 检查 FreeRTOS API 的返回值以确保它们成功。
- 检查与调度器相关的配置，如 `configUSE_TIME_SLICING` 和 `configUSE_PREEMPTION`，是否根据应用程序要求正确设置。
- [此页面](https://www.freertos.org/Debugging-Hard-Faults-On-Cortex-M-Microcontrollers.html)提供了有关调试 Cortex-M 微控制器上硬件故障的详细信息。
