# 13 故障排查

<a id="131-chapter-introduction-and-scope"></a>
## 13.1 本章简介与范围

本章重点介绍 FreeRTOS 新用户最常遇到的问题。首先讨论多年来最常引发支持请求的三类问题：中断优先级分配错误、栈溢出，以及不恰当地使用 `printf()`。随后以常见问题解答的形式，简要介绍其他常见错误、可能原因和解决方法。

> *使用 `configASSERT()` 可以立即捕获并定位许多最常见的错误来源，从而提高开发效率。强烈建议在开发或调试 FreeRTOS 应用程序时定义 `configASSERT()`。第 12.2 节介绍了 `configASSERT()`。*

<a id="132-interrupt-priorities"></a>
## 13.2 中断优先级

> *注意：这是引发支持请求的首要原因。在大多数移植中，定义 `configASSERT()` 可以立即捕获此错误！*

如果所用 FreeRTOS 移植支持中断嵌套，并且某个中断的服务程序使用 FreeRTOS API，那么该中断的逻辑优先级*必须*设置为等于或低于 `configMAX_SYSCALL_INTERRUPT_PRIORITY`，具体说明参见第 7.8 节“中断嵌套”。否则临界区将无法有效工作，进而造成间歇性故障。

在具有以下特征的处理器上运行 FreeRTOS 时，应格外小心：

- 中断优先级默认处于可能的最高优先级。某些 ARM Cortex 处理器以及其他一些处理器就是如此。在这类处理器上，使用 FreeRTOS API 的中断不能保留未初始化的优先级。

- 数值较大的优先级编号表示逻辑上较低的中断优先级。这可能有违直觉，容易造成混淆。ARM Cortex 处理器以及其他一些处理器同样采用这种方式。

- 例如，在这类处理器上，以优先级 5 执行的中断可以被优先级 4 的中断抢占。因此，如果把 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 设为 5，任何使用 FreeRTOS API 的中断都只能分配数值大于或等于 5 的优先级。在这种情况下，中断优先级 5 或 6 有效，而中断优先级 3 明确无效。

  ![](media/image91.png)

- 不同的库实现要求以不同方式指定中断优先级。这一点对面向 ARM Cortex 处理器的库尤其重要，因为中断优先级在写入硬件寄存器前需要进行位移。有些库会自行执行位移，而另一些库要求在把优先级传给库函数之前完成位移。

- 同一种体系结构的不同实现可能实现不同数量的中断优先级位。例如，一家制造商的 Cortex-M 处理器可能实现 3 个优先级位，而另一家制造商的 Cortex-M 处理器可能实现 4 个优先级位。

- 定义中断优先级的位可以拆分为抢占优先级位和子优先级位。应确保所有这些位都用于指定抢占优先级，不使用子优先级。

在某些 FreeRTOS 移植中，`configMAX_SYSCALL_INTERRUPT_PRIORITY` 也称为 `configMAX_API_CALL_INTERRUPT_PRIORITY`。

<a id="133-stack-overflow"></a>
## 13.3 栈溢出

栈溢出是引发支持请求的第二常见原因。FreeRTOS 提供了多项功能，帮助捕获并调试与栈有关的问题[^28]。

[^28]: FreeRTOS Windows 移植不提供这些功能。

<a id="1331-the-uxtaskgetstackhighwatermark-api-function"></a>
### 13.3.1 uxTaskGetStackHighWaterMark() API 函数

每个任务都有自己的栈，其总大小在创建任务时指定。`uxTaskGetStackHighWaterMark()` 用于查询任务距离用尽所分配栈空间还有多近。该值称为栈的“高水位标记”。

<a name="list13.1" title="代码清单 13.1 uxTaskGetStackHighWaterMark() API 函数原型"></a>

```c
UBaseType_t uxTaskGetStackHighWaterMark( TaskHandle_t xTask );
```

***代码清单 13.1*** *`uxTaskGetStackHighWaterMark()` API 函数原型*

**uxTaskGetStackHighWaterMark() 参数和返回值**

- `xTask`

  要查询栈高水位标记的任务，也就是目标任务的句柄。有关如何获取任务句柄的信息，请参见 `xTaskCreate()` API 函数的 `pxCreatedTask` 参数。

  任务可以传入 NULL 代替有效的任务句柄，以查询自身的栈高水位标记。

- 返回值

  随着任务执行和中断处理，任务使用的栈空间会增加或减少。`uxTaskGetStackHighWaterMark()` 返回自任务开始执行以来曾经可用的最小剩余栈空间，也就是栈使用量达到最大值（最深位置）时仍未使用的栈空间。高水位标记越接近零，任务就越接近栈溢出。

可以使用 `uxTaskGetStackHighWaterMark2()` API 代替 `uxTaskGetStackHighWaterMark()`，两者仅返回类型不同。

<a name="list13.2" title="代码清单 13.2 uxTaskGetStackHighWaterMark2() API 函数原型"></a>

```c
configSTACK_DEPTH_TYPE uxTaskGetStackHighWaterMark2( TaskHandle_t xTask );
```

***代码清单 13.2*** *`uxTaskGetStackHighWaterMark2()` API 函数原型*

使用 `configSTACK_DEPTH_TYPE` 后，应用程序开发者可以控制表示栈深度所使用的类型。

<a id="1332-run-time-stack-checkingoverview"></a>
### 13.3.2 运行时栈检查：概述

FreeRTOS 包含三种可选的运行时栈检查机制。这些机制由 FreeRTOSConfig.h 中的编译时配置常量 `configCHECK_FOR_STACK_OVERFLOW` 控制。所有方法都会增加执行上下文切换所需的时间。

栈溢出钩子（或栈溢出回调）是内核检测到栈溢出时调用的函数。要使用栈溢出钩子函数：

1. 按照以下各小节的说明，在 FreeRTOSConfig.h 中把 `configCHECK_FOR_STACK_OVERFLOW` 设为 1、2 或 3。

1. 使用代码清单 13.3 所示的准确函数名和原型，实现该钩子函数。

<a name="list13.3" title="代码清单 13.3 栈溢出钩子函数原型"></a>

```c
void vApplicationStackOverflowHook( TaskHandle_t *pxTask, signed char *pcTaskName );
```

***代码清单 13.3*** *栈溢出钩子函数原型*

提供栈溢出钩子是为了更容易捕获并调试栈错误，但栈溢出发生后实际上无法可靠恢复。函数参数会把发生栈溢出的任务句柄和任务名称传入钩子函数。

栈溢出钩子在中断上下文中被调用。

某些微控制器检测到错误的内存访问时会生成故障异常，因此故障可能在内核有机会调用栈溢出钩子函数之前触发。

<a id="1333-run-time-stack-checkingmethod-1"></a>
### 13.3.3 运行时栈检查：方法 1

当 `configCHECK_FOR_STACK_OVERFLOW` 设为 1 时选择方法 1。

每当任务被换出时，其完整执行上下文都会保存到任务栈中，栈使用量很可能在此时达到峰值。当 `configCHECK_FOR_STACK_OVERFLOW` 设为 1 时，内核会在保存上下文后检查栈指针是否仍位于有效栈空间内。如果发现栈指针超出有效范围，就调用栈溢出钩子。

方法 1 执行速度快，但可能漏掉发生在两次上下文切换之间的栈溢出。

<a id="1334-run-time-stack-checkingmethod-2"></a>
### 13.3.4 运行时栈检查：方法 2

方法 2 会在方法 1 所述检查的基础上执行额外检查。当 `configCHECK_FOR_STACK_OVERFLOW` 设为 2 时选择该方法。

创建任务时，系统会用已知模式填充任务栈。方法 2 检查任务栈空间最后 20 个有效字节，确认该模式没有被覆盖。如果这 20 个字节中有任何一个与预期值不同，就调用栈溢出钩子函数。

方法 2 的执行速度不如方法 1，但由于只检查 20 个字节，速度仍然相对较快。它很可能捕获所有栈溢出，但仍有可能漏掉某些溢出，只是这种情况极不可能发生。

<a id="1334-run-time-stack-checkingmethod-3"></a>
### 13.3.4 运行时栈检查：方法 3

当 `configCHECK_FOR_STACK_OVERFLOW` 设为 3 时选择方法 3。

该方法仅在部分移植中可用。可用时，它会启用 ISR 栈检查。检测到 ISR 栈溢出时，系统会触发断言。请注意，此时不会调用栈溢出钩子函数，因为该钩子专门用于任务栈，而不是 ISR 栈。

<a id="134-use-of-printf-and-sprintf"></a>
## 13.4 printf() 和 sprintf() 的使用

通过 `printf()` 记录日志是一种常见错误来源。应用程序开发者如果没有意识到这一点，往往会为了辅助调试而继续增加 `printf()` 调用，反而使问题更加严重。

许多交叉编译器供应商会提供适合小型嵌入式系统使用的 `printf()` 实现。即使如此，该实现也可能不是线程安全的，很可能不适合在中断服务程序中使用，而且根据输出目标的不同，执行时间可能相当长。

如果没有专为小型嵌入式系统设计的 `printf()` 实现，而改用通用 `printf()` 实现，则必须格外谨慎，原因如下：

- 仅仅加入一次 `printf()` 或 `sprintf()` 调用，就可能显著增大应用程序可执行文件的体积。

- `printf()` 和 `sprintf()` 可能调用 `malloc()`。如果使用的内存分配方案不是 heap\_3，这种调用可能无效。更多信息参见第 3.2 节“内存分配方案示例”。

- `printf()` 和 `sprintf()` 所需的栈空间可能达到其他情况下的许多倍。

<a id="1341-printf-stdargc"></a>
### 13.4.1 printf-stdarg.c

许多 FreeRTOS 演示项目使用名为 printf-stdarg.c 的文件。该文件提供一种精简且节省栈空间的 `sprintf()` 实现，可替代标准库版本。大多数情况下，这样可以为每个调用 `sprintf()` 及相关函数的任务分配小得多的栈。

printf-stdarg.c 还提供一种把 `printf()` 输出逐字符发送到端口的机制。虽然这种方式速度较慢，但可以进一步减少栈使用量。

请注意，FreeRTOS 下载包中并非所有 `printf-stdarg.c` 副本都实现了 `snprintf()`。未实现 `snprintf()` 的版本会直接映射到 `sprintf()`，因而只是忽略缓冲区大小参数。

printf-stdarg.c 是开源软件，但归第三方所有，因此其许可证与 FreeRTOS 分开。许可证条款位于该源文件顶部。

<a id="135-other-common-sources-of-error"></a>
## 13.5 其他常见错误来源

<a id="1351-symptom-adding-a-simple-task-to-a-demo-causes-the-demo-to-crash"></a>
### 13.5.1 症状：向演示程序添加一个简单任务后，演示程序崩溃

创建任务需要从堆中获取内存。许多演示应用项目会把堆大小设为刚好足以创建演示任务。因此，创建这些任务后，剩余堆空间不足以继续添加任务、队列、事件组或信号量。

调用 `vTaskStartScheduler()` 时，系统会自动创建空闲任务，并且可能还会创建 RTOS 守护任务。只有剩余堆内存不足以创建这些任务时，`vTaskStartScheduler()` 才会返回。在 `vTaskStartScheduler()` 调用后加入一个空循环 `[ for(;;); ]`，可以让此错误更容易调试。

要添加更多任务，必须增大堆大小，或者移除一些现有演示任务。堆大小能够增加的程度始终受可用 RAM 容量限制。更多信息参见第 3.2 节“内存分配方案示例”。

<a id="1352-symptom-using-an-api-function-within-an-interrupt-causes-the-application-to-crash"></a>
### 13.5.2 症状：在中断中使用 API 函数导致应用程序崩溃

不要在中断服务程序中使用 API 函数，除非该 API 函数名以“...FromISR()”结尾。尤其不要在中断中创建临界区，除非使用中断安全宏。更多信息参见第 7.2 节“从 ISR 使用 FreeRTOS API”。

在支持中断嵌套的 FreeRTOS 移植中，不要在优先级高于 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 的中断内使用任何 API 函数。更多信息参见第 7.8 节“中断嵌套”。

<a id="1353-symptom-sometimes-the-application-crashes-within-an-interrupt-service-routine"></a>
### 13.5.3 症状：应用程序有时会在中断服务程序中崩溃

首先应检查该中断是否造成栈溢出。某些移植只检查任务中的栈溢出，而不检查中断中的栈溢出。

不同移植和编译器定义及使用中断的方式有所不同。因此，第二项检查是确认中断服务程序所使用的语法、宏和调用约定与当前移植的文档页面完全一致，并与该移植附带的演示应用程序完全一致。

如果应用程序运行在使用较小优先级编号表示较高逻辑优先级的处理器上，应确保为每个中断分配优先级时考虑这一点，因为这种方式可能有违直觉。如果应用程序运行在默认把每个中断设为可能的最高优先级的处理器上，应确保每个中断都没有保留默认优先级。更多信息参见第 7.8 节“中断嵌套”和第 13.2 节“中断优先级”。

<a id="1354-symptom-the-scheduler-crashes-when-attempting-to-start-the-first-task"></a>
### 13.5.4 症状：调度器尝试启动第一个任务时崩溃

确保已经安装 FreeRTOS 中断处理程序。有关说明，请参阅当前所用 FreeRTOS 移植的文档页面；有关示例，请参阅该移植附带的演示应用程序。

某些处理器必须处于特权模式才能启动调度器。最简单的实现方式是在调用 main() 之前，通过 C 启动代码把处理器置于特权模式。

<a id="1355-symptom-interrupts-are-unexpectedly-left-disabled-or-critical-sections-do-not-nest-correctly"></a>
### 13.5.5 症状：中断意外保持禁用，或临界区嵌套不正确

如果在调度器启动前调用 FreeRTOS API 函数，系统会有意保持中断禁用，直到第一个任务开始执行后才重新启用中断。这样可以防止系统初始化期间，在调度器尚未启动且可能处于不一致状态时，某个中断试图使用 FreeRTOS API 函数而导致系统崩溃。

除了调用 `taskENTER_CRITICAL()` 和 `taskEXIT_CRITICAL()` 之外，不要以任何其他方式修改微控制器的中断使能位或优先级标志。这些宏会记录调用嵌套深度，确保只有当调用嵌套完全退回到零时才重新启用中断。请注意，某些库函数本身也可能启用和禁用中断。

<a id="1356-symptom-the-application-crashes-even-before-the-scheduler-is-started"></a>
### 13.5.6 症状：应用程序在调度器启动前就已经崩溃

在调度器启动前，不得允许任何可能引起上下文切换的中断服务程序执行。任何试图向队列、信号量等 FreeRTOS 对象发送数据或从中接收数据的中断服务程序同样如此。调度器启动前无法进行上下文切换。

许多 API 函数必须在调度器启动后才能调用。在调用 `vTaskStartScheduler()` 之前，最好把 API 的使用限制在创建任务、队列和信号量等对象，而不要使用这些对象。

<a id="1357-symptom-calling-api-functions-while-the-scheduler-is-suspended-or-from-inside-a-critical-section-causes-the-application-to-crash"></a>
### 13.5.7 症状：调度器挂起或处于临界区时调用 API 函数导致应用程序崩溃

调用 `vTaskSuspendAll()` 会挂起调度器，调用 `xTaskResumeAll()` 会恢复调度器。调用 `taskENTER_CRITICAL()` 会进入临界区，调用 `taskEXIT_CRITICAL()` 会退出临界区。

不要在调度器挂起期间或临界区内部调用 API 函数。

<a id="136-additional-debugging-steps"></a>
 ## 13.6 其他调试步骤

如果遇到上述常见原因未涵盖的问题，可以尝试以下调试步骤：

- 定义 `configASSERT()`，并在应用程序的 FreeRTOSConfig 文件中启用内存分配失败检查和栈溢出检查。
- 检查 FreeRTOS API 的返回值，确认调用成功。
- 检查与调度器有关的配置，例如 `configUSE_TIME_SLICING` 和 `configUSE_PREEMPTION`，确认其设置符合应用程序要求。
- [此页面](https://www.freertos.org/Debugging-Hard-Faults-On-Cortex-M-Microcontrollers.html)详细介绍了如何调试 Cortex-M 微控制器上的硬故障。
